Codex 系统设计：一次任务究竟怎样跑起来

这篇不再讨论“好的 Agent 应有什么理念”，而是回答一个具体问题：你在 Codex 里输入“修好这个 bug”后，文字怎样变成工具调用，工具结果怎样回到模型，文件为什么真的被改了，测试失败后为什么还能继续，以及 DeepSeek V4 Pro 要兼容或优化 Codex 时到底要适配什么。

一、先把结论说清：Codex 不是一个模型

最小而准确的说法是：

Codex 是一套围绕模型运行的编程 Agent Harness；模型只负责根据当前输入决定下一步，Harness 负责组装输入、执行工具、保存状态、实施权限、把结果送回模型，并重复这个过程。

Harness 可以译作“运行支架”或“代理运行系统”。它不是一条系统提示词，也不是几个函数的集合。至少有六类部件：

部件负责什么不负责什么
客户端终端、IDE 或桌面界面；接收用户输入，显示过程、diff 和审批框通常不替模型决定代码怎么改
会话与编排核心维护 thread、turn、item；拼装模型请求；驱动工具循环不亲自理解业务语义
模型 API传送指令、历史、工具定义和结构化输出不执行本地命令
模型读上下文，推断下一步，输出消息或工具调用不能直接碰你的磁盘、终端和 GitHub
工具执行层运行 shell、应用补丁、读图、调用 MCP；返回 stdout、diff、错误不判断改动是否符合产品目标
权限与沙箱强制限制文件、网络和危险动作；必要时发起审批不依赖模型“自觉守规矩”

因此，最终效果不是简单的“模型分数 + 工具数量”。更接近下面三个因素的乘积：

  • 模型能力：能否理解代码、诊断失败、选择正确动作；
  • Harness 能力：能否把正确资料和可靠工具交给模型，并安全执行；
  • 模型—Harness 适配：模型是否熟悉这套消息格式、工具语法、错误输出和长任务节奏。
关于 DeepSeek V4 Pro 的当前事实：截至 2026 年 8 月 10 日，DeepSeek 官方 Codex 接入页仍写明：只有 deepseek-v4-flash 支持 Codex，V4 Pro 的 Responses API/Codex 支持“预计在 2026 年 8 月上旬”加入，但价格页仍标为不支持。官方明确说 V4-Flash-0731 经重新后训练、原生支持 Responses API，并“专门适配 Codex”；尚未公开证明 V4 Pro 正式版已经完成同样的 Codex 专项后训练。本文会把“接口接入”“配置适配”和“模型后训练”分开。

二、整条运行链：从一句话到一次真实改动

先看最重要的一张图。以下是一次本地 Codex 任务的逻辑路径；不同客户端的界面不同，但核心循环相近。

1. 用户
“修复退款金额为 0 时接口返回 500 的问题，并运行相关测试”
↓
2. Codex Harness
加载配置与 AGENTS.md，取出会话历史，列出工具，构造 Responses API 请求
↓
3. 模型
输出普通消息，或输出结构化工具调用：搜索、读文件、运行测试、应用补丁
↓
4. 权限网关与执行器
检查沙箱/审批 → 真正执行命令或补丁 → 得到 stdout、exit code、diff 或错误
↓
5. Harness 再次请求模型
把工具调用及其结果追加到历史；模型根据新证据决定下一步
↺ 重复，直到模型给出 final_answer 或任务失败/中断

这里最容易误解的一点是：模型不在一口气里完成整个任务。一次“修 bug”通常对应多次模型推理：

  1. 第一次推理：决定先搜索什么；
  2. Harness 执行搜索，把结果回传；
  3. 第二次推理：决定读哪些文件；
  4. Harness 返回文件内容；
  5. 第三次推理：提出补丁；
  6. Harness 应用补丁并返回 diff；
  7. 第四次推理：决定运行哪组测试；
  8. Harness 返回失败信息；
  9. 第五次推理：诊断新失败并修正；
  10. 测试通过后，模型才输出最终说明。

所以所谓“Agent 能连续工作”，不是模型在后台持续拥有意识，而是 Harness 不断进行“请求模型—执行动作—回传结果”的循环。

三、Codex 用什么数据结构管理一次任务

Codex App Server 的公开协议把运行状态分成三个核心对象：线程（Thread）、轮次（Turn）和条目（Item）。这是理解整套系统最直接的入口。

对象含义例子
Thread一段可以继续、恢复或分叉的完整对话“退款 bug 修复”这一整个会话
Turn一次用户请求及模型为此完成的全部工作“先诊断并修复”；下一轮可能是“再补回归测试”
Item轮次里可单独记录和流式展示的工作单元用户消息、模型消息、推理摘要、命令执行、文件改动、MCP 调用、计划更新

客户端启动一段会话时，大致会调用：

{
  "method": "thread/start",
  "id": 10,
  "params": {
    "model": "gpt-5.6-terra",
    "cwd": "/project/refund-service",
    "approvalPolicy": "onRequest",
    "sandbox": "workspaceWrite"
  }
}

用户发出任务时，再调用 turn/start：

{
  "method": "turn/start",
  "id": 11,
  "params": {
    "threadId": "thr_123",
    "input": [{
      "type": "text",
      "text": "修复退款金额为 0 时返回 500 的问题，并运行相关测试"
    }]
  }
}

随后，命令、补丁、计划、模型消息都变成 item。每个 item 通常经历 item/started 与 item/completed；后者是最终权威状态。例如命令 item 会携带命令、工作目录、状态、聚合输出、退出码和耗时，文件改动 item 会携带路径、改动类型与 diff。

这比“把所有过程写成一串聊天文本”多出两个关键能力：

  • 客户端能明确知道哪段是命令、哪段是 diff、哪段才是最终答复，不必从自然语言里猜；
  • 失败、审批、恢复和审计可以绑定到具体 item，而不是绑定到模糊的一整段回答。

四、模型每次到底看到了什么：上下文编译

大模型本身不会“打开仓库”。模型能看到的只有本次 API 请求里传入的内容。Codex 的一项核心工作，就是在每次推理前编译出合适的上下文（context）。可以把它理解成给模型生成一份临时输入包。

4.1 输入包的主要来源

来源怎样进入模型注意
Codex 基础指令作为高优先级指令，规定角色、工具习惯、安全与完成方式不同模型目录可以带不同基础指令
全局与项目 AGENTS.md启动时从全局、仓库根目录到当前目录逐层发现并注入离当前目录越近的规则越具体；默认合计上限为 32 KiB
用户本轮输入作为 turn 的输入 item这是任务目标，不等于全部项目背景
会话历史先前的用户消息、模型输出、工具调用及工具结果太长时需要压缩
工具定义名称、用途、参数 schema、调用格式模型只会请求调用；Harness 才真正执行
Skill触发后把完整 SKILL.md 及需要的资料加入当前任务不应把所有 Skill 正文永久塞进基础提示
文件与外部资料模型先调用 shell、文件工具、搜索或 MCP；结果作为新 item 回传仓库文件不会自动全部装进上下文

4.2 AGENTS.md 的注入不是“模型自己想起来读”

Codex CLI 会自动枚举这些文件。官方提示指南给出的具体形式是：每个发现到的文件被包装为一条靠近对话顶部的用户角色消息，大致如下：

# AGENTS.md instructions for services/refund
<INSTRUCTIONS>
修改退款逻辑后必须运行 make test-refund。
金额单位统一使用整数分，不得使用浮点数。
</INSTRUCTIONS>

注入顺序是从全局到仓库根目录，再到更深的子目录。这样，根目录可以规定通用测试，退款服务目录可以覆盖为自己的测试命令。这里没有神秘的“长期记忆”：本质是 Harness 在调用模型前把文件内容变成了输入消息。

4.3 为什么不把整个仓库一次塞进去

即使模型有一百万 token 的窗口，把整个仓库塞进去通常仍不合理：传输和推理更慢，成本更高，相关代码会被大量噪声稀释，而且仓库状态随工具执行不断变化。Codex 更常见的做法是：

  1. 先给模型目录位置、规则、工具和任务；
  2. 模型用 rg、git、测试命令等寻找证据；
  3. 只把命令返回的相关片段加入后续上下文；
  4. 需要时继续读取，输出过大时截断或分页。

因此，Codex 并不是“拥有仓库上下文”，而是拥有获取仓库上下文的能力。这一区别非常重要。

五、最核心的技术：模型—工具循环

下面是一段删去网络和异常细节后的伪代码。它不是 Codex 源码，但准确表达了公开协议呈现的逻辑：

history = load_thread(thread_id)
instructions = load_base_prompt() + discover_agents_md(cwd)
tools = build_tool_catalog(config, cwd)

while True:
    request = {
        "instructions": instructions,
        "input": history,
        "tools": tools,
        "parallel_tool_calls": True
    }

    response = responses_api(request)
    persist(response.output)

    if response contains final_answer and no pending tool call:
        finish_turn()
        break

    for call in response.tool_calls:
        decision = policy_engine.check(call, sandbox, approval_policy)

        if decision requires approval:
            decision = ask_client_and_wait(call)

        if decision is denied:
            result = tool_error("declined")
        else:
            result = executor.run(call)

        persist(result)
        history += call
        history += result

    if context_is_near_limit(history):
        history = compact(history)

5.1 工具调用不是一句“请运行测试”

模型返回的是机器可识别的结构。例如它可能输出：

{
  "type": "function_call",
  "call_id": "call_17",
  "name": "shell_command",
  "arguments": {
    "command": "rg -n \"refund|amount\" src tests",
    "workdir": "/project/refund-service"
  }
}

Harness 找到名为 shell_command 的执行器，检查权限，运行命令，然后把结果与同一个 call_id 绑定：

{
  "type": "function_call_output",
  "call_id": "call_17",
  "output": "src/refund.ts:42: if (!amount) throw ...\nexit_code: 0"
}

下一次模型推理会同时看到“我刚才请求了什么”和“真实世界返回了什么”。它由此发现 !amount 把合法的 0 当成假值，于是继续读测试或生成补丁。

5.2 Harness 不替模型规划，但替模型保持因果链

模型负责“看到结果后该怎么办”；Harness 负责保证调用与结果一一对应、顺序不乱、状态可保存。如果 Harness 丢了 call_id，把输出配给错误的调用，或者只保留 stdout 而丢掉失败状态，模型再聪明也会在错误证据上推理。

这就是模型适配为什么不只是“API 地址能通”。Agent 任务依赖一条很长的因果链：模型的第十步判断可能建立在前九次工具结果的结构和顺序上。

六、为什么 Codex 特别强调 Shell、apply_patch 和计划工具

6.1 Shell 是通用感知器和执行器

与给模型制作几十个“读文件”“列目录”“运行 Git”小工具相比，一个接近真实终端的 shell 工具覆盖面更广：rg 搜索、sed 读取、git diff 检查、测试框架验证、编译器报错都能通过同一接口返回。Codex 的模型训练又大量接触了终端轨迹，因此命令名称、参数和输出越接近真实终端分布，模型通常越容易正确使用。

长时间命令还需要进程状态。Codex 的执行工具可以启动带 PTY 的长驻会话，返回 session id；之后用 write_stdin 继续输入、轮询或终止。这使 REPL、开发服务器和长测试不必一次阻塞到结束。

6.2 apply_patch 把“编辑文件”变成受约束动作

模型若用 shell 拼接整份文件，容易因引号、编码、并发改动而覆盖用户内容。apply_patch 要求它给出局部 diff：

*** Begin Patch
*** Update File: src/refund.ts
@@
-  if (!amount) {
+  if (amount == null) {
     throw new InvalidAmountError();
   }
*** End Patch

Harness 解析这份补丁，检查上下文是否仍匹配当前文件，然后应用。失败时返回“找不到上下文”之类的明确错误，模型可以重新读取文件再生成补丁。OpenAI 官方提示指南明确建议使用其 apply_patch 实现，并说明 Codex 模型针对这种 diff 格式做过训练。

6.3 update_plan 不是推理器，而是外部任务状态

update_plan 只维护带状态的步骤列表，例如 pending、in_progress、completed。它不会自动规划，也不会保证任务完成；它的价值是把“当前正在做什么”变成结构化状态，供界面展示、用户纠偏和长任务恢复。

6.4 工具输出也需要设计

输出不是越多越好。官方 Codex 提示指南建议，工具返回接近 10k token 时截断，并保留头尾、截去中间；并建议并行调用按“多个 function_call，随后对应的多个 function_call_output”排列。原因不是审美，而是模型训练时见过这种分布。输出格式突然变化，可能让模型把语义搜索结果误认为 rg 输出，或误判某条命令的失败范围。

关键结论：工具的名称、参数、错误、输出截断、并行顺序，都是模型—Harness 接口的一部分；不只是函数能不能被调用。

七、状态、恢复和压缩：长任务为什么不会完全失忆

7.1 有两种状态，不能混为一谈

状态保存在哪里举例
对话/轨迹状态Thread 的持久化记录与模型历史用户目标、模型消息、工具调用、测试输出、计划
世界状态文件系统、Git、进程、数据库、外部服务当前代码内容、未提交 diff、测试服务器是否仍运行

恢复 thread 只能恢复“过去发生过什么”，不能保证世界仍和当时一样。用户可能在会话外改了文件，后台进程可能退出，远程分支可能更新。因此可靠 Agent 恢复后要重新读取 git status、关键文件和测试结果，而不能盲信旧聊天。

7.2 Resume、Fork、Steer、Interrupt

  • thread/resume：重新加载已保存的 thread，继续追加 turn；
  • thread/fork：复制某个历史点，创建新 thread，用于尝试另一条路线；
  • turn/steer：在当前 turn 尚未结束时追加用户要求，例如“先处理失败测试”；
  • turn/interrupt：请求取消当前 turn。

这说明用户干预不是“等 Agent 说完再发下一条聊天”这一种形式，而是运行协议的一部分。客户端知道哪个 turn 正在进行，能把新输入送入同一条运行轨迹。

7.3 Compaction 不是普通摘要

当历史接近上下文上限时，Codex 可以触发压缩（compaction）。Responses API 返回一个更短的压缩 item；它携带继续任务所需的关键先前状态，后续请求保留这个 item，而不必反复传送全部旧消息。这个对象是给模型继续运行用的，不是给用户阅读的完整会议纪要。

压缩必然有信息选择，因此重要的不变量不能只存在于漫长聊天里。测试命令、接口约束放进 AGENTS.md；任务当前状态放进计划或进度文件；真实改动保存在 Git diff；验收标准落实为测试。这样即使聊天被压缩，Agent 仍能从外部状态重建事实。

7.4 phase 等元数据为什么不能丢

Codex 的 assistant item 可以带 phase: commentary 或 phase: final_answer。前者表示工作中的进度消息，后者才是收尾。OpenAI 明确说明，对某些 Codex 模型，如果 Harness 在重建历史时丢掉 phase，性能会显著下降：模型可能把中间汇报误当作任务已经结束。

DeepSeek 的思考模式也有类似的协议要求：若一次 assistant 输出包含工具调用，后续请求必须完整回传相应 reasoning_content；丢失会直接得到 400 错误。这再次说明，Agent 历史不是“只保存可见文字”就够了。

八、模型为什么不能想做什么就做什么：沙箱与审批

Codex 把安全分成两个互相独立的层：

层回答的问题例子
沙箱（sandbox）这个动作在技术上能访问什么？只能写工作区；网络默认关闭；不能读取受保护路径
审批策略（approval policy）什么时候必须暂停并取得许可？出工作区写文件、联网、运行不受信命令时询问

模型先提出工具调用。策略引擎判断它是否在当前沙箱内；需要越界时，App Server 给客户端发起一个服务器请求，包含 thread、turn、item、命令、工作目录、理由和可选决策。用户或独立 reviewer 返回接受、会话内接受、拒绝或取消。之后执行器才继续，最终 item 标记为 completed、failed 或 declined。

所以“系统提示里写着不要访问网络”只是软约束；“进程处于无网络沙箱”才是硬约束。模型即使被提示注入诱导，也只能发起请求，不能凭一段文本自行突破操作系统边界。

这也是 Codex 相比许多简单 Agent 的实质优势之一：安全边界不由同一个可能犯错的模型同时提出、解释和执行。模型负责申请，确定性程序负责裁决和强制。

九、App Server 和事件流：为什么 CLI、IDE、桌面端可以共用核心

Codex App Server 对客户端提供双向 JSON-RPC 2.0 风格协议，可通过标准输入输出的 JSONL、WebSocket 或 Unix socket 传输。客户端先 initialize，再启动或恢复 thread、启动 turn，并持续读取通知。

常见事件包括：

  • turn/started、turn/completed：一轮任务开始与结束；
  • item/started、item/completed：命令、补丁、消息等工作单元的生命周期；
  • item/commandExecution/outputDelta：终端输出增量；
  • item/agentMessage/delta：模型消息增量；
  • turn/diff/updated：本轮累积 diff；
  • turn/plan/updated：计划状态更新；
  • 审批请求与 serverRequest/resolved：客户端接管需要用户决定的动作。

因此界面不需要理解模型的全部逻辑。它只订阅结构化事件：终端面板渲染 command item，diff 面板渲染 fileChange，进度区渲染 plan，聊天区渲染 commentary 和 final_answer。Codex CLI、SDK 与富客户端可以共享 thread/turn/item 语义，同时拥有不同 UI。

非交互模式 codex exec --json 也会输出 JSONL，例如 thread.started、turn.started、item.*、turn.completed。CI 可以不解析人类聊天文字，直接消费事件和最终结构化结果。

十、“模型为 Codex 特殊优化”究竟可能优化什么

这句话至少有四个完全不同的技术层级。以后看到厂商宣传，先问它指哪一级。

级别具体工作只做到这一级会怎样
1. 传输协议兼容实现 Responses API 的请求、流式事件、工具调用与结果回传Codex 能连上，但模型未必会高质量使用 Harness
2. 模型目录适配声明上下文窗口、推理档位、apply_patch 类型、shell 类型、并行工具、截断策略Harness 知道怎样和该模型通信
3. 提示与轨迹适配提供合适基础指令，保存 phase/reasoning 等元数据，匹配工具输出分布长任务不易因格式错误、提前结束或历史损坏而崩溃
4. 模型后训练用真实或合成 Agent 轨迹训练：搜索、补丁、测试、失败恢复、审批、收尾模型本身学会在这套 Harness 里选择更好的动作

10.1 DeepSeek 已公开了什么

DeepSeek 的 Codex 配置页很有价值，因为它直接公开了一份模型目录。V4 Flash 和计划中的 V4 Pro 条目包含：

wire_api = responses apply_patch = freeform shell = shell_command parallel_tool_calls = true context = 1,048,576 tool output limit = 10,000 tokens multi_agent v2

这说明 Codex 不是把任意模型名称写进 config.toml 就完事；Harness 还要知道这个模型支持怎样的补丁、shell、推理等级、并行和上下文策略。DeepSeek 页面甚至把 Codex 基础 instructions 放进 models.json，表明模型提示也被视为 provider 适配的一部分。

2026 年 7 月 31 日的官方更新进一步说，V4-Flash-0731 架构和尺寸不变，只重新进行了后训练；新版增强 Agent 能力，原生支持 Responses API，并专门适配 Codex。这里可以确认“V4 Flash 不只是加了一个 API 转换层”。但官方没有公开训练数据构成、是否直接使用 Codex 轨迹、各项优化贡献，也没有对尚未正式支持 Codex 的 V4 Pro 给出同等陈述。

10.2 为什么基础模型很强，接入后仍可能很差

  • 能写正确代码，却经常输出无法解析的补丁；
  • 会调用工具，但不根据 exit code 和 stderr 修复；
  • 把 commentary 当 final，汇报完计划就提前停止；
  • 并行调用顺序混乱，把 A 工具的输出配给 B；
  • 工具调用后丢失必要 reasoning 元数据，下一请求报错；
  • 面对 10k token 截断输出，不会继续缩小范围读取；
  • 写完代码后不运行测试，或测试失败仍宣称完成。

这些不完全是“智力”问题，而是轨迹分布问题。模型若在后训练中反复经历“搜索—读取—补丁—测试—失败—修复—复验—总结”，就更可能在 Codex 里形成稳定动作习惯。

判断 DeepSeek V4 Pro 是否真的为 Codex 优化：等正式支持后，至少检查四件事：官方是否明确写“专门适配/后训练”；Responses API 是否完整保留工具与 reasoning/phase 相关状态；官方模型目录是否与实际能力一致；在同一 Codex 版本、同一任务、同一权限下，端到端修复率是否提高。只看“能够在模型选择器里出现”远远不够。

十一、Codex 相比“普通 Agent”多了什么

“普通 Agent”没有统一定义。这里以最常见的简单 ReAct 实现作比较：一份系统提示、一个 messages 数组、若干 function tools、一个 while 循环。

技术点简单 Agent 常见做法Codex 做法
任务状态内存中的聊天 messages持久化 Thread → Turn → Item，可恢复、分叉、归档
项目规则每次手贴一大段 promptAGENTS.md 从全局到当前目录自动发现并分层注入
行动接口随手定义几个函数围绕 shell、apply_patch、计划等训练分布较稳定的工具
工具轨迹只保存可见文本或简化结果保留 call、output、item 状态、phase、错误和增量事件
长任务超长后整体摘要一等 compaction item，加外部文件/diff/计划保存真实状态
安全提示模型“不要做危险操作”操作系统沙箱 + 审批协议 + 精确作用域

这些并不是 Codex 独有的理论发明。一个认真设计的自研 Agent 完全可以实现相同机制。Codex 的优势在于：这些机制被做成完整产品，并与模型后训练、工具格式、客户端协议和权限执行共同磨合，而不是停留在一张架构图上。

十二、知道原理后，怎样更好地与 Codex 和未来的 V4 Pro 协作

12.1 给 Harness 可验证的终点，不要只给抽象愿望

好的任务描述至少包含四类信息：

目标：修复 amount=0 时退款接口返回 500。
定位：相关代码在 services/refund，接口为 POST /refund。
边界：金额仍使用整数分；不要改公开响应 schema。
完成条件：新增回归测试；运行 make test-refund；最后检查 git diff。

这不是为了“讨好模型”，而是为 Agent loop 提供停止条件。模型知道该搜索哪里，测试命令能提供确定反馈，最终是否完成可以被人检查。

12.2 把稳定规则放在正确位置

  • 一次任务特有的目标：放当前 prompt；
  • 整个仓库都适用的构建、测试与禁令：放根 AGENTS.md；
  • 某个子系统特有的命令和不变量：放靠近该目录的 AGENTS.md；
  • 可复用的完整工作流：做成 Skill；
  • 必须强制执行的权限与危险动作：交给沙箱、规则和审批，不要只写提示。

12.3 发生问题时先判断坏在哪一层

现象优先怀疑怎样验证
工具调用 JSON/补丁无法解析模型—工具格式适配查看 tool call 原始 item 与模型目录里的工具类型
模型提出命令但未运行审批、沙箱或执行器查看 item 是否 declined、SandboxError 或等待 approval
工具调用后 API 返回 400provider 历史重放DeepSeek 思考模式检查 reasoning_content 是否完整保留
补丁正确但没跑测试任务完成定义或模型轨迹检查 AGENTS.md/Prompt 是否给出验证要求及是否存在测试 item
长任务忘记早期约束上下文压缩与外部状态检查约束是否只在旧聊天，是否有计划/规格/测试承载
反复读错目录cwd、项目指令或检索策略查看 thread 的 cwd、instructionSources 与搜索命令
中途汇报后直接结束phase 保存、基础提示或模型适配查看 commentary/final_answer item 是否被正确区分

12.4 V4 Pro 支持后怎样做公平实测

固定同一 Codex 版本、同一仓库快照、同一 AGENTS.md、同一权限、同一推理档位和同一任务集，只替换模型。每个任务从干净 Git worktree 开始，记录：

  • 最终测试通过率和隐藏验收通过率；
  • 错误工具调用、补丁应用失败和 API 失败次数；
  • 测试失败后的恢复率；
  • 虚假完成率，即声称完成但验证未通过；
  • 模型请求次数、输入/输出 token、工具次数、总耗时和费用；
  • 需要用户澄清或审批的次数。

如果只比较聊天回答，你测到的是代码讲解能力；只有让模型在同一 Harness 里真正读、改、测，才是在测 Codex Agent 能力。

十三、怎样把这套设计借到你自己的 Agent

不要一上来复刻整个 Codex。按下面顺序做一个最小可用 Harness，每一步都能独立验收。

13.1 第一步：先把运行记录从聊天文本升级为事件

Thread {
  id, provider, model, cwd, created_at, status
}

Turn {
  id, thread_id, user_input, status, started_at, ended_at
}

Item {
  id, turn_id,
  type,          // user_message | agent_message | tool_call | tool_result | file_change
  status,        // started | completed | failed | declined
  payload_json,
  created_at
}

先做到：服务重启后能恢复 thread；每个 tool_result 能找到对应 tool_call；失败 item 不会被当成成功。没有这一步，后续压缩、审计和 UI 都会依赖脆弱的字符串解析。

13.2 第二步：实现最小 Agent loop

只接三个工具：只读搜索、局部补丁、验证命令。每个工具都有明确 JSON schema、超时、错误类型和最大输出。循环只处理三种模型输出：消息、工具调用、最终回答。不要让模型把“要运行的命令”藏在普通 Markdown 里由正则提取。

13.3 第三步：在执行器前加策略网关

model tool call
      ↓
validate schema
      ↓
classify side effect
      ↓
check allowed roots / network / command policy
      ↓
allow | ask approval | deny
      ↓
execute and return structured result

策略网关要用确定性代码。模型可以给出理由，但不能自己批准自己的越权请求。

13.4 第四步：做上下文编译器

将输入分层：基础指令、项目规则、本轮任务、最近轨迹、工具目录、按需资料、压缩状态。为每一层设置来源、优先级和 token 预算。工具输出太大时不要静默丢弃；返回“已截断、原始大小、保留范围”，让模型知道需要再次缩小查询。

13.5 第五步：把“完成”交给验证器提供证据

模型可以决定运行哪些验证，但通过与否由测试、类型检查、schema 校验或业务规则程序返回。Turn 只有同时满足以下条件才标记 completed：

  • 没有待处理工具调用或审批；
  • 模型产生 final，而不是 commentary；
  • 任务要求的验证 item 已成功；
  • 所有文件改动有可回读 diff；
  • 若验证缺失，最终状态明确标为“未验证”，不能伪装成完成。

13.6 第六步：最后再加压缩、多 Agent 和 MCP

单 Agent 的事件、工具、权限、验证和恢复稳定后，再做：

  • 压缩：保留任务目标、已确认事实、未决问题、文件与验证状态；
  • 子 Agent：为每个子任务创建隔离 thread，结果作为结构化 item 汇总；
  • 并行：只并行互不依赖的读取或隔离工作区写入；
  • MCP：把外部系统工具也放进同一个权限与事件模型；
  • 评测：保存完整 trace，按失败层归因，而不只给最终答案打分。

对 InnoSpark 这类系统，最值得直接借鉴的不是“让 Agent 更自主”，而是三件技术部件：上下文编译器、事件化任务状态、确定性验证闭环。它们能解决多 AI 讨论中最难维护的矛盾：每条结论从哪里来、由什么动作产生、后来被什么证据推翻，以及当前哪一版才有效。

十四、公开资料能确认到哪里

Codex CLI、Codex SDK 和 App Server 的关键部分是开源的；官方文档公开了 App Server 协议、thread/turn/item、审批、事件、AGENTS.md 注入、工具建议和 compaction。IDE 扩展与 Codex Cloud 并非全部开源，因此本文没有把云端调度、内部系统提示生成、训练数据或隐藏评测细节写成已知事实。

文中的“会话与编排核心”是依据公开接口划分的逻辑层，而不是声称 OpenAI 内部恰好以同名服务部署。伪代码表达的是可观察的运行机制，不是逐行复刻源码。

十五、把整篇压缩成一句可用的话

Codex 的本质，是把模型放进一个持久、可执行、可验证、可审批的事件循环：模型提出下一步，Harness 决定怎样执行并把真实结果送回来，直到出现有证据支持的完成状态。

以后评价 DeepSeek V4 Pro 的“Codex 优化”，不要只问它代码能力多强。要分别问：Responses API 是否兼容；历史元数据是否无损；工具格式是否匹配；模型是否经过 Agent 轨迹后训练；同一 Harness 下是否更会搜索、修改、验证和恢复。理解这五件事，你才能判断问题出在模型还是 Codex，也才能把 Codex 的有效部分真正借到自己的系统里。

Codex 系统设计：模型与 Harness 如何协同

把 GPT-5.6 Sol 的模型能力，与 Codex 的上下文、工具、执行环境、权限、验证和恢复机制分开理解

领域：AI · 核心问题：Codex 为什么不只是“会写代码的模型”，以及怎样把它的系统设计借到自己的 Agent 项目中

先给结论：Codex 的优势不应被概括成“GPT-5.6 Sol 很强”或“给模型接了终端”。更准确的对象是一个闭环工作系统：模型负责在不完全信息下理解、判断、生成和选择行动；运行支架（harness）负责组织指令与上下文、暴露受约束的工具、执行动作、保存外部状态、返回真实反馈、控制权限，并用测试与差异证明任务是否完成。二者还有显著的适配效应，所以不能用简单减法把贡献完全剥离。

一、先划清三个对象：模型、Harness、产品界面

你提出的拆分非常重要，因为人看到的是 Codex 的最终体验，却很容易把整套系统的行为都归因于模型。至少要区分三层：

  1. 模型（model）：例如 GPT-5.6 Sol。它接收当前请求中可见的消息、工具说明和工具结果，产生文本或结构化工具调用。它的能力包括语义理解、代码推理、计划、工具选择、根据错误修正方案等。
  2. 运行支架（harness）：围绕模型的一整套运行契约。OpenAI 的公开材料把 harness 概括为指令、工具、路由、输出要求和验证检查的整体。本文还把会话运行时、上下文组装、权限、执行环境、持久状态和恢复机制纳入其中。
  3. 产品界面（surface）：CLI、IDE、桌面端、云端、SDK 或你自己做的客户端。界面负责把任务、进度、命令、差异、审批和结果呈现给人，但界面不等于底层 Agent 逻辑。

一次任务的可观察效果，更适合写成下面的分解：

Q观察 = Q模型 + Q支架 + Q交互 + ε Q_{\text{观察}}=Q_{\text{模型}}+Q_{\text{支架}}+Q_{\text{交互}}+\varepsilon

其中“交互项”不是可有可无的修饰。模型是否接受过面向工具调用、代码修改、长任务恢复的训练，会影响它能否充分利用 harness；反过来，工具描述、观察格式和完成条件是否契合模型，也会影响同一个模型的表现。因此，即使你拿到同名 API 模型，随手接一个 Shell，也不必然复现 Codex 的体验。

证据边界：OpenAI 已公开 Codex 的大量行为、协议和扩展接口，但没有公开生产系统的全部私有调度逻辑、隐藏指令和每一种上下文压缩策略。下文凡涉及官方明确说明的行为，会称为“已核验事实”；把这些事实组织成七层架构，是本文为了分析而做的系统建模，不声称等同于 OpenAI 内部唯一真实的模块图。

二、GPT-5.6 Sol 本身贡献什么，又不直接负责什么

截至本文核验时，官方把 GPT-5.6 Sol 定位为 GPT-5.6 系列中处理复杂专业工作的前沿模型，模型标识为 gpt-5.6-sol，gpt-5.6 别名路由到它。官方模型页列出的上下文窗口为 1,050,000 token，最大输出为 128,000 token，并支持函数调用（function calling）、结构化输出（structured outputs）以及多类工具接口。这说明它具备成为强 Agent“决策核”的条件，但不说明它独自拥有文件系统、终端或项目状态。

2.1 模型擅长的是条件判断，不是替代运行环境

在 Codex 回路里，模型主要完成四类不可轻易写成确定性程序的工作：

  • 解释目标：把自然语言中的意图、约束、非目标和隐含风险转成当前行动。
  • 选择信息：判断下一步该读哪份文件、查哪个符号、运行哪条测试，而不是把整个仓库无差别塞进上下文。
  • 生成候选改变：提出设计、写代码、改文档、构造测试，并在多种方案中权衡。
  • 诊断与修复：看到编译错误、测试失败、日志或差异后，形成新的因果解释并决定如何纠正。

这几项都依赖跨文件语义和情境判断，是模型的核心价值。若换成能力明显更弱的模型，即便工具和沙箱完全相同，也可能出现读错入口、修复表象、不理解不变量或无法在失败后重规划的问题。

2.2 模型不直接保证五件事

  • 它不会凭自身参数实时知道你磁盘上文件的真实内容；必须由 harness 读取并返回。
  • 它输出“运行测试”不等于测试真的运行；必须有执行器启动进程并捕获退出码。
  • 它认为“已经完成”不等于验收标准成立；必须由外部检查给出证据。
  • 它承诺“不碰工作区外文件”不是安全边界；必须由操作系统级沙箱或权限系统强制。
  • 它记得上一步不等于状态可靠持久化；长任务仍需要文件、Git、日志或会话存储承载状态。

这正是模型与 harness 的根本分工：模型给出带不确定性的决策，系统把决策变成受约束、可观察、可恢复的现实动作。

三、把 Codex 重建成一张七层系统图

官方长任务材料把核心循环概括为：规划、编辑、运行测试或构建工具、观察结果、修复失败、更新文档或状态，然后重复。为了回答“为什么这比普通 Agent 更稳”，还需要把循环背后的支撑层展开。

第 7 层：人机交互与并行调度
进度流、转向、暂停、恢复、审阅、子 Agent、工作树
第 6 层：验证与完成契约
测试、构建、lint、类型检查、差异审阅、完成定义
第 5 层：外部状态与恢复
仓库文件、Git diff、工件、线程日志、检查点、压缩摘要
第 4 层：执行与权限边界
工作目录、进程、沙箱、网络策略、审批、规则
第 3 层：工具与扩展
Shell、补丁、检索、MCP、插件、Skill 脚本、结构化结果
第 2 层：指令与上下文组装
目标、AGENTS.md、Skill 渐进加载、相关文件、近期观察
第 1 层：模型决策核
理解、规划、代码生成、工具选择、错误诊断与重规划

3.1 会话运行时：Thread、Turn、Item 不只是界面名词

Codex App Server 的公开协议把运行状态拆成线程（thread）、轮次（turn）和项目（item）：线程容纳一段可继续、可恢复或可分叉的对话；一轮对应一次用户请求及其后续 Agent 工作；item 则是用户消息、模型消息、命令执行、文件改变或工具调用等事件单位。

这种设计比“不断往一个 messages 数组末尾追加字符串”多了几个关键能力：

  • 命令、工具、文本和文件变化都有明确类型，客户端不必从自然语言里猜发生了什么。
  • 长任务可以流式报告 started、增量输出、completed 或 interrupted，人可以在运行中转向（steer）或中断。
  • 线程可恢复、分叉、归档和压缩；“继续工作”不必依赖模型凭空复述旧状态。
  • 审批请求能够绑定到具体线程、工具调用和动作，而不是成为一条脱离上下文的弹窗。

这已经揭示一个重要架构原则：Agent 是事件驱动的状态机，不是一段无限递归的提示词。

3.2 指令与上下文组装：真正稀缺的是注意力，而不是窗口上限

1.05M token 的窗口很大，但“能放下”不等于“应该全放进去”。Codex 的公开设计至少包含两种上下文分层机制：

  1. 持久项目指令：AGENTS.md 按全局、仓库根目录到当前工作目录逐层发现，较近目录的规则更具体。这样，同一条通用开发原则和某个子模块的特殊测试命令可以同时存在。
  2. Skill 渐进披露（progressive disclosure）：启动时先只暴露 Skill 的名称和描述；匹配到任务后再加载完整 SKILL.md，随后按需读取引用资料或运行脚本。大量工作流不必常驻上下文。

此外，模型通过文件搜索、符号搜索和命令逐步取得仓库信息。一个好的 harness 不是“把一切交给模型”，而是像编译器一样，把目标、规则、相关证据和最新观察组装成当前决策所需的上下文包。本文把这层称为上下文编译器（context compiler）；这是分析用名称，不是官方模块名。

设计含义：上下文管理的目标不是最大化 token 使用量，而是最大化“当前一步所需证据 / 总上下文”的比例。子 Agent、摘要、Skill 渐进加载和外部文件状态，本质上都在对抗主线程被日志与中间草稿污染。

3.3 工具层：工具不是 API 列表，而是行动契约

模型想修改现实世界，必须通过工具调用（tool calling）。Codex 的基本工具包括读取与修改文件、执行命令、查看差异等；MCP（Model Context Protocol）和插件又可连接浏览器、设计工具、GitHub 或其他系统。Skill 则主要说明怎样组合这些工具完成可复用工作流。

官方工具设计文档要求每个工具明确名称、意图、输入与输出模式、授权、外部副作用和失败行为，并建议把读取与写入拆开。它解决的不是形式美观，而是四个实际问题：

  • 可选择：模型能根据描述判断何时调用，避免多个工具语义重叠。
  • 可校验：结构化参数可以在执行前检查类型、枚举、必填字段和目标身份。
  • 可恢复：结构化错误能告诉模型是参数错误、权限不足、资源不存在还是暂时失败。
  • 可治理：系统能区分只读、写入、破坏性和开放世界动作，应用不同审批策略。

所以，“给 Agent 一段 Python，可以调用所有内部 API”通常不是灵活，而是放弃了路由、安全、可观察性和评测边界。工具粒度应围绕用户可理解的完整动作设计，同时把权限或风险不同的动作拆开。

3.4 执行层：Sandbox 与 Approval 是正交的两道门

沙箱（sandbox）回答“技术上能做什么”，审批策略（approval policy）回答“何时必须停下来问谁”。官方文档明确把两者分开：本地默认通常禁止网络，写权限限制在活动工作区；模型生成的子进程也继承相同边界。当动作需要跨出边界时，审批流程才介入。

这比在系统提示词里写“危险命令先询问”强得多，因为安全属性不再依赖模型始终正确理解和服从。Codex 还允许用规则（rules）对命令前缀设置允许、询问或禁止，并对可安全解析的复合 Shell 命令逐项检查。Hooks 则能在工具调用前后、压缩前后、停止时等生命周期节点运行确定性脚本，完成密钥扫描、自定义验证或审计。

由此得到一个可借鉴的原则：自主性不是取消限制，而是扩大一块边界清楚、失败可见、日常动作无需反复审批的安全工作区。

3.5 外部状态：把任务记在世界里，而不是只记在对话里

官方长任务文章把 Codex 的连贯性归因于真实反馈、外部化状态和持续可转向性。代码仓库天然就是一种外部记忆：文件保存当前实现，Git diff 保存本轮变化，测试报告保存失败证据，设计文档保存约束，任务状态文件保存未完成项。

这与“让模型记住 25 小时里所有思考”完全不同。后者会随着上下文增长变得昂贵而混乱；前者让模型在需要时重新观察权威状态。一个可靠 harness 应明确区分：

状态类型适合载体不应主要依赖
当前代码真相工作区文件、构建产物、数据库迁移状态模型对旧文件的记忆
本轮改变Git diff、补丁、变更清单自然语言“我改了什么”
任务契约目标、验收条件、设计文档、AGENTS.md散落在多轮聊天里的暗示
即时观察退出码、测试失败、日志、截图模型预期会发生什么
长程摘要检查点、状态文件、压缩摘要完整原始日志永久常驻上下文

3.6 验证层：“完成”必须是外部可判定的谓词

普通聊天常在模型给出答案时结束；工程 Agent 必须在结果满足完成定义（definition of done）时结束。对代码任务，完成证据可能包括测试、构建、lint、类型检查、静态分析、可视化检查和最终 diff。可以把一个简化的完成条件写成：

Done≔ ArtifactExists∧ AcceptancePasses∧ NoPendingApproval∧ EvidenceRecorded \mathrm{Done}:=\mathrm{ArtifactExists}\land\mathrm{AcceptancePasses}\land\mathrm{NoPendingApproval}\land\mathrm{EvidenceRecorded}

模型仍可判断“哪些测试最相关”“这个失败是否由本次修改引起”，但最终布尔证据由确定性程序产生。若某项无法运行，也应把“未验证及原因”作为状态，而不是默认为通过。

3.7 人机交互与并行层：可转向性也是架构能力

Codex 的 thread/turn 协议支持运行中追加约束、暂停、中断和恢复；界面又让人看到命令、工具活动和差异。这使用户可以在长任务尚未结束时纠偏，而不必等 Agent 走完错误路线。

并行工作则依赖隔离。官方文档建议用独立线程和 Git 工作树（worktree）让多个任务拥有分离的检出目录，避免两个 Agent 同时写同一批文件。子 Agent 适合把代码探索、测试或日志分析等高噪声工作移出主线程，只返回蒸馏后的结果；写密集任务若没有文件所有权或工作树隔离，反而会增加冲突。

四、贯穿案例：为 InnoSpark 增加“一键导出到 Obsidian”

假设任务是：在 InnoSpark 中增加一键导出，将选定知识库复制到用户的 Obsidian 库；不得移动或修改原项目数据；保留 Markdown、附件和内部链接；目标已存在时先预览冲突；失败后可重试，不得留下半成品。

4.1 只有强模型时会发生什么

把需求和若干文件直接贴给 GPT-5.6 Sol，它大概率能提出合理架构，甚至写出质量不错的导出函数。但它无法自行确认仓库真实目录、现有数据模型、所有链接编码方式、操作系统文件权限和测试结果。你得到的是一个高质量候选答案，不是已验证的仓库改变。

4.2 加一套 Codex 式 Harness 后，任务怎样流动

  1. 建立任务契约：系统把结果、约束和验收条件单独保存。关键不变量是“源库字节不变”“目标要么完整提交，要么回滚”“冲突必须先展示”。
  2. 发现项目规则：加载仓库根部 AGENTS.md，进入导出模块时再加载更具体的规则；若已有 Obsidian 导出 Skill，只在任务命中时载入完整流程。
  3. 构造相关上下文：模型先搜索知识库数据结构、附件解析、已有复制工具和测试入口，不把整个仓库一次性注入。
  4. 形成可执行计划：把工作拆成扫描、规划、冲突预览、临时目录复制、原子提交、回滚和测试。此处计划是可修改状态，不是一次性散文。
  5. 通过工具修改：使用补丁工具编辑明确文件；必要时执行生成器或格式化器。每个工具调用都有目标、参数、输出与退出状态。
  6. 在边界内运行：默认只写仓库和测试临时目录。若集成测试需要访问用户真实 Obsidian 库，系统必须请求单独授权，不能因为模型说“只是测试”就越界。
  7. 接收真实反馈：运行单元测试、类型检查和一个含中文文件名、重复附件、断链与权限失败的端到端用例。模型看到实际错误后再修复。
  8. 检查不变量：对源目录运行前后哈希比较；模拟中途失败，确认临时目录清理；验证内部链接在复制后仍指向正确目标。
  9. 审阅差异：最终结果包括改动文件、设计取舍、测试命令及结果、仍未覆盖风险。用户可在 diff 上批注，再让同一线程继续处理。

注意：上述九步里，真正需要高级模型创造性推理的部分主要是理解需求、定位架构、设计事务语义、诊断失败和权衡实现；文件读取、哈希比较、权限限制、执行测试和记录证据都应由 harness 完成。二者的界面越清楚，系统越可靠。

五、相较“传统 Agent”的优势：先定义比较对象

“传统 Agent”不是严格统一的类别。为了避免把旧系统稻草人化，本文把比较基线限定为一种常见的简化实现：一个系统提示词、一个模型、若干函数工具和一段“思考—行动—观察”循环，完整历史持续追加到同一上下文，模型自行宣布完成。很多成熟 Agent 框架也已经加入状态机、沙箱和评测；一旦加入，它们与 Codex 的差距自然缩小。

反馈工具返回一段文本退出码、diff、测试、结构化事件和增量进度模型能基于现实而非想象修复
完成判断模型说“完成了”外部验收门与证据清单降低虚假完成
并行多 Agent 共享目录或只靠消息协商独立线程、上下文隔离、工作树、结果汇总减少污染与写冲突
复用复制长提示词AGENTS.md、Skill、MCP、插件、Hook把经验放到合适层级
可观察性最终回答或少量日志typed item、工具轨迹、审批、差异、测试证据便于调试、评测和审计

六、这些设计为何有效：六种机制与三种代价

6.1 长程连贯来自“反复重新锚定现实”

长任务不是一次超长推理。每一轮工具观察都会把模型重新锚定到文件、退出码和测试结果；外部状态又允许它在压缩上下文后重新读取真相。因此连贯性来自许多局部闭环，而不是一条永不断裂的内部思维链。

6.2 可靠性来自异质校验

让另一个相似模型评价代码，能发现一部分问题，但两者可能共享盲点。编译器、类型系统、测试、哈希和权限检查与语言模型的错误模式不同。把模型判断与确定性检查组合，可靠性通常高于反复让模型“再仔细想想”。

6.3 安全边界反而释放自主性

如果 Agent 拥有宿主机全部权限，系统就只能频繁向用户确认；若工作区和网络有强边界，大量低风险操作可以自动执行。沙箱不是自主性的对立面，而是自主性的基础设施。

6.4 渐进披露把上下文当缓存管理

AGENTS.md 保留每次都需要的稳定规则，Skill 描述只承担路由，详细流程和参考资料按需加载，原始日志写回外部存储。这与缓存层次类似：高频且关键的信息靠近模型，低频且庞大的信息保留在可检索外部层。

6.5 可转向性降低错误路线的沉没成本

任务中途出现新信息时，人可以追加限制、暂停或中断，不必等 Agent 完成整轮才重开会话。更重要的是，转向发生在保留线程、文件和差异状态的环境里，不必从零解释。

6.6 复用单位从“提示词”升级为“工作流资产”

成熟经验可以按性质分别落到项目规则、Skill、脚本、工具契约、Hook 或测试，而不是继续把系统提示词写长。模型负责需要语境的部分，脚本负责可确定的部分，测试负责验收。这也是把个人技巧变成团队能力的过程。

6.7 代价与边界

  • 系统复杂度：线程、权限、工具、恢复、日志和评测都会引入工程成本。小任务可能不值得启动完整流程。
  • 延迟与费用：反复读文件、跑测试、调用子 Agent 会增加时间和 token。强模型加完整 harness 不是每一步都经济。
  • 错误仍会穿透：测试可能不完整，工具描述可能误导，沙箱配置可能过宽，模型也可能修改了错误但恰好通过测试。Harness 把风险变得可管理，并不把概率降为零。

七、你该怎样借鉴：先选路线，再造系统

“借鉴 Codex”有三种完全不同的含义。选择错误，会让你在不必要的地方重复造轮子。

路线适用情况优先使用你主要开发什么
A. 定制现成 Codex任务本质是代码仓库工作AGENTS.md、Skill、MCP、Hook、规则、工作树项目规范、领域流程、专用工具与验收
B. 把 Codex 嵌入产品需要从自己的 UI、CI 或后台驱动 coding agentCodex SDK；深度客户端集成时用 App Server业务界面、任务队列、权限映射、结果审阅
C. 自建通用 Harness任务跨越非代码领域，或必须完全控制调度与模型Responses/Agents SDK 加自建执行与策略层线程状态机、上下文编译、工具协议、沙箱、验证、评测
对你当前阶段的建议：InnoSpark 与 L2 Editor 仍以软件开发为主，不建议先复刻一套 Codex。先走 A：把项目规则、专项流程和确定性验收接到 Codex；若要让 InnoSpark 内部调度编程任务，再走 B。只有当你的产品要调度“市场调研—需求—设计—开发—发布”整条跨域流水线，而且现有 Codex 只是其中一个专家时，才值得走 C；这时可以让上层编排器通过 MCP 调用 Codex，而不是把 Codex 本身重写一遍。

7.1 自建时的最小数据模型

不要从“写一份厉害的 system prompt”开始。先定义可持久化对象：

Thread {
  id, goal, constraints, status, workspace, created_at
}

Turn {
  id, thread_id, user_input, started_at, completed_at, status
}

Item = UserMessage | AgentMessage | ToolCall | ToolResult
     | FileChange | ApprovalRequest | Checkpoint | Verification

ToolCall {
  id, tool_name, validated_input, risk_class, state
}

Verification {
  criterion_id, command_or_check, outcome, evidence_ref
}

这里最重要的不是字段名，而是把消息、动作、现实结果和验收证据分开。只有这样，你才能重放一轮、查询未完成工具、审计副作用，或在上下文压缩后恢复。

7.2 把 Agent 循环写成显式状态机

RECEIVED
  → CONTEXT_BUILT
  → MODEL_DECISION
  → TOOL_PROPOSED
  → POLICY_CHECKED
  → TOOL_RUNNING
  → OBSERVATION_RECORDED
  → VERIFYING
  → DONE | RETRY | BLOCKED | INTERRUPTED

每个箭头都应有可检查的进入条件。工具超时不能直接回到“让模型继续”；应先记录超时类型、进程状态和可否安全重试。需要用户选择时进入 BLOCKED，而不是让模型猜。发生中断时保存检查点，恢复后先重新观察外部状态。

7.3 做一个有优先级的上下文编译器

可采用下面的稳定优先级，而不是简单截取最近消息：

  1. P0：安全边界、当前目标、用户最新修改。
  2. P1：验收条件、未解决决策、当前步骤。
  3. P2：任务命中的项目规则和 Skill 指令。
  4. P3：相关文件片段、接口、不变量和近期 diff。
  5. P4：最新工具观察，尤其错误、退出码和失败测试。
  6. P5：旧轮次摘要、低优先级参考和可再次检索的材料。

压缩时优先丢掉可重新获得的原始日志，不丢目标、不变量、用户决定和仍未解决的失败。每条摘要最好附原始工件引用，以便模型怀疑摘要时回读。

7.4 只做少量、高质量的工具

第一版可以只有：搜索文件、读取文件、应用补丁、执行命令、查看 diff、请求用户输入六类。每个工具都写清：

  • 何时使用与何时不用；
  • 输入模式、最大范围、路径解析规则；
  • 输出的稳定字段，而不只是 stdout 大字符串；
  • 只读、写入、破坏性、外部网络等风险标注；
  • 超时、部分成功、权限不足和资源冲突的错误码；
  • 是否幂等（idempotent），以及重试会不会重复副作用。

工具数量不是能力指标。若两个工具描述高度重叠、返回巨量无结构文本，新增工具反而会降低选择准确率并污染上下文。

7.5 权限系统必须在模型外部

最小可用方案可以把动作分成四级：

级别例子默认策略
R0 只读读仓库、搜索符号、查看状态工作区内自动允许
R1 可恢复写入补丁修改、生成临时文件隔离工作区内允许并记录 diff
R2 外部或难恢复网络发布、推送、改远程数据需要明确授权或细粒度策略
R3 破坏性删除生产数据、覆盖不可恢复资源阻止或强制人工复核

模型只能提出动作及理由，策略引擎根据真实工具、参数、作用域和当前授权做决定。审批通过也应尽量只授予一次、一个目标或一类前缀，不升级整个会话为无限权限。

7.6 把验证器设计成一等组件

为每类任务建立“证据生成器”，而不是在提示词末尾写一句“请测试”。例如：

  • 代码修改：目标测试、全量测试、类型检查、lint、diff 范围。
  • 数据迁移：行数守恒、校验和、约束、回滚演练。
  • 网页界面：构建、浏览器交互脚本、截图或可访问性检查。
  • 文档：链接、结构、禁用模式、渲染或格式校验。

验证结果进入结构化 Verification item。模型可以解释失败并修改代码，但不能把失败改写成成功。达到重试上限后，应以“部分完成 + 证据 + 阻塞原因”结束。

7.7 最后才加多 Agent

多 Agent 首先解决吞吐和上下文隔离，不自动提升单步正确率。只有任务能按文件、读写权或成果边界独立切分时才并行。建议先用于只读探索、测试分析和审查，再尝试并行写入；每个写 Agent 使用独立工作树，主 Agent 只接收摘要和可审阅补丁。

7.8 适合你的四阶段落地顺序

  1. 第一阶段：把“完成”写实。为现有项目建立机器可运行的构建、测试、安装和最小闭环验收；在根 AGENTS.md 只写稳定命令、关键不变量和必须提供的证据。
  2. 第二阶段：把重复工作流做成 Skill。例如“从零拉取并验证 InnoSpark + 插件”“导出到 Obsidian 的兼容性检查”“发布前检查”。需要完全确定的步骤放脚本，不让模型每次重写。
  3. 第三阶段：补专用工具与 Hook。将内部状态查询、测试夹具、数据一致性检查做成窄工具；在停止或工具调用后运行验证 Hook。此时再收集 trace，查看失败集中在哪一层。
  4. 第四阶段：程序化编排。若要从自己的产品发起 coding thread，先用 Codex SDK；若 Codex 只是更大流水线中的开发专家，上层用 Agents SDK 编排，通过 Codex MCP 交付清楚规格与工作目录。

八、怎样真正分离模型与 Harness：做二维消融，不凭感觉

因为存在交互项，你不能只比较“ChatGPT 回答”和“Codex 成果”，然后把差异全部算给工具。更可靠的做法是固定一批真实任务，沿模型与 harness 两条轴做消融实验（ablation study）。

实验组模型Harness回答什么问题
AGPT-5.6 Sol只给静态任务材料，不允许工具模型能否理解并提出正确候选方案
BGPT-5.6 Sol裸 Shell / 文件工具，简单循环仅增加行动能力带来多少收益
CGPT-5.6 Sol完整上下文、权限、状态、验证与恢复生产级 harness 的增量贡献
D较低成本模型与 C 完全相同模型能力下降后 harness 能补偿多少
EGPT-5.6 SolC 去掉某一层，如无外部验证具体组件的边际价值

8.1 任务集不能只用算法题

应覆盖不同失败模式：陌生仓库定位、跨文件功能、模糊 bug、依赖安装、需要权限的外部动作、测试不完整、长任务中途改需求、故意注入工具失败。每题准备隐藏验收测试，避免模型仅迎合表面描述。

8.2 建议记录的指标

  • 端到端成功率：隐藏验收是否全过，而不是最终回答是否自信。
  • 首次有效修复率：第一次补丁通过多少目标检查。
  • 恢复率：工具失败或测试失败后，能否诊断并回到正确路线。
  • 虚假完成率：声称完成但存在失败检查、未运行验证或未满足约束的比例。
  • 越权与副作用：是否尝试访问不必要路径、网络或远程写操作。
  • 人类干预次数：哪些询问真正需要决策，哪些只是 harness 缺乏信息。
  • 成本与延迟：输入、输出、工具次数、测试时间、子 Agent 开销。
  • 上下文效率：送入模型的 token 中，有多少与当前决策实际相关。

8.3 怎样解释结果

若 A 已能给出正确设计但无法落地，B/C 提升主要来自行动与验证；若 B 经常找错文件而 C 稳定，说明上下文组装和项目规则重要；若 Sol 在 B/C 都显著优于较弱模型，说明判断核仍是瓶颈；若弱模型在 C 上接近 Sol，说明任务已被 harness 约束得足够清楚，可以降本。

最值得关注的不是“哪组总分最高”，而是失败归属：模型误解、上下文缺失、工具契约模糊、执行不稳定、权限阻塞、验证不足还是恢复策略错误。只有归因到层，你才能决定下一笔工程投入放在哪里。

九、借鉴 Codex 时最容易犯的八个错误

  1. 把 Harness 等同于系统提示词。提示词能表达规范，不能提供操作系统边界、进程状态、持久化和验收证据。
  2. 让模型直接调用内部万能 API。这让权限、失败语义、结构化输出和评测都失去边界。应围绕用户动作设计窄工具。
  3. 把所有资料一次性塞入长上下文。大窗口提高容量，不消除注意力竞争。先检索、按需加载、保留可回读引用。
  4. 用模型自评代替测试。模型审查适合发现语义风险，确定性验收负责证明可运行事实，两者不能互换。
  5. 只记录聊天，不记录世界状态。恢复时应重新读取文件、diff、进程和测试结果，而不是相信旧摘要仍对应现实。
  6. 先上多 Agent，再解决单 Agent 的完成闭环。多个不可靠循环只会更快地产生冲突和噪声。
  7. 把审批当礼貌用语。“我可以删除吗”若不绑定实际工具调用、精确目标和强制策略，就不是安全机制。
  8. 只评最终答案，不评轨迹。同样成功的结果可能一个来自安全可复现路径，一个来自偶然越权。应同时记录动作、失败、审批和验证。

十、压缩成一个可长期使用的心智模型

以后看到 Codex 完成一项复杂任务，可以按下面的问题逐层分析：

  1. 模型判断：哪一步需要理解、创造、取舍或诊断？
  2. 上下文供给：模型凭什么知道当前目标、代码和失败证据？
  3. 行动契约：它通过什么工具改变世界，参数和失败是否结构化？
  4. 权限边界：什么是技术上禁止的，什么必须人工批准？
  5. 外部状态：中断、压缩或换模型后，任务真相保存在哪里？
  6. 完成证据：谁证明结果有效，模型能否单方面宣布通过？
  7. 人机协作：用户怎样看到、纠偏、审阅和接管？

Codex 最值得借鉴的不是某条提示词，也不是“让 Agent 自己跑终端”，而是把开放式智能放入一个有边界的工程闭环：让模型负责无法预先穷举的判断，让程序负责可以确定执行和验证的部分，让外部状态承载时间，让权限系统承载信任。

这也回答了最初的拆分问题：GPT-5.6 Sol 决定系统推理上限，Harness 决定这些推理能否接触真实世界、持续纠错并留下证据；二者的适配决定最终体验。研究或开发 Agent 时，应同时评估两条轴，并保留交互项，而不是把 Codex 的整体表现直接当成模型基准。

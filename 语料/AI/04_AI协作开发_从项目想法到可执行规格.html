一、它与普通项目文档究竟有什么不同

1. 已有项目文档描述现实，构建规格规定未来

给一个成熟项目写 README、使用指南或架构说明，基本任务是描述已经存在的事实：

  • 软件现在有什么功能；
  • 安装和启动命令是什么；
  • 一次请求现在经过哪些模块；
  • 哪些接口和数据结构已经被其他部分依赖。

这种文档如果与代码冲突，应当以运行证据和代码为线索修正文档。因为代码所构成的系统已经存在，文档是在画它的地图。

让 AI 从零构建项目时，时间方向相反。系统还不存在，你写的是规范性文档：它不只说“我想要什么”，还规定未来实现必须满足什么、可以自由选择什么，以及怎样证明它满足了要求。此时，文档是代码的上游约束。

视角理解已有项目时让 AI 新建项目时
黑盒观察系统现在对外提供什么规定未来系统必须表现出什么行为
灰盒恢复项目当前的主要处理阶段规定推荐的系统边界、主要阶段和接口
白盒定位真实文件、函数和状态更新只提前固定不能交给 AI 自由选择的实现约束
验证用测试和运行轨迹确认理解是否正确用测试和验收场景确认实现是否符合规格

2. “让 AI 照着做”不等于“一次生成必然成功”

这里必须直接否定一个过强的期待：不存在一篇文档，可以让任意模型在任意规模项目中一次生成全部代码，并且天然保证没有遗漏、没有冲突、能够运行。

原因不神秘：

  1. 文档不可能预见所有现实冲突，例如依赖版本、运行环境和第三方接口变化；
  2. 自然语言仍可能有多种解释；
  3. 代码是否正确，需要在真实环境里安装、构建、运行和测试；
  4. 用户往往要看到原型，才能发现自己真正想要什么；
  5. 如果 AI 没有文件、终端或浏览器工具，再好的文档也不能让它亲自验证结果。

因此，“照着文档产出完整项目”的现实含义应当是：

AI 能够根据规格先提出阻塞问题，再生成设计与任务计划，逐步实现各部分，运行现有验证手段，修正失败，最后清楚报告已验证和未验证的内容。

文档的价值不是取消迭代，而是让每轮迭代都有稳定的判定依据，避免模型每次都重新猜你的目标。

3. 给这种文档一个准确名称

本文把它称为项目构建规格。你也会看到“项目规格”“实现规格”“spec”或“spec-driven development（规格驱动开发）”等名称。名称不是重点，重点是它同时包含三种性质：

  • 约束性：写清必须满足、禁止发生和允许自由选择的内容；
  • 可实施性：AI 能从中推出结构、任务和修改动作；
  • 可验证性：人和机器都能依据它判断结果是否合格。
不是项目构建规格：“做一个简洁、现代、稳定、功能完善的语料转 HTML 工具。”这句话表达了愿望，却没有决定系统边界，也无法判定“现代”和“完善”是否实现。

二、贯穿案例：StudyHTML Lite

为了避免后文变成术语清单，全文只使用同一个小项目。

项目想法

名称：StudyHTML Lite

一句话目标：把用户已经写好的 Markdown 学习语料转换成一个可离线打开的 HTML 文件。

核心原则：它只负责呈现，不调用 AI 改写语料内容。

用户最初可能只会这样告诉 AI：

帮我做一个把 Markdown 转成好看的 HTML 的小工具，要有预览和下载。

这已经足够开启讨论，却不够直接进入编码。AI 仍然必须猜：

  • 它是网页、桌面应用、命令行工具，还是现有项目的插件？
  • 文件是否上传服务器？
  • “好看”指固定模板，还是允许用户自定义？
  • Markdown 中的代码块、表格、公式和危险 HTML 怎样处理？
  • 输出是单个独立 HTML，还是 HTML 加资源文件夹？
  • 空文件、错误编码、超大文件怎样提示？
  • “完成”只指页面出现，还是还包括测试、文档与构建命令？

项目构建规格所做的事情，就是把这些会显著改变实现的分叉逐一关闭；对于不影响目标的小决定，则明确交给 AI。

阻塞问题：如果不同答案会导致项目边界、数据安全、核心技术路线或验收结果明显不同，那么它必须在编码前解决。例如“文件是否上传云端”就是阻塞问题；按钮圆角是 8px 还是 10px，通常不是。

三、先写目标、边界和决定权

1. 先回答“为什么”，但不要写成宏大口号

项目目标最有用的写法包含四个要素：

  1. 谁：哪类用户；
  2. 在什么情境：他正在完成什么任务；
  3. 遇到什么困难：当前成本或风险是什么；
  4. 希望产生什么变化：不是功能名，而是任务结果。

弱目标

开发一个强大的 Markdown 转 HTML 系统，提高学习效率。

可工作的目标

让已经完成学习语料写作的个人用户，不需要手写 HTML 和 CSS，也能在本地把一份 Markdown 转换为可离线保存、阅读和分享的单个 HTML 文件。

第二种写法能帮助 AI判断：重点是本地、离线、单文件和已有内容的呈现；它不是在线编辑平台，也不是 AI 写作助手。

2. 用“第一版不做什么”切断自动膨胀

AI 很容易根据相似产品补全“常见功能”。这并不是恶意，而是模型在填补空白。如果你只写“生成 HTML”，它可能顺手增加账号、云同步、模板市场、版本历史或在线协作。于是项目看似更完整，实际却偏离了第一版目标。

StudyHTML Lite 的第一版边界可以写成：

本版包含：选择本地 Markdown 文件、验证输入、生成预览、下载单个 HTML、显示可理解的错误。

本版明确不包含：账号系统、服务器上传、数据库、AI 改写、多人协作、模板市场、版本管理、PDF 导出。

“不做”不是对未来永久禁止，而是防止本轮交付失去结束位置。

3. 把决定分成固定、授权和待确认三类

一份对 AI 友好的规格，不是把所有细节都固定。它应当明确决定权：

类别含义StudyHTML Lite 示例
固定决定AI 必须遵守，不得自行替换文件只在本地处理；不得改写正文；输出必须是单个 HTML
授权决定AI 可以在约束内自行选择，但应记录选择内部函数名、模块文件数量、测试库、按钮的细小视觉参数
待确认决定当前证据不足，实施前必须暂停提问是否支持原始 HTML；数学公式采用何种离线渲染方案

这张表解决了一个常见矛盾：文档太粗，AI 大量猜测；文档太细，又把 AI 降成机械打字员，还可能提前固定错误方案。好的规格固定高风险决定，授权低风险细节，并把真正未知项暴露出来。

进入“写详细需求”前的门槛
  • 能够用一段话说清用户、情境、困难和目标结果；
  • 第一版包含与不包含的内容没有明显矛盾；
  • 所有会改变核心路线的问题，都已决定或明确标成待确认；
  • AI 被授权自行决定的范围已经写出。

达不到这四点，就不应急着列技术栈和文件目录。

四、把黑盒需求写成可观察的契约

1. 一条需求应当像“未来事实”

黑盒需求不解释内部怎样实现，只描述在某种条件下，外部能够观察到什么。最实用的句式是：

在……条件下，当用户……时，系统必须……；如果……失败，系统必须……。

例如：

模糊写法

支持 Markdown 导入，错误处理要完善，HTML 要美观且兼容性好。

可验收写法

用户选择 UTF-8 编码的 .md 文件后，系统必须显示文件名并允许生成预览；若文件为空，生成按钮不得产生下载文件，并显示“文件内容为空”的提示。

后者没有彻底定义所有设计，却已经能够被人操作、被测试检查。

2. 给需求编号，建立稳定引用

编号不是为了形式主义，而是为了让设计、任务和测试都能指出自己在服务哪一条要求。StudyHTML Lite 可以先写五条核心需求：

编号级别可观察要求
REQ-001必须用户能够选择一个本地 .md 文件；处理期间不得把文件内容发送到网络。
REQ-002必须生成的预览必须保留标题、段落、列表和代码块的内容与层次，不得增删正文语句。
REQ-003必须用户能够下载一个包含正文与样式的单个 .html 文件，并在断网状态下打开阅读。
REQ-004必须空文件或无法读取的文件不得产生伪成功结果；界面必须显示原因，并保留用户重新选择文件的入口。
REQ-005应该手机宽度下正文不产生页面级横向滚动；代码块自身允许横向滚动。

注意这些要求都指向用户或外部系统能观察的结果。至于内部用几个函数、是否使用某个 Markdown 解析库，暂时不写进黑盒需求。

3. 用场景把多条需求连成一个完整动作

单条需求容易局部正确、整体断裂。一个用户场景就是从起点到结果的完整动作。它可以用“前提—动作—结果”写出：

场景 A：正常生成

前提：用户打开工具，准备了一份包含标题、列表和代码块的 UTF-8 Markdown 文件。

动作：用户选择文件并点击“生成”。

结果：页面显示预览；用户点击“下载”得到单个 HTML；断网打开该 HTML，正文内容与原文件一致，标题和代码块可读。

场景 B：空文件失败

前提：用户选择一个内容为空的 Markdown 文件。

动作：系统完成读取。

结果：页面显示“文件内容为空”；不展示旧预览为新结果，不创建下载文件。

这种写法在行为驱动开发中常被整理为 Given—When—Then。你不需要背英文术语，只要记住：先给条件，再给动作，最后写外部可见结果。结果尽量不要写成“数据库插入一行”这类内部细节，因为用户真正关心的是界面、文件、消息或其他系统收到的输出。

4. 例子比形容词更能传达预期

如果格式重要，给一个最小输入和预期输出；如果视觉重要，给参考页面、截图或明确的设计规则；如果错误提示重要，写出消息内容或至少写出必须包含的信息。AI 从例子中识别边界，通常比从“友好”“现代”“专业”等形容词中猜测更稳定。

输入片段：
# 马尔可夫链

- 状态空间
- 转移概率

```python
P = [[0.8, 0.2], [0.3, 0.7]]
```

预期：
1. “马尔可夫链”成为一级标题；
2. 两项内容成为无序列表；
3. Python 代码原样保留在独立代码块中；
4. 不新增总结，不改写术语。
进入“设计内部路线”前的门槛
  • 每个核心用户动作至少有一个正常场景；
  • 每个高风险失败至少有一个失败场景；
  • “简洁、稳定、完善”一类词已经被例子或判定条件替代；
  • 每条必须需求都有稳定编号；
  • 不看实现代码，也能判断场景结果是否出现。
本节停一下：你能否判断这句话的问题？

原句：“系统应采用优秀的解析方案，高质量地处理各种 Markdown。”

答案：它把实现评价和行为要求混在一起。“优秀”“高质量”“各种”都没有边界。应先列出本版支持的结构，例如标题、列表、代码块和表格，再给输入输出样例；解析库的选择可以留到技术设计。

五、用灰盒蓝图规定主路线

1. 灰盒不是函数清单，而是责任与交接

黑盒契约说“用户应该得到什么”，却没有说明系统怎样组织。完全不写内部路线，AI 可能生成一个所有逻辑挤在单文件里的项目；过早写到函数级，又会把规格绑在尚未验证的实现上。

灰盒蓝图停在中间层，只回答：

  • 系统边界在哪里；
  • 一次请求经过哪些主要阶段；
  • 每个阶段接收什么、交出什么；
  • 错误从哪里产生，怎样传到用户；
  • 哪些信息需要保存，哪些只在本次操作中存在。

StudyHTML Lite 的主路线可以写成：

本地文件选择
→ 读取并验证文本
→ 把 Markdown 转为结构化文档
→ 套用固定阅读模板生成 HTML
→ 在页面中预览
→ 下载单个 HTML 文件

这里的“结构化文档”不是新功能，而是一种中间数据：例如把“一级标题”“列表项”“代码块”表示成有类型的节点。它让“理解 Markdown”与“决定 HTML 长什么样”分开，日后更换样式时不必重写文件读取逻辑。

2. 每个阶段都写输入、输出和失败

阶段输入成功输出失败结果
文件读取用户选择的本地文件文件名与文本不可读、编码异常、内容为空
输入验证文本确认可继续处理产生带错误码和用户消息的失败结果
Markdown 解析合法文本结构化文档节点指出不支持或无法解析的位置
HTML 生成结构化文档与模板完整 HTML 字符串不覆盖上一份成功结果，并报告失败
预览与下载HTML 字符串可读预览与文件下载显示浏览器限制或生成失败信息

这张表比“创建 parser、renderer、downloadService 三个类”更稳定。类名可以变化，阶段之间的责任和数据交接不应随意混乱。

3. 对交接数据写最小契约

如果一个阶段的输出会交给另一个阶段，仅写“返回结果”太模糊。可以给出一个小型数据契约：

成功：
{
  "ok": true,
  "html": "<!doctype html>...",
  "warnings": []
}

失败：
{
  "ok": false,
  "errorCode": "EMPTY_INPUT",
  "message": "文件内容为空"
}

它不要求 AI 必须照抄这个 JavaScript 对象，却固定了重要语义：成功和失败不能混在一起；失败有稳定机器码，也有给用户看的消息；成功时才允许进入预览和下载。

4. 灰盒蓝图应能追溯到黑盒需求

每个主要阶段都应当服务某些需求。例如：

阶段主要负责的需求为什么需要它
本地文件读取REQ-001保证输入来自用户本地，且不必经过服务器
解析与生成REQ-002、REQ-003保留内容层次并生成离线单文件
错误结果REQ-004让失败可见，避免伪成功
响应式样式REQ-005保证手机阅读不出现页面级横向溢出

如果某个模块找不到任何需求来源，可能是过度设计；如果某条需求没有任何阶段负责，说明设计遗漏。

进入“固定技术约束”前的门槛
  • 能够从用户动作一路追到最终输出；
  • 每个阶段的输入、输出和失败方式都清楚；
  • 每条核心需求至少有一个阶段负责；
  • 蓝图尚未陷入逐函数伪代码，允许 AI 在阶段内部组织实现。

六、白盒只写真正的硬约束

1. 不是越具体越好

白盒内容会接近具体技术：语言、框架、存储结构、接口格式、依赖限制、安全规则，甚至某个核心算法。它的成本也最高，因为技术环境一变，白盒细节最容易过时。

只有满足以下至少一项，才值得提前固定：

  • 与现有项目兼容所必需；
  • 涉及隐私、安全、数据丢失或不可逆迁移；
  • 其他模块将长期依赖这一接口或数据格式；
  • 运行环境已经限制可用语言、框架或依赖；
  • 某种质量目标必须通过特定结构才能稳定达到；
  • 用户已经明确做出不可由 AI 改写的设计决定。

StudyHTML Lite 值得固定的白盒约束包括：

  • 必须：文件内容只在浏览器内处理，运行时不得发出网络请求；
  • 必须：正文转换与页面样式分开；不得让样式层改写内容节点；
  • 必须：输出 HTML 自含必要 CSS，不依赖在线字体或 CDN；
  • 必须：失败不得清除上一份仍然有效的输入文件；
  • 应该：核心转换函数在相同输入与模板下产生相同输出，便于测试；
  • 可以：AI 自行选择经过维护、许可证兼容的 Markdown 解析库，并在设计说明中记录理由。

不值得在最初规格中固定的细节可能包括：

  • 内部函数必须叫 convertMarkdownToHtml；
  • 必须分成恰好七个源文件；
  • 每个类必须使用某一种设计模式；
  • 按钮圆角必须是某个像素值，而视觉上并无严格参考；
  • 在尚未比较方案前，强行指定一个自己也不了解的库。

2. 用“必须、应该、可以”表达强度

规格中最危险的词是“最好”“尽量”“适当”。它们把责任留给 AI 猜。可以借用工程规范中的三档表达：

词实际含义偏离时怎样处理
必须 / 禁止缺少它就不合格，或会造成明确风险不得自行偏离；发现冲突必须暂停报告
应该 / 不建议默认遵守，但存在经过说明的例外偏离前说明理由、影响和替代方案
可以属于实现自由，不影响合格判定AI 可自行决定并保持一致

重要的是强度与理由一致。不要把个人审美偏好写成“必须”，也不要把隐私底线写成“尽量”。

3. 写出贯穿所有路径的不变量

不变量：不管用户走正常路径还是失败路径，都必须始终成立的条件。它不是某一步做什么，而是系统任何时刻都不能破坏的底线。

本例的不变量包括：

  • 原始 Markdown 文件永不被修改；
  • 在没有成功生成新 HTML 前，不能把旧结果标记成新结果；
  • 任何正文内容都不得被发送到网络；
  • 下载按钮只指向最近一次成功生成的 HTML；
  • 失败消息必须与失败原因对应，不能统一显示“未知错误”。

不变量比函数流程更值得写进规格，因为它们横跨多个模块和异常分支，也是 AI 最容易在局部修改时意外破坏的东西。

进入“设计验收”前的门槛
  • 每条硬约束都有业务、兼容、安全或质量理由；
  • 强制项、推荐项和自由项没有混用；
  • 关键隐私、数据和失败底线已写成不变量；
  • 没有用大量函数名和文件名假装规格很精确。

七、验收证据决定“完整”是什么意思

1. 没有判卷标准，“完成”只是模型的自我评价

AI 可能生成代码、看到页面出现，就说“项目已完成”。人类开发者也会犯同样的错误。问题在于，“有代码”“能启动”“核心功能正确”“可以交付”是四个不同层次。

规格必须提供判卷标准：当实际结果出现时，怎样判断它与预期一致。工程里有时称它为 test oracle；你只需记住它就是“正确答案的判定办法”。

2. 让需求、场景、测试一一对应

需求验证方式合格证据
REQ-001 本地处理自动测试 + 浏览器网络面板人工检查读取样例文件成功；生成期间无对外请求
REQ-002 内容不改写固定输入样例比较标题、段落、列表、代码文本与输入逐项一致
REQ-003 离线单文件构建后人工验收只下载一个 HTML；断网后可打开且样式存在
REQ-004 失败可见空文件与不可读文件测试不产生下载物；消息包含具体原因；可重新选择
REQ-005 手机可读390px 视口检查页面无整体横向滚动；代码块可独立滚动

这张映射表还会暴露两种问题：

  • 有需求却没有验证办法：要求仍然太模糊，或测试能力尚未准备；
  • 有大量测试却找不到需求来源：测试可能在保护偶然实现细节，给后续修改制造阻力。

3. 完整项目至少包含哪些交付物

“完整”不等于文件数量多。对于一个可以独立运行的小工具，更可靠的定义是：另一个人拿到仓库后，不依赖作者脑内知识，也能建立环境、运行项目、验证核心行为并理解已知限制。

StudyHTML Lite 的交付清单可以是：

  • 实现核心功能的源代码；
  • 依赖声明与锁定文件；
  • 可重复的安装、测试、构建和启动命令；
  • 覆盖核心正常路径和失败路径的自动测试；
  • 用于人工验收的固定 Markdown 样例；
  • README：说明用途、启动、构建、使用和限制；
  • 项目构建规格与技术设计，且内容与最终实现一致；
  • 不得包含真实密钥、个人文件或调试残留；
  • 最终报告：列出已验证、未验证和已知问题。

4. 写出 Definition of Done：完成边界

Definition of Done 可以直译为“完成定义”：只有全部条件满足，本轮才允许称为完成。示例：

  1. 从干净环境按 README 安装依赖能够成功；
  2. npm test 全部通过；
  3. npm run build 成功且无未解释错误；
  4. 场景 A 与场景 B 的人工验收通过；
  5. 390px 移动端检查通过；
  6. 规格中的所有“必须”要求都有验证记录；
  7. 未验证项被明确标出，不得用“应该没问题”冒充验证；
  8. README、设计说明和实际命令一致。

这里的命令只是本例。在真实项目里，应写入仓库真正使用的命令；如果 AI 没有条件执行某项检查，它必须报告“未验证”，而不是把“生成了代码”写成“验证通过”。

规格可以交给 AI 实施的门槛
  • 每条“必须”需求都有至少一种可执行或可人工复现的检查；
  • 正常路径、失败路径和数据安全底线都有证据来源；
  • 已经定义源代码以外的必要交付物；
  • “完成”是一个条件集合，不是 AI 自己决定的一句话。

八、不要让一篇巨型文档承担所有职责

1. 小项目可以一篇写完，中型项目应按用途拆开

你最初问的是“写一篇什么样的说明文档”。对很小、一次性的小工具，一篇 PROJECT_SPEC.md 的确可以包含目标、需求、设计、任务和验收。但项目变大后，所有内容塞进一篇文档会产生三个问题：

  1. 产品目标、技术设计和当前任务的变化速度不同，改一处容易让另一处过期；
  2. 同一条要求在多个段落重复，久而久之互相冲突；
  3. AI 每次都加载全部内容，会让真正相关的约束被淹没。

更稳妥的文件分工是：

文件或载体主要回答不应拿它代替什么
PROJECT_SPEC.md为什么做、做什么、不做什么、怎样验收不负责列出每个函数和当前任务进度
DESIGN.md主要组件、流程、数据契约、硬约束与技术决定不替代用户需求，也不写成全仓库代码解释
TASKS.md这一次按什么顺序实施，哪些已完成、被什么阻塞不把暂时任务状态写回长期架构原则
AGENTS.mdAI 在这个仓库中怎样安装、测试、修改和汇报不替代某个功能的产品规格
tests/ 与样例哪些行为能够被机器重复验证不单独承担“为什么做”的解释

这些名称不是强制标准。重要的是职责分开：规格决定正确方向，设计决定主要结构，任务决定当前顺序，仓库指令决定 AI 的工作规则，测试提供可执行证据。

2. AGENTS.md 为什么不能代替项目规格

AGENTS.md 一类文件适合放长期、跨任务都成立的操作说明，例如：

  • 怎样安装依赖；
  • 运行哪些测试与格式化命令；
  • 哪些目录可以修改，哪些生成物不得手改；
  • 代码风格和提交前检查；
  • 遇到冲突、失败或不确定时如何汇报。

但“这个版本要增加离线 HTML 导出”是具体项目或功能要求，应放进规格。否则几个月后功能已完成，AI 仍会把一次性目标当成所有任务都必须重复执行的长期规则。

3. 只保留一个事实来源

同一条决定尽量只在一个地方完整定义，其他文件通过编号引用。例如：

PROJECT_SPEC.md:
REQ-003：输出必须是可离线打开的单个 HTML 文件。

DESIGN.md:
导出模块负责实现 REQ-003；样式写入 HTML 的 <style>，不引用 CDN。

TASKS.md:
- [ ] T-07 实现 REQ-003 的单文件导出
- [ ] T-08 为 REQ-003 增加断网验收样例

tests/acceptance/export.spec.ts:
// Covers: REQ-003

这样需求改变时，先改规格，再检查设计、任务和测试是否需要同步；无需在五个地方寻找五段略有不同的自然语言。

九、AI 应当怎样按阶段执行

1. 文档写完后，不要直接说“全部做完”

即使规格已经充分，也应要求 AI 经过多个检查点。原因不是把小项目官僚化，而是让错误在代价较低的时候暴露：需求误解应在写代码前发现，架构冲突应在铺开文件前发现，运行错误应在交付前发现。

阶段AI 要做什么产出进入下一阶段的标准
0. 澄清找冲突、模糊词、隐含假设和缺失边界阻塞问题与假设清单没有未处理的阻塞问题
1. 规格确认把讨论整理为目标、需求、场景和验收PROJECT_SPEC.md每条必须需求可判定，用户确认方向
2. 技术设计检查现有环境，设计主要阶段、接口和风险DESIGN.md需求都有责任归属，重大选择有理由
3. 任务拆分按依赖顺序拆成可独立验证的小任务TASKS.md每项任务指向需求与验证，不只是文件名
4. 第一条纵向切片先做一条从输入到输出的最小完整路径能运行的骨架核心场景端到端跑通，而非只有空目录
5. 扩展与异常补其余需求、失败路径、边界和文档候选完整项目自动测试通过，关键人工检查完成
6. 最终审计逐项对照规格、清理临时内容、报告缺口交付报告完成定义全部满足，或清楚列出未完成项
纵向切片：先完成一条很薄但从用户输入贯穿到真实输出的路线。例如先支持“一个简单 Markdown 文件 → 页面预览 → 单文件下载”，而不是先把所有界面画完、所有解析类型建完，却没有任何一条路线能运行。

2. 让 AI 在开始前先反驳规格

你不希望 AI 只顺着你的方案优化，可以在执行协议中明确写：

在修改代码前：
1. 检查规格内部是否矛盾；
2. 列出会显著改变实现的缺失决定；
3. 区分已确认事实、你的推断和仍待确认的假设；
4. 若发现更简单方案，说明它能删除哪些复杂度及其代价；
5. 对阻塞问题暂停实施；对非阻塞细节按授权范围自行决定。

这里的关键不是要求 AI “挑刺”三个字，而是给出挑刺的对象和停止规则。否则它可能为了显得批判而制造无关异议，或者发现真正冲突后仍继续猜测。

3. 跨多轮对话时，把进度留在仓库里

不要依赖“模型应该记得上次做到哪里”。每轮结束至少更新：

  • 已完成任务及对应需求编号；
  • 实际运行过的命令与结果；
  • 新增决定及其理由；
  • 当前阻塞和下一步；
  • 规格是否因用户反馈发生变化。

下一轮 AI 先读规格、设计、任务状态和仓库指令，再检查当前代码。这比把旧聊天全文重新塞进上下文更可靠，因为仓库中的文件是可检查、可版本化的当前事实。

4. 规格不是永远冻结的，但修改必须显式

做出原型后，你可能发现需求本身不合理。此时不是强迫代码服从旧文档，也不是让 AI 悄悄偏离，而是：

发现现实冲突
→ 说明原规格哪里失效
→ 用户确认新决定
→ 更新规格与变更记录
→ 同步设计、任务和测试
→ 再修改实现

规格的权威性来自“当前实现应当能追溯到当前规格”，而不是“初稿永远不许改变”。

怎样把模板用得不官僚

对于两三天能完成的小工具，可以把第 7—13 节压缩成几张表；对于已经嵌入主项目的插件，则应把长期仓库规则放进 AGENTS.md，把功能规格与技术设计拆开。判断是否需要拆文档，只问两个问题：

  1. 这部分内容的变化速度是否与其他部分明显不同？
  2. AI 执行某个具体任务时，是否需要加载这部分全部内容？

如果两个答案都是“否”，继续放在一篇文档里就够了。不要为了模仿大型团队而制造空文件。

十一、常见失败写法与最终检查表

1. 只有功能列表，没有完整场景

“上传、预览、导出、删除”四个词没有说明它们怎样连接，也没有说明失败后保留什么。改为至少写一条从起点到结果的正常路径，再为高风险位置写失败路径。

2. 把技术栈当成需求

“React + FastAPI + PostgreSQL”只是实现选择，不能说明用户为什么需要项目、系统怎样才算正确。先写行为和边界，再判断技术选择是否真的被环境或规模要求固定。

3. 用形容词代替标准

“高性能、健壮、优雅、现代、用户友好”都需要继续追问。性能应说明参考环境、输入规模和测量方式；友好应给出关键交互或错误消息；视觉应给参考样例与允许变化范围。

4. 只写成功路径

文件为空、网络中断、权限不足、外部接口超时、数据库迁移失败时会发生什么，往往比正常路径更决定项目是否可靠。至少覆盖会造成数据丢失、隐私泄露和伪成功的失败。

5. 提前规定全部白盒细节

逐函数伪代码会让 AI 忠实实现一个未经验证的方案。规格应固定外部行为、主要边界和高风险约束，把可逆的低层选择留给设计阶段。

6. 所有资料全文同时塞给模型

上下文越长不等于执行越稳定。长期规则、当前规格、技术设计和任务状态应当分工；执行某项任务时加载相关部分，并用需求编号保持跨文件联系。

7. 规格改了，测试和文档没有改

结果会出现三个“真相”：用户口头想法、旧规格、当前代码。每次需求变化都应显式更新规格，再检查设计、任务和测试的影响。

8. 把“AI 说完成”当成完成

最终报告必须区分：

  • 已实现且已验证：有运行命令或人工复现记录；
  • 已实现但未验证：代码存在，但环境不允许检查；
  • 未实现：尚未满足规格；
  • 偏离规格：说明原因、影响和是否获得用户确认。

一份好规格的八个特点

特点检查问题
有边界第一版明确不做什么吗？
可观察不看内部实现，能判断用户是否得到结果吗？
分层目标、黑盒行为、灰盒路线和白盒约束是否没有混成一团？
决定权明确AI 知道哪些必须遵守、哪些可以选择、哪些需要提问吗？
有例子关键输入、输出、失败和视觉预期是否有具体样例？
可追溯设计、任务和测试能指回需求编号吗？
可验证每个“必须”是否都有检查办法和通过证据？
可演化修改规格时，是否能看出受影响的设计、任务与测试？
最短审稿法：逐段问三句话——“这段做出了什么决定？”“AI 能据此采取什么动作？”“人怎样验证动作正确？”如果三问都答不出，这段大概率只是背景或修辞，应删减、移动或改写。

十二、自检与结论

自检 1：为什么不能只给 AI 一份传统 README？

README 通常面向已经存在的项目，主要说明用途、安装和使用。它很少完整规定第一版边界、待确认问题、内部主路线、硬约束、任务顺序和完成证据。AI 可以从 README 猜出项目轮廓，却无法据此可靠判断所有实现选择与验收结果。

自检 2：黑盒规格写得越详细，是否越好？

不是。应详细到能够判定行为是否正确，但不应混入无关的内部实现。例如“断网仍能打开单个 HTML”是可验收要求；“必须使用某函数拼接 style 标签”是实现细节，除非存在特殊兼容理由。

自检 3：什么时候必须写白盒约束？

当选择与兼容、安全、隐私、不可逆数据、外部接口、固定运行环境或明确质量底线有关时。可逆且低风险的函数组织、命名和局部算法，通常留给设计与实现阶段。

自检 4：为什么测试不能等代码完成后再随便补？

因为验收标准决定“什么叫正确”。如果先生成大量代码，再临时发明测试，测试容易顺着当前实现写，只证明“代码和自己一致”，而不是证明它满足用户需求。至少核心验收场景应在实施前确定。

自检 5：规格发现错误后，是坚持规格还是直接改代码？

都不是。先显式说明规格为什么失效，确认新决定并更新规格，再同步设计、任务和测试，最后修改代码。这样当前文档与当前实现仍然对应。

最终压缩

已有项目的文档主要是在描述现实；让 AI 新建项目的文档是在规定未来。因此，你真正要写的是：

目标与非目标
→ 可观察的黑盒需求与失败场景
→ 主要阶段、数据交接与系统边界
→ 少量不可违反的白盒约束
→ 需求对应的测试、样例与完成定义
→ 带检查点的实施流程与最终报告

它最重要的特点不是“足够详细”，而是关键决定不含糊、非关键细节不乱管、每项要求都能落到行动、每项行动都有办法验收。

对你的实际项目，更适合的做法也不是把所有内容继续堆进一篇越来越长的需求报告。可以把“产品与功能规格”“主系统中的技术设计”“AI 的长期工作规则”“当前任务清单”“可执行验收”分开维护，再用需求编号连接。这样 AI 每次拿到的是当前任务真正需要的上下文，同时仍能追溯到你最初想解决的问题。

一句话记忆：给 AI 写项目文档，不是在教它逐字敲代码，而是在给它一张带边界的施工图、一套明确的决定权和一份不能自评的验收卷。

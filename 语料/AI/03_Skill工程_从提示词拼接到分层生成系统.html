先修：只假设你知道 API 调用会向模型发送消息。文中的 systemPrompt、注册表、结构化输出等术语都会在第一次出现时解释。

先给结论：你设想的“从整体到局部逐层指导”方向是对的，但“多层 Skill”这个名称容易把实现带偏。如果三层最后仍被完整拼进同一个长提示词，模型并没有逐层工作，只是一次读了三份文档。真正的分层至少要同时具备两件事：不同阶段只装载当前需要的信息；结构越脆弱、越需要一致性的部分，越少依赖自然语言临场生成，越多交给结构化数据、固定模板和校验代码。

因此，本文会提出一个比“三份从大到小的 Skill”更准确的设计：

纵向是生成流水线：理解语料 → 规划整稿 → 选择页面模式 → 渲染 HTML → 校验；横向是可选知识模块：受众、学科、语言、视觉增强。Skill 负责流程和选择，确定性代码负责最终装配与验收。

全文使用一个贯穿例子：把一篇已经定稿的“初中数学：三角形内角和”语料转换成适合学生自学的 16:9 HTML 文稿。源语料内容不能被 Skill 改写；系统需要决定怎样分页、怎样措辞、哪些页面使用图示，以及怎样保证每页没有溢出。

正式阅读前：先记住六个核心对象

① 宿主编排器

真正读取文件、选择模块、组织消息并调用模型的代码。Skill 本身不会主动跳进模型。

→
② Skill 入口

一份短而稳定的工作流程：告诉模型先做什么、何时读取哪类细节、怎样验收。

→
③ 按需参考模块

语言、学科、整稿结构和页面模式等细节；只在当前任务或阶段需要时装载。

前三者共同形成“模型此刻看到的上下文”，但不直接等于最终 HTML。
④ 结构化整稿计划

页面列表、每页意图、源文对应关系、布局 ID 和容量预算，是模型与代码之间的合同。

→
⑤ 确定性渲染器

按布局 ID 和内容槽位生成固定 HTML/CSS/JS；相同输入应得到相同结构。

→
⑥ 校验与修复

检查内容覆盖、结构一致、外部资源、页面溢出和交互；失败就定位到具体页面。

这张图也给出了本文对你三个问题的总回答。第一问发生在①—③：谁把 Skill 以什么形式送给模型。第二问发生在②—⑥：多层知识如何与生成阶段连接。第三问则要比较当前 Agent Skills 的“入口 + 按需资源”模式，以及文档生成 Skill 中“模型判断 + 脚本执行 + 视觉校验”的组合。

一、先拆掉一个误解：Skill 不是模型内部的一块新器官

1. Skill 在被加载前，只是文件系统中的普通文本

模型不会因为某个目录里出现了 SKILL.md 就自动获得能力。中间必须有一个程序完成以下动作：

  1. 找到可用的 Skill；
  2. 读取名称、用途和正文；
  3. 判断本次任务需要哪些内容；
  4. 把这些内容放进模型能看到的消息，或者提供一个让模型读取它们的工具；
  5. 维持冲突优先级、上下文长度和版本记录。

本文把这个程序称为宿主编排器。在你的项目里，它不是抽象概念，而主要对应 SkillRegistry、composeInstructions()、buildGenerationPrompts() 和 GenerationService.generate() 这一条代码链。

消息：调用聊天模型时发送的一组带角色文本。最常见的角色是 system 与 user。system 通常放长期行为、规则和输出协议；user 放当前任务与材料。角色会影响模型如何理解文本，但不会像编程语言权限那样提供绝对强制力。

2. 你当前项目中，Skill 的真实流动路径

根据提交 4482dfe 中的代码，用户在设置界面多选 Skill 后，界面只保存一组 skillIds。真正生成时发生的是：

设置中的 skillIds→注册表按 ID 读文件→SHA-256 校验→按类别拼接全文→systemPrompt→模型

逐步看：

  1. VisualizerSettingsForm 把用户选择写入 skillIds: string[]。
  2. SkillRegistry.load() 从当前工作区的 .inno-visualizer/skills/.../SKILL.md 读取对应文件。
  3. 它重新计算文件哈希值；若文件被注册表之外的动作改过，就拒绝继续。这能避免“界面显示的是旧 Skill，实际读取的是另一份内容”。
  4. composeInstructions() 按 mode、subject、enhancement 分类；一次最多一个 mode、一个 subject，可以有多个 enhancement。
  5. 组合结果与固定输出协议一起形成 systemPrompt。
  6. 已完成的 Assistant 原回答、父版本 manifest、Deck 结构、父版本 HTML 和本次生成语义被放入 userPrompt。
  7. OpenAI 兼容接口最终收到两条消息：一条 system，一条 user；Anthropic Messages 接口则把前者放在独立的 system 字段，后者作为 user message。

用简化后的形状表示，就是：

systemPrompt =
  核心不可变规则
  + 措辞设置
  + 视觉扩展设置
  + 使用模式设置
  + mode Skill 全文
  + subject Skill 全文
  + enhancement Skill 全文
  + 手工修改说明（若有）
  + 本次调整要求（若有）
  + 消息级额外要求（若有）
  + title/deck/html 输出协议

userPrompt =
  源 Assistant 回答
  + 父版本资料（若有）
  + “首次生成”或“重新规划”的本次语义

这回答了你的第一问：在当前 Inno Visualizer 中，Skill 没有被嵌入原聊天，也不是作为独立工具由模型临时调用；被选中的 Markdown 全文由扩展代码直接拼进一次隔离模型调用的 systemPrompt。调用结果也不写进主聊天 JSONL，这是项目用隔离 Completion 保证的。

3. 当前设计已经做对了什么

在讨论改进前，先明确已有基础，否则容易推翻本来有价值的部分。

  • 核心安全规则不交给用户 Skill 覆盖。自包含 HTML、1600×900、节点协议、禁止外链等规则在代码内固定。
  • Skill 有版本证据。每次生成的 manifest 记录 Skill 的 ID、版本和 hash，可以追查某个 HTML 当时用了哪份说明。
  • 当前材料与长期规则分开。源回答进入 userPrompt，规则进入 systemPrompt，职责大体清楚。
  • 允许正交组合。模式、学科和增强不是一个巨型枚举，理论上可以组合。
  • 生成后还有机器校验。模型不能仅凭一句“我已经遵守”就进入版本仓库。

这些设计使它已经不是“在用户消息前面加一段提示词”的玩具实现，而是一个有来源、有版本、有边界的提示编排器。

4. 当前 Skill 为什么还不能充分发挥

问题也很具体。

问题 A：你导入的是单个 Markdown，激活时整份全文进入上下文

注册表允许最大约 512 KiB 的 Markdown，但模型真正关心的是 token——可近似理解为模型处理文本时的计量单位。几十万字节虽然能存，却不代表适合一次送入模型。Skill 越长，源语料和生成 HTML 能使用的注意力与上下文就越少。

更关键的是，当前 skill.content 包含整份文件，YAML frontmatter 也会一起被拼进去；解析器只利用 id/name/version/category 做注册，却没有把头部从正文中剥离。它不会造成严重错误，但会增加噪声。

问题 B：没有“发现—激活—按需资源”三步

当前 UI 由用户直接多选 Skill。这在 V1 中很可靠，但模型看不到一个轻量目录，也不能在读到“三角形内角和”后主动说“我还需要 K12 数学和几何图示模块”。所有选择必须在调用前完成。

问题 C：一次模型调用没有工具回路

ModelRequest 只有 systemPrompt、userPrompt 和最大输出 token，没有 tools。因此，即使 SKILL.md 写着“需要时读取 references/page-layouts.md”，模型也没有文件读取工具可用。它只能看到宿主事先拼进去的内容。

问题 D：物理顺序不等于可靠优先级

技术文档声明了“核心不可变规则 > 用户手改 > 本次调整 > 消息设置 > 各类 Skill”的优先级；而组合函数的物理顺序是核心、设置、Skill、手改、调整、额外要求。自然语言模型能理解标题中的“不可变”“优先”，但代码没有先检查两段规则是否冲突，也没有把低优先级冲突自动删除。

例如 enhancement Skill 若说“可从网络加载图片”，核心规则说“禁止网络资源”，模型有机会遵守核心规则，但更稳妥的系统应在调用前就报告冲突，在调用后由验证器拒绝外链，而不是单靠文字位置。

问题 E：模型同时生成 Deck 结构与完整 HTML，存在双重表达

当前输出要求模型给出 deck.slides 和完整 html，然后验证两者数量、顺序和 ID 一致。这里同一份页面信息被写了两次：一次是结构 JSON，一次是 HTML DOM。模型必须自行保持同步，任何一次疏忽都会失败。

第一问的直接建议：短期保留“用户显式选择 + systemPrompt 注入”，因为它与现有一次性 Completion 架构相容；但应缩短激活正文、剥离 frontmatter、显示最终组合摘要、做冲突检查。中期把生成拆成计划与渲染两个阶段，才值得引入真正的按需模块。
局部自检 1：把 references 文件放进 Skill 目录后，当前模型会自动读取吗？
答案：不会。当前模型调用没有文件工具，注册表也只导入一个 Markdown 文件。除非宿主代码读取 references 并把内容注入消息，或者把模型调用改造成可调用读取工具的循环，否则文件只是在磁盘上存在。

二、怎样让 Skill 在当前架构中立刻发挥得更好

在大改流水线之前，有几项低风险改进能直接提升效果。

1. 把 Skill 写成“决策程序”，不要写成领域百科

一个有效的激活正文应该回答：

  • 本 Skill 适用于什么输入；
  • 首先观察哪些特征；
  • 按什么顺序作决定；
  • 哪些规则绝不能违反；
  • 哪些地方允许模型自由设计；
  • 输出怎样检查。

例如 K12 自学文稿 Skill 不必解释“什么是 HTML”或列出全部 CSS 属性。它更需要说明：先识别学生阶段和核心结论；每页必须独立理解；新概念第一次出现时就地解释；证明页不能只放结论；最后执行页数、字号、公式和溢出检查。

2. 为每份 Skill 加上“使用”和“不使用”的边界

你当前 frontmatter 没有 description，只能由 UI 名称帮助用户选择。可以扩展为兼容 Agent Skills 的字段：

---
name: k12-self-study-deck
description: 将已定稿的中小学数理语料规划为可独立阅读的分页文稿；在受众为学生自主学习、预习或复习时使用。不要用于教师现场讲稿或修改源语料事实。
metadata:
  id: k12-self-study-deck
  version: "2.0.0"
  category: mode
---

description 的作用不是展示一句广告词，而是成为未来自动选择或模型选择的依据。它必须同时写“做什么”和“何时用”，最好再写一个最容易误触发的反例。

3. 组合前先规范化，而不是直接 join()

可以把每份激活内容解析成较小的内部结构：

SkillInstruction
├── purpose          目的
├── requiredRules    必须遵守
├── preferences      默认偏好
├── workflow         工作步骤
├── conditionalRules 条件规则
└── validation       验收项

宿主先做三件事：去除 frontmatter；把相同类别的规则合并；发现互斥内容就报错或按已声明优先级处理。最终再输出带清楚边界的区块，例如 <skill_content name="...">...</skill_content>。结构化标签不是魔法，但比多个相似的 ## Skill 标题更容易在日志、上下文压缩和调试中定位。

4. 给用户看“本次到底送了什么”

现在设置页能看见 Skill 名称，却看不见本次生成最终使用了哪些规则、总长度大约多少、是否有冲突。建议在生成前或调试页提供一份不泄露 API Key 的 Prompt 摘要：

显示项 价值
激活 Skill 与版本/hash 能复现结果
每个区块估算 token 防止 Skill 吞掉上下文
规则优先级 用户能发现覆盖关系
条件模块选择原因 知道系统为何加载它
被忽略或冲突的规则 防止静默失败

不建议默认向普通用户展示完整 systemPrompt；但开发模式应能导出它，否则 Skill 失败时只能凭成品猜原因。

5. 给 Skill 做对照实验，而不是只读文本审查

选十篇固定语料，保存三组结果：不用 Skill、使用旧 Skill、使用新 Skill。评分不只看“漂亮不漂亮”，而要检查：

  • 源内容覆盖率；
  • 页面结构是否服务于学习；
  • 每页文字与图形是否溢出；
  • 相同输入多次生成的稳定性；
  • 规则冲突或无关 Skill 是否导致退化；
  • 平均输入 token、输出 token 和失败重试次数。

Skill 的价值是相对基线的增益。如果模型不用 Skill 已经能完成某条常识规则，那条规则继续占据上下文未必有意义。

三、第二问：你的“多层 Skill”应该怎样重新设计

你的原想法是：大体方向 → 语言要求与整体模板 → 单页模板。这个划分直觉上由抽象到具体，但它混合了三种性质不同的东西：决策原则、任务知识和可执行模板。它们不应该都以同一种 Markdown 提示存在。

1. 推荐的四层，不是三层

第 0 层：产品合同

安全、内容忠实、输出 schema、1600×900、禁止外链、节点 ID 等不可变规则。

位置：核心代码与验证器，始终生效。

第 1 层：工作流入口

分析语料、规划整稿、选择模块、渲染、验证的顺序，以及何时停止或返工。

位置：短小的根 SKILL.md。

第 2 层：按需知识

语言适配、学科特征、整稿叙事、页面模式选择规则和特殊例外。

位置：references；按任务与阶段装载。

第 3 层：确定性执行

HTML shell、主题 token、页面渲染函数、schema、静态检查和浏览器溢出检测。

位置：assets、scripts 与核心包代码。

这四层与“从大到小”并不冲突，但多了一条关键分界：文字说明到哪里结束，代码合同从哪里开始。

2. 为什么单页模板不应主要写成更细的提示词

假设你给模型一段“概念页模板”：标题在左上、定义在左、示意图在右、底部有一句总结。若仍要求模型每次从零写 HTML，它可能：

  • 忘记某个 class；
  • 在文字过长时压小字号；
  • 给两个页面生成重复 ID；
  • 使用相近但不相同的间距；
  • Deck JSON 选了某模式，HTML 却实现成另一种。

这类错误并不需要“更聪明的模型”解决。模板本来就是确定性结构，应该写成渲染函数：

layoutId: concept-diagram
slots:
  title        最多 18 个汉字
  definition   最多 180 个汉字
  diagram      一个结构化 SVG 描述
  takeaway     最多 36 个汉字
fallback:
  definition 超限 → 拆成 concept-definition + concept-example 两页

模型负责选择 concept-diagram，并填写槽位；渲染器负责生成正确 DOM、CSS 与交互。这样“单页模板”仍是局部层，但它从一篇提示词变成了一个有容量、有输入字段、有退化策略的接口。

3. 垂直流水线：每一步只解决一种问题

对“三角形内角和”语料，建议的生成过程是：

阶段 A｜内容分析：标出源文的核心结论、定义、证明步骤、例子和总结，并记录每项对应的源文片段。

阶段 B｜整稿规划：决定先用直观实验提出问题，再给证明，最后总结；输出页面序列，不写 HTML。

阶段 C｜页面模式选择：实验页选 geometry-experiment，证明页选 step-proof，总结页选 summary-map。

阶段 D｜确定性渲染：代码把页面计划和槽位渲染为统一的自包含 HTML。

阶段 E｜校验与修复：机器检查 schema、引用、ID、外链和容量；浏览器检查像素溢出，失败时只返修对应页面计划。

阶段之间传递的不是大段自然语言，而是一个结构化计划。例如：

{
  "audience": "初中自主学习",
  "narrative": "实验观察 → 形式证明 → 应用与总结",
  "slides": [
    {
      "id": "slide-003",
      "purpose": "解释平行线证明中的角对应关系",
      "sourceRefs": ["paragraph-4", "paragraph-5"],
      "layoutId": "step-proof",
      "density": "medium",
      "blocks": [
        {"type": "diagram", "contentRef": "diagram-angles"},
        {"type": "steps", "items": ["作平行线", "使用内错角", "合成平角"]}
      ]
    }
  ]
}

sourceRefs 很重要：它让系统检查每一页内容来自哪里，也让“完整覆盖源语料”从一句道德要求变成可以测量的映射。

4. 横向模块：不要把所有变体塞进根 Skill

同一条流水线可以装载不同模块：

维度 示例模块 它改变什么 它不应改变什么
受众/语言 audience-k12.md 句长、术语解释、提示方式 数学事实与证明结论
使用场景 delivery-self-study.md 每页自解释、回顾与练习 页面技术协议
学科 subject-math.md 公式、证明、图形的处理 通用导航和安全

5. 推荐的 Skill 包目录

为了兼容 Agent Skills 的主流格式，可以使用一个入口和一层资源引用，避免引用文件再指向更深层文档：

html-learning-deck/
├── SKILL.md
├── references/
│   ├── audience-k12.md
│   ├── delivery-self-study.md
│   ├── subject-math.md
│   ├── deck-architecture.md
│   ├── page-pattern-index.md
│   ├── visual-geometry.md
│   └── failure-repair.md
├── assets/
│   ├── shell.html
│   ├── theme-tokens.json
│   └── layouts.json
└── scripts/
    ├── render-deck.mjs
    ├── validate-structure.mjs
    └── inspect-overflow.mjs

根 SKILL.md 不复制这些文件，而只写核心流程和加载条件：

1. 不修改源语料；先生成带 sourceRefs 的 ContentPlan。
2. 受众是中小学生时装载 references/audience-k12.md。
3. 学科是数学时装载 references/subject-math.md；几何图示出现时再装载 visual-geometry.md。
4. 先依据 page-pattern-index 选择 layoutId，不直接发明页面 DOM。
5. 调用 renderer 生成 HTML，再运行结构与溢出校验；失败只修复被报告的页面。

注意：这只是“Skill 包应该长什么样”。你的当前插件还不支持导入目录、枚举资源或调用脚本，需要宿主能力配套。

局部自检 2：把“十种单页模板的全部 CSS/HTML”写进 SKILL.md，算多层设计吗？
答案：不算。它只是把局部细节集中塞进同一次上下文。真正的分层要求当前阶段只加载需要的模板信息；更稳妥的做法是让模型选择 layoutId，由渲染器实现模板。

四、与你当前代码最匹配的落地路线

官方 Agent Skills 常假设 Agent 有文件读取或专用激活工具，但你的 Inno Visualizer 是一次隔离 Completion。直接照搬“模型需要时自己读文件”会失效。你有三条实现路线。

路线 A：调用前由宿主静态组合

宿主根据 UI 设置和简单元数据决定要加载哪些模块，然后一次性调用模型。

优点是改动小、行为可预测；缺点是仍然不能根据语料内部情况动态补充模块。适合 V1.1：先支持 Skill 目录包、资源 hash、frontmatter 剥离和更细的组合槽位。

路线 B：两阶段调用，由第一次计划决定第二次上下文

第一次模型调用只做内容分析与模块选择，输出固定 JSON：

{
  "sourceType": "k12-math-proof",
  "requiredModules": ["subject-math", "visual-geometry", "deck-concept-proof"],
  "contentPlan": {"...": "..."}
}

宿主校验 requiredModules 必须来自注册表允许的枚举，再加载对应文件。第二次调用得到核心规则、已选模块和 contentPlan，只生成 DeckPlan。随后由代码渲染。

优点是不用引入完整工具调用协议，却已经实现真正的按需加载与阶段隔离；缺点是增加一次模型调用和延迟。

路线 C：把 Completion 改造成能调用 Skill 工具的 Agent 循环

向模型提供 activate_skill(name)、read_skill_resource(skill, path) 等工具。模型读轻量目录，自行决定何时加载。它最接近开放 Agent Skills 的客户端实现，也最灵活；但需要工具调用、循环控制、权限、上下文去重和调用上限，明显超出当前 ModelRequest 合同。

我推荐路线 B。你的任务天然分成“理解与规划”和“渲染与验证”，两次调用有清晰产物，也方便保存中间结构。现在就上路线 C 会让插件从文稿生成器变成通用 Agent Runtime，工程范围膨胀太快。

1. 一个可执行的 V2 架构

源回答→规划调用→ContentPlan + 模块 ID→宿主加载模块→DeckPlan→渲染器→校验

建议把现有 title + deck + html 协议改成：模型只输出 title + deckPlan；HTML 由 renderer 从 deckPlan 生成。若你暂时不能取消模型生成 HTML，也至少让模型先单独提交 DeckPlan，第二阶段再根据确认后的结构生成 HTML，避免在一个超长输出中同时规划和实现。

2. 注册表需要从“单文件记录”升级为“包记录”

当前 SkillRecord 只有入口文件路径和整文件 hash。V2 可以增加：

SkillPackageRecord
├── name / description / version / category
├── entryPath + entryHash
├── resources[]
│   ├── relativePath
│   ├── kind: reference | asset | script
│   ├── hash
│   └── estimatedTokens（文本资源）
└── enabled / trusted / importedAt

导入时拒绝绝对路径、.. 路径穿越和符号链接逃逸；列出资源但不默认读取；每个生成版本继续记录实际使用的资源及 hash，而不是只记录根 Skill。

3. 页面模式应该成为受限枚举

不要让模型返回任意 layoutId。宿主在规划调用的 schema 中提供合法枚举，例如：

title-cover
concept-definition
concept-diagram
step-proof
worked-example
comparison
summary-map
practice-question

每个模式还要有容量规则与允许 block 类型。这样模型的创造性集中在“选择哪种表达”和“怎样组织内容”，不会浪费在重复搭建导航、缩放脚本和基础 CSS 上。

4. 校验分三层

  • 语义校验：所有重要源段是否至少被某个 sourceRef 覆盖；是否出现无来源的新事实。
  • 结构校验：layoutId、block 类型、ID、字段长度和 DeckPlan schema 是否有效。
  • 浏览器校验：1600×900 实际渲染后是否有文字或图形超边界；交互、翻页和连续模式是否正常。

机器很难完全证明“没有改变原意”，但 sourceRef、内容覆盖和新事实标记能显著提高可审计性。

五、第三问：前沿 Skill 设计中有没有类似结构

有，而且与你的直觉最接近的不是“Skill 继承树”，而是渐进式披露。

1. Agent Skills 开放规范：三层加载

Agent Skills 规范把加载分成：

  1. 启动时只提供所有 Skill 的 name + description，形成轻量目录；
  2. 任务匹配后加载完整 SKILL.md；
  3. scripts、references 和 assets 仅在需要时读取。

规范建议 SKILL.md 保持在约 500 行以内，较长细节拆到资源文件，并且引用尽量只从入口文件向下一层，不建立很深的引用链。这与“整体→局部”相似，但它的核心不是文档层级漂亮，而是上下文成本随需要逐步支付。

面向客户端实现者的官方指南还给出了两种激活方式：有文件工具的 Agent 直接读取 SKILL.md；没有文件访问能力的系统提供专用 activate_skill 工具，或由宿主程序注入。它也建议用结构标签包住 Skill 内容、列出但不急于读取资源、去重重复激活，并在上下文压缩时保护已激活的规则。

2. 官方复杂文档 Skill：入口像路由器，细节在指南与脚本

Anthropic 公开的 PPTX Skill 是很贴近你项目的参考：根 SKILL.md 先按“读取、基于模板编辑、从零创建”分流；具体编辑流程放在 editing.md，创建细节放在 pptxgenjs.md，另有解包、复制页面、清理、打包和缩略图脚本。模型负责判断任务路线与内容映射，容易出错的文件操作交给脚本，并通过渲染后的视觉检查收尾。

这提供了两个值得借鉴的点：

  • 根 Skill 是路由器和流程，不是全部知识的仓库；
  • 复杂格式的可靠性来自“说明 + 工具 + 验证”，不是无限延长提示词。

官方 Web Artifacts Builder 也把初始化、开发、打包为单文件 HTML 分成固定步骤，并用脚本完成脚手架与打包。这与 Inno Visualizer 的自包含 HTML 目标相近，但你的项目还需要更严格的内容忠实和分页结构，所以不能直接照搬它的前端自由度。

3. GitHub Copilot 的采用说明了可移植方向

GitHub 官方文档已经支持项目级和个人级 Agent Skills，并接受 .github/skills、.claude/skills 或 .agents/skills 等位置。它说明“文件夹 + SKILL.md + 资源”的格式正在成为跨客户端接口，而不是某一家模型独有的提示写法。

对你的意义是：如果 Inno Visualizer 的导入格式逐步兼容 name/description + SKILL.md + references/scripts/assets，未来可以复用外部 Skill，或把你的 K12 文稿 Skill 带到其他 Agent；项目专用的 category、优先级和 Deck schema 可以放在扩展 metadata 中。

4. 还没有形成统一标准的部分

必须直截了当地说：目前没有一个被 Agent Skills 规范统一定义的“多层 Skill 继承体系”。以下问题仍由各客户端自行决定：

  • 一个 Skill 能否依赖或调用另一个 Skill；
  • 多个 Skill 冲突时如何排序；
  • 自动选择由模型、关键词还是用户完成；
  • 资源是否能被模型直接读取；
  • Skill 内容在上下文压缩中怎样保留；
  • 脚本的权限与沙箱如何管理。

因此，不建议为 Inno Visualizer 设计复杂的“父 Skill—子 Skill—孙 Skill”继承语法。它会带来菱形依赖、版本冲突和难以复现的最终提示。更稳妥的是：一个根工作流 + 一层平铺资源 + 明确的模块 ID + 宿主记录实际装载集合。

5. 真正更前沿、也更重要的三个方向

第一是上下文工程：不是追求单个完美提示，而是控制目录、激活、装载、去重、压缩与证据链。你的当前 skill-composer 已经是其早期形态。

第二是程序化执行：把模型擅长的语义判断与代码擅长的确定性操作分开。布局渲染、路径安全、HTML stamp、schema 和视觉检测都应尽可能程序化。

第三是评测驱动的 Skill 开发：用固定任务集、失败类型和量化指标比较 Skill 版本。官方最佳实践同样强调从真实任务和纠错记录提炼 Skill，再通过真实执行迭代，而不是只让模型凭常识写第一版。

局部自检 3：你的设计与前沿方向最接近的准确表述是什么？
答案：不是“建立多层继承 Skill”，而是“建立一个使用渐进式披露的分阶段文稿生成 Skill：根入口负责路由，条件参考按需装载，页面结构由受限布局目录与确定性渲染器实现，并通过评测闭环迭代”。

六、针对 Inno Visualizer 的推荐决策

把全文压缩为工程决策，我建议你按下面顺序推进。

近期：不改模型调用合同也能完成

  1. 扩展 frontmatter，加入 description，保留现有 id/version/category 作为 metadata。
  2. 解析时分离 frontmatter 与正文，不再把注册信息重复注入模型。
  3. 给激活正文设置合理的 token 上限，而不是只设 512 KiB 文件上限。
  4. 在组合器中建立显式优先级和冲突诊断；开发界面显示本次 Skill、版本、估算 token 与最终区块摘要。
  5. 建立十到二十篇固定语料的 Skill 回归集。

中期：实现真正的分层

  1. 把生成拆成 ContentPlan / DeckPlan 与 HTML 两阶段。
  2. 支持 Skill 目录包和资源清单；先做宿主静态装载，再做规划调用选择模块。
  3. 页面模板变为受限 layoutId + slots，并由 renderer 生成 DOM。
  4. manifest 记录本次实际使用的入口与资源 hash。
  5. 校验错误指向 slide ID、layout ID 与具体字段，使返修局部化。

暂缓：不要过早扩张

  1. 暂不做任意 Skill 互相依赖或继承。
  2. 暂不把模型调用升级为完整通用 Agent 工具循环。
  3. 暂不支持任意脚本由导入 Skill 执行；先只允许内置、受信、固定接口脚本。
  4. 暂不让模型自己发明页面模板或修改核心 HTML shell。

这不是保守，而是在保护项目边界：Inno Visualizer 的价值是可靠地把已定稿语料变成可读文稿，不是重造一个通用 Agent 平台。

七、结论：Skill 的价值不在“层数”，而在正确分配判断与执行

你的第一问可以用一句话回答：当前 Skill 由插件读取并全文拼入 systemPrompt，源语料与父版本放入 userPrompt，然后通过隔离 Completion 一次送给模型；它不是模型自主加载的工具。

第二问的答案是：保留“整体到局部”的思路，但把它改成四层——产品合同、根工作流、按需参考、确定性执行；再把生成改成内容分析、整稿规划、页面选择、渲染和校验五个阶段。语言与学科属于可选参考模块，单页模板属于 layout 接口和渲染器。

第三问的答案是：Agent Skills 的渐进式披露、官方复杂文档 Skill 的入口路由与按需指南、脚本加视觉校验，都是成熟的类似设计；但多层继承和冲突语义尚无统一标准，不值得自行发明一套复杂体系。

最终设计可以压缩成这条关系：

模型负责理解“这页为什么存在、应该表达什么、该选哪种页面模式”；Skill 负责规定判断流程和选择边界；渲染器负责“页面究竟怎样稳定生成”；验证器负责证明结果满足合同。

当这四者分工清楚时，Skill 不需要写成一本巨著，也能发挥得更好。

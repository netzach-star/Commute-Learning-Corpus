0. 先给出本文的中心结论

当一个项目缺少内部结构文档，而你又需要修改功能时，正确做法不是先把所有代码从头到尾读一遍，也不是等待别人补出一份完美架构说明。你应当从一个具体、可重现的系统行为进入，沿着它的实际执行路径，恢复一个足以支持当前变更的局部模型。

明确要改变的行为
→ 重现当前行为
→ 找到入口
→ 追踪调用链与数据变化
→ 识别状态、副作用和不变量
→ 用日志、断点与测试验证
→ 设计最小修改
→ 验证异常与回退路径
→ 把新认识沉淀成文档

这里最重要的变化，是从“我要理解整个项目”转为：

为了安全地改变某个行为，我现在必须理解哪些部分？哪些部分暂时可以视为黑盒？

这套方法属于软件工程中的程序理解、代码库探索和变更影响分析。工程师有时也会把它形象地称为“软件考古”：现有代码是遗址，测试、日志、版本历史和残留文档是证据，你的任务是根据这些证据重建系统真正的结构，而不是只相信某一份可能已经过期的说明。

1. 为什么项目文档看起来总在描述黑盒

你观察到，很多项目文档主要回答：

  • 项目提供什么功能；
  • 如何安装和启动；
  • 有哪些命令、接口和配置；
  • 输入输出格式是什么；
  • 数据怎样保存或导出。

这些内容的共同特点是：它们把项目当成一个对外提供能力的整体。只要输入符合契约，使用者通常不需要知道内部由哪些函数、队列、状态机和存储组件协作完成。

这种文档并不是低质量文档。相反，对外部使用者而言，它是最应该稳定维护的部分，因为外部接口一旦改变，会影响所有调用者。内部实现则可以在不改变外部行为的前提下不断重构，因此更容易变化，也更难靠一份静态文档永久描述。

需要修正的一点：数据库不一定是“黑盒输出”。对普通用户而言，它通常是系统内部的持久化状态；只有当其他服务直接依赖某张表、某个文件格式或某组字段时，它才同时成为跨模块接口。是否属于输出，取决于谁被允许依赖它。
对象通常属于什么修改风险来自哪里
HTML 文件显式输出物用户、其他工具可能直接消费
HTTP API 返回值对外契约调用方依赖字段和语义
数据库表内部持久化模型迁移、数据一致性、隐含共享依赖
共享数据库表事实上的跨系统接口多个服务可能绕过正式 API 直接读取
日志可观察副产品运维和监控可能依赖格式
消息队列事件服务之间的接口异步消费者依赖事件结构与时序
缓存内部临时状态过期策略和一致性假设

因此，问题不是“为什么没人写白盒文档”，而是：内部结构变化太快、层次太多，单一文档很难同时做到完整、准确和易维护。成熟团队通常把内部知识分散到架构说明、流程文档、数据模型、决策记录和自动化测试中。

2. 黑盒、灰盒与白盒：三种不同的理解层次

2.1 黑盒视角：系统向外界承诺什么

黑盒视角只关心外部可观察行为。例如：

输入：一段对话、生成参数和模板选择。

输出：一个可打开的 HTML 文件，以及成功或失败状态。

这里不关心系统用了几轮模型、怎样存储任务、如何生成页面结构。黑盒模型适合用户、调用方、验收测试和产品需求。

2.2 灰盒视角：系统内部有哪些主要阶段

灰盒视角会打开系统，但只看到主要处理阶段：

用户发起生成
→ 收集并规范化对话
→ 规划内容结构
→ 用户确认大纲
→ 生成 HTML
→ 保存文件与状态
→ 展示结果

灰盒模型回答各阶段的职责、输入输出、依赖关系和失败位置，但不要求立即知道每一个函数。对维护者而言，它通常是最有价值的中间层：没有它，阅读代码容易迷失；有了它，又能继续定位具体实现。

2.3 白盒视角：具体由哪些代码实现

GenerateButton.onClick()
  → generationService.startTask()
  → conversationRepository.loadMessages()
  → outlinePlanner.createOutline()
  → htmlGenerator.generate()
  → artifactRepository.save()
  → taskStore.markCompleted()

白盒视角直接对应文件、函数、类型和数据库操作，是实际修改代码所需的层次。但白盒模型越细，越容易过期。因此你不应一次性建立全项目的函数级地图，而应围绕当前变更按需深入。

合理目标：知道“生成 HTML”流程经过哪些模块，并能定位每个关键阶段的实现。
不合理目标：在修改一个删除功能前，先记住整个仓库中每个文件和函数的用途。

3. 不要寻找一本不存在的“完整项目说明书”

你可能会自然地期待一份文档，它同时描述系统目标、所有模块、完整调用关系、数据结构、异常处理、历史设计理由和每个函数的作用。但这种文档几乎不可能长期保持准确。

原因至少有四个：

  1. 不同读者需要不同抽象层次。 新开发者需要模块地图，维护者需要某条流程，架构师关心边界，测试人员关心行为与不变量。
  2. 代码变化速度高于文档更新速度。 函数调用和文件组织可能每周变化，而产品边界和核心领域模型相对稳定。
  3. 很多知识并不写在代码结构中。 “为什么不用另一种方案”“哪个怪异分支是为了兼容旧数据”等理由只能从版本历史、讨论和决策记录中恢复。
  4. 系统实际行为由运行环境共同决定。 配置、数据库内容、动态注册、并发时序和外部服务都会影响执行，静态图无法完全覆盖。

因此，更现实的知识来源是四类证据：

证据主要告诉你什么局限
代码系统可能怎样运行、有哪些分支与依赖可能包含废弃代码和未启用路径
测试哪些行为被团队要求保持测试可能缺失或只覆盖理想路径
运行轨迹当前环境下实际上怎样运行一次轨迹无法覆盖所有分支
历史与 ADR为什么形成当前设计记录可能不完整，背景可能改变

你的目标不是从某一份材料中获得绝对真相，而是让多种证据相互校验，形成一个暂时可信的工作模型。

4. 第一步：把“理解项目”改写成具体变更问题

“我要理解这个项目”不是一个可完成的任务。项目越大，这个目标越会让你在目录、框架和工具名之间漫游，却无法判断何时算理解完成。

更好的表达包含三部分：

当前行为：系统现在怎样工作？

目标行为：希望改变成什么？

需要理解的范围：为完成这个改变，哪些入口、状态、数据和副作用必须查清？

例如：

当前行为：
删除生成结果时，只删除 HTML 文件，不删除资源目录。

目标行为：
删除 HTML 时，同时删除它独占的资源目录；
如果资源被其他结果共享，则不能误删。

需要理解：
删除入口、文件记录、资源归属关系、数据库状态、
失败补偿、界面刷新和重复删除行为。

这个改写会立即缩小搜索空间。你不需要理解模型调用、内容规划和模板设计；你主要需要理解“制品生命周期”这一条路径。

阶段完成标准

在继续读代码前，你应当能用一两句话说明：哪个可观察行为要改变；成功后用户能看到什么差异；若修改失败，最严重的后果是什么。

5. 第二步：找到入口，并追踪一条纵向切片

5.1 什么是入口

入口是一次系统行为被触发的位置。常见入口包括：

  • 用户点击按钮；
  • HTTP 请求到达路由；
  • 命令行命令；
  • 定时任务；
  • 消息队列事件；
  • 插件回调；
  • 应用启动或文件变化。

寻找入口时，不要只看目录名猜测。应使用可观察线索：

  • 搜索界面上的文字，如“生成 HTML”“删除结果”；
  • 查看浏览器网络请求，定位 API 路径；
  • 运行功能并观察日志模块名；
  • 搜索测试用例中调用的公共函数；
  • 搜索事件名、数据库状态值或错误提示。

5.2 为什么要纵向切片，而不是横向扫目录

横向阅读通常是“把某个目录中所有文件读完”。纵向切片则是“从一个用户行为开始，一直跟到最终副作用”。

例如，一个“生成 HTML”行为可能跨越：

前端按钮
→ API 路由
→ 任务编排服务
→ 模型适配器
→ HTML 生成器
→ 文件仓库
→ 数据库状态
→ 前端结果展示

如果你先把前端目录读完，只会了解许多与当前功能无关的组件；如果顺着调用链向下，你会很快看到这条功能真正涉及的边界。

5.3 每经过一个节点都问六个问题

  1. 它接收什么输入？
  2. 它产生什么输出？
  3. 它调用谁，谁又调用它？
  4. 它修改了哪些持久化或共享状态？
  5. 它可能怎样失败？
  6. 失败后由谁处理、重试或回滚？

把答案写成追踪表，而不是只在脑中记忆：

步骤组件输入输出副作用失败方式
1生成按钮用户选项请求参数设置加载状态参数缺失
2API 控制器HTTP 请求任务编号创建任务记录权限或校验失败
3任务编排器任务配置阶段结果调用模型超时、取消
4HTML 生成器语料与结构HTML 字符串通常无格式无效
5文件仓库HTML 与资源输出路径写磁盘权限、磁盘不足
6状态仓库任务编号完成状态更新数据库事务失败

6. 第三步：同时记录控制流、数据流、状态流与副作用

很多初学者追踪项目时，只记“函数 A 调用函数 B”。这只能恢复控制流，却无法回答数据如何变化、对象处于什么状态、什么时候已经产生不可逆影响。

6.1 控制流：谁决定下一步执行什么

用户
→ 前端事件处理器
→ API 控制器
→ 应用服务
→ 领域服务
→ 仓库或外部适配器

控制流主要回答调用顺序、同步与异步边界、错误返回方向。

6.2 数据流：一个对象经过了哪些表示转换

ConversationMessage[]
→ CorpusDocument
→ Outline
→ PageModel[]
→ HTML string
→ ArtifactRecord

每一步都应写清楚数据类型和语义，而不是只写“处理数据”。尤其要注意：

  • 哪些字段来自用户；
  • 哪些字段由模型或程序推断；
  • 哪些对象会被序列化；
  • 哪些转换会丢失信息；
  • 哪些格式已经成为其他模块依赖的契约。

6.3 状态流：核心对象经历哪些生命周期

created
→ validating
→ planning
→ awaiting_confirmation
→ generating
→ saving
→ completed

同时记录失败分支：

validating → rejected
planning → failed
awaiting_confirmation → cancelled
generating → retrying → failed
saving → inconsistent

状态流能揭示许多函数调用图看不出的关键问题：哪一步允许用户取消、哪一步能够重试、哪一步以后已经写入文件、哪一步失败会留下半成品。

6.4 副作用：系统对外部世界做了什么

典型副作用包括：

  • 写数据库；
  • 写文件或删除文件；
  • 调用模型 API；
  • 发送事件或通知；
  • 修改缓存；
  • 产生费用；
  • 改变用户可见状态。
一个典型一致性陷阱：如果系统先把数据库状态更新为 completed，再写 HTML 文件，那么文件写入失败时，界面会显示任务完成，但输出文件不存在。只有同时记录状态和副作用，才能发现这种问题。

7. 第四步：建立五张局部地图

“画架构图”不应理解为制作一张漂亮的大图。更实用的是围绕当前流程建立五张小地图，每张回答不同问题。

7.1 模块职责图：谁负责什么

界面层
  └─ 接收用户操作、展示状态
应用编排层
  └─ 控制步骤、权限、事务与任务生命周期
内容处理层
  └─ 把原始对话转换为结构化语料
HTML 生成层
  └─ 把页面模型转换为最终文件
存储层
  └─ 保存任务、制品、配置和索引
外部服务适配层
  └─ 隔离模型 API、文件系统等外部依赖

职责图最重要的不是层数，而是判断一个规则“应该属于哪里”。例如“未确认大纲不得进入最终生成”是应用流程规则，不应只隐藏在前端按钮是否可点击之中。

7.2 控制流图：一次请求按什么顺序推进

它回答谁发起、谁编排、谁返回、异步任务在哪里开始。对于复杂系统，可以分别画正常路径与异常路径，不要把所有分支塞进一张图。

7.3 数据流图：各阶段传递什么

它回答模块之间传递的是原始消息、领域对象、DTO、文件路径还是事件。数据流图能帮助你识别不必要耦合：如果 HTML 生成器直接读取数据库和界面状态，它就同时依赖了多个层次，很难独立测试。

7.4 状态与生命周期图：对象何时合法

对任务、文件、用户会话等核心对象分别记录状态，而不是只画“整个系统状态”。不同对象可能不同步：任务已经失败，但临时文件仍存在；数据库记录已删除，但资源目录仍在。

7.5 边界与接口图：哪些连接点允许被依赖

边界包括：

  • 模块公开函数或类接口；
  • HTTP API；
  • 仓库接口；
  • 事件结构；
  • 文件格式；
  • 插件协议；
  • 配置结构。

修改边界内部的实现，通常比修改边界本身风险低。若一次变更需要同时改 API、数据库表、事件格式和前端状态，说明它跨越多个契约，应当被视为高风险变更。

8. 第五步：寻找隐藏的不变量

理解流程并不等于能够安全修改。你还需要知道系统中哪些条件在任何时候都必须成立，这些条件称为不变量。

例如：

  • 每个已完成任务必须对应一个可读取的输出文件；
  • 一个资源目录只能由明确的制品拥有，或者必须记录共享引用；
  • 用户未确认大纲前，不能生成最终 HTML；
  • 同一个任务不能同时存在两个互相冲突的“当前版本”；
  • 删除制品不能影响其他任务仍在使用的资源；
  • 数据库记录与文件系统状态必须最终一致。

项目很少有一份“不变量清单”。你通常要从以下位置推断：

位置能暴露什么不变量
参数校验哪些输入组合被认为非法
数据库约束唯一性、非空、引用关系
测试断言团队认为必须保持的行为
异常处理哪些失败被预期，如何恢复
重试和幂等逻辑重复执行时什么必须保持一致
文件命名规则对象身份、归属和查找关系
Git 历史曾被破坏过、因此特别保护的条件

很多严重缺陷不是“某个函数算错”，而是新功能打破了一个未被发现的不变量。例如删除逻辑在正常情况下工作，但它错误地假设资源目录从不共享，于是删除一个 HTML 时破坏了另一个 HTML。

阶段完成标准

在改代码前，至少列出三类不变量：数据完整性不变量、状态顺序不变量、权限或归属不变量。若一条都说不出来，说明你对变更风险还没有形成模型。

9. 第六步：用运行证据验证你的代码阅读

静态阅读只能告诉你代码“可能”怎样运行。真实系统可能存在未启用旧实现、条件配置、动态注册、缓存、并发任务和外部服务差异，因此必须进行动态验证。

9.1 静态手段

  • 查找引用和调用层次；
  • 阅读类型定义与接口实现；
  • 查看数据库迁移；
  • 阅读测试和测试夹具；
  • 查看 Git blame、提交历史和相关 issue；
  • 搜索状态枚举、错误码和事件名。

9.2 动态手段

  • 在关键节点加入临时结构化日志；
  • 设置断点，查看实际调用栈；
  • 观察网络请求与响应；
  • 在操作前后比较数据库记录；
  • 在操作前后比较文件系统；
  • 人为制造超时、无权限、磁盘失败等异常；
  • 记录状态变化时间和线程或任务编号。

9.3 建立“假设—证据”表

不要把阅读推断直接当作事实。可以记录：

假设证据结果
任务完成后才写数据库运行日志与 SQL 时间错误：数据库先更新
每个 HTML 都有独立资源目录样例数据、创建逻辑尚未确认旧版本数据
删除 API 只被前端调用全局搜索、接口日志还有批量清理任务调用
重复删除是安全的连续调用两次第二次返回 500，需设计幂等行为

这张表能够防止“我看代码好像是这样”逐渐变成未经验证的架构事实。

10. 第七步：修改前写一份小型变更设计

小型变更不需要几十页文档，但需要把你的理解转化为可审查的设计。推荐至少包含以下部分。

10.1 当前行为与目标行为

当前：删除 HTML 后，资源目录和数据库记录可能残留。
目标：删除操作最终使数据库、HTML 和独占资源一致消失；
共享资源不得被误删。

10.2 主要修改点与可能受影响模块

主要修改：artifactDeletionService
可能涉及：
- artifactRepository
- resourceReferenceChecker
- delete API
- 批量清理任务
- 前端列表刷新
- 审计日志

10.3 需要保持的不变量

  • 不能删除其他制品仍在引用的资源；
  • 重复删除应具有明确、稳定的结果；
  • 中途失败不能静默留下“数据库已删、文件仍在”的未知状态；
  • 用户只能删除有权限访问的制品。

10.4 失败与恢复策略

必须明确讨论部分成功：

  • 数据库删除成功，文件删除失败怎么办？
  • HTML 删除成功，资源目录删除失败怎么办？
  • 进程在两个步骤之间崩溃怎么办？
  • 是否需要事务、补偿任务、软删除或待清理状态？

10.5 验证矩阵

场景预期结果验证方式
正常删除独占资源记录、HTML、资源均消失集成测试
资源目录不存在仍能达到一致终态幂等测试
资源被共享只删当前制品引用关系测试
无文件权限进入明确失败或待清理状态故障注入
重复删除返回稳定结果，不破坏其他数据连续调用
中途崩溃重启后可恢复或重新清理恢复测试

这份文档真正指导的是“在哪里改、为什么这样改、什么不能破坏、怎样证明完成”，而不是泛泛描述项目有什么功能。

11. 第八步：用特征测试保护现有行为

面对测试不充分的项目，直接重构最危险。此时应先补特征测试：它不判断当前行为是否合理，而是忠实记录系统现在实际上怎样运行。

例如，现有缺陷可能是：

给定：一个 HTML 文件和对应资源目录
执行：当前删除操作
实际：HTML 被删除，资源目录仍然存在

先把这个行为固定下来，有两个价值：

  1. 你确认自己找到了真正执行删除的路径，而不是修改了未被调用的旧代码；
  2. 修改后能够明确区分“有意改变的行为”和“意外受影响的行为”。

接下来再把目标测试写成：

给定：一个 HTML 文件和它独占的资源目录
执行：新的删除操作
期望：HTML 与资源目录均被删除，数据库达到一致终态

但不能只写正常路径。对有副作用的功能，至少覆盖：

  • 边界输入；
  • 重复调用；
  • 部分资源缺失；
  • 外部依赖失败；
  • 权限不足；
  • 并发执行；
  • 旧版本数据。
测试的角色：测试不只是验收工具，也是可执行的内部文档。它描述系统承诺保持哪些行为，并在代码改变时主动提醒你模型是否被破坏。

12. 哪些内部文档值得长期维护

不要试图记录每个函数。应优先维护变化较慢、对未来变更有高价值的信息。

12.1 ARCHITECTURE.md：稳定的整体结构

建议包含：

  • 系统目标与边界；
  • 核心模块和职责；
  • 主要运行时组件；
  • 关键接口与依赖方向；
  • 最重要的技术取舍。

它回答“整个项目大致怎样组织”，不回答每条业务流程的所有细节。

12.2 DEVELOPMENT.md：开发与调试基线

包括安装、启动、测试、环境变量、测试账号、调试方法、常见故障和本地数据构造。它能让后来者先获得一个可重复运行的项目，而不是在环境问题中误判代码行为。

12.3 docs/flows/：重要场景的流程文档

docs/flows/generate-html.md
docs/flows/delete-artifact.md
docs/flows/revise-block.md
docs/flows/recover-failed-task.md

每篇建议记录：

  • 入口与触发条件；
  • 控制流与数据流；
  • 状态变化；
  • 外部副作用；
  • 关键不变量；
  • 失败处理；
  • 关键代码位置。

12.4 docs/data-model.md：数据对象及其关系

它应解释领域对象、字段语义、对象生命周期、数据库表与文件系统之间的对应关系。不要只复制数据库建表语句，因为字段结构不能解释业务含义和合法状态。

12.5 docs/adr/：架构决策记录

ADR，即 Architecture Decision Record，记录一项重要设计为什么被选择。例如：

ADR-004：每个 HTML 使用独立资源目录

背景：资源需要离线访问并随制品一起删除。
备选：统一资源池、内容寻址存储、独立目录。
决定：第一阶段使用独立目录。
理由：实现简单，归属清晰，删除成本低。
后果：可能重复存储相同资源；未来若共享需增加引用管理。

代码能够告诉你“现在采用独立目录”，却很难告诉你为什么没有选择共享资源池。ADR 保存的正是这种最容易丢失的设计理由。

12.6 测试：可执行契约

高价值测试描述正常流程、边界条件、错误恢复和不变量。流程文档与测试应相互对应：文档解释结构，测试确保关键行为仍然成立。

13. InnoSpark 案例：怎样重建“生成 HTML”闭环

下面不假设 InnoSpark 当前代码一定如此，而是示范怎样建立一份待验证的工作模型。

13.1 先定义理解目标

当前行为：用户提供对话内容，系统经过若干处理后生成 HTML。

计划变更：在最终生成前增加可确认的大纲，并允许失败后从某个阶段恢复。

必须理解：生成入口、轮次编排、阶段数据、任务状态、文件写入、重试边界和用户确认状态。

13.2 建立灰盒闭环

用户选择对话和生成要求
→ 创建生成任务
→ 检查内容规模与输入合法性
→ 整理完整语料
→ 生成大纲
→ 等待用户确认
→ 生成页面模型与 HTML
→ 保存 HTML、资源与元数据
→ 更新任务状态并展示结果
→ 用户反馈或局部修改

13.3 数据流草图

ConversationMessage[]
→ SourceCorpus
→ ContentPlan
→ ConfirmedOutline
→ BlockModel[]
→ HtmlArtifact
→ ArtifactRecord

这里要进一步查清：

  • SourceCorpus 是否保存原始消息来源，还是只保留改写文本；
  • 大纲确认后，确认的是全文结构还是只确认标题列表；
  • BlockModel 是否是稳定中间表示，能否支持局部修改；
  • HTML 和资源目录如何关联；
  • 数据库记录保存的是最终文件路径，还是还保存中间阶段数据。

13.4 状态流草图

created
→ validating
→ corpus_ready
→ outline_ready
→ awaiting_confirmation
→ generating_html
→ saving
→ completed

异常与恢复状态可能包括：

validating → rejected
corpus_ready → planning_failed
awaiting_confirmation → cancelled
generating_html → retryable_failed / terminal_failed
saving → cleanup_required

13.5 初步不变量

  • 未确认的大纲不能被当成最终生成依据；
  • 任务进入 completed 时，HTML 必须存在且能够打开；
  • 中间阶段数据应能与同一任务唯一关联；
  • 重试不能重复创建互相冲突的最终制品；
  • 局部修改不能在没有记录的情况下破坏原始语料与块结构的对应关系；
  • 删除最终制品时，资源归属和数据库记录必须得到一致处理。

13.6 用证据逐项验证

要确认的问题优先证据
真正创建任务的入口在哪里前端网络请求、API 路由、集成测试
多轮 AI 由谁编排应用服务调用链、模型调用日志
确认大纲状态保存在哪里数据库迁移、状态枚举、请求负载
文件何时写入文件时间、日志、断点
失败后从头重跑还是阶段恢复重试代码、任务状态、故障注入
资源目录是否可能共享创建逻辑、历史数据、删除测试

当这些问题有证据支持后，你才适合设计“大纲确认”和“阶段恢复”。否则很可能把新逻辑只加在界面上，却没有建立真实的后端状态；或者为了恢复任务重复生成文件，造成多个版本冲突。

14. 一套可直接执行的项目考古流程

以后面对任何陌生项目，可以按以下顺序执行。

  1. 建立运行基线。 从干净环境启动项目，重现目标功能，知道日志、测试和数据在哪里。
  2. 定义具体变更。 写清当前行为、目标行为、失败后果和理解范围。
  3. 定位入口。 从界面、API、命令、事件或测试找到真正触发行为的位置。
  4. 追踪纵向切片。 沿调用链直到最终数据库、文件、事件或外部服务副作用。
  5. 记录四条流。 控制流、数据流、状态流和副作用分别记录。
  6. 建立五张地图。 职责、控制、数据、生命周期和接口边界。
  7. 提炼不变量。 找出数据完整性、状态顺序、归属权限、幂等与恢复条件。
  8. 动态验证。 用日志、断点、数据库比较、文件比较和故障注入验证推断。
  9. 补特征测试。 固定当前实际行为，确认自己改的是有效路径。
  10. 写变更设计。 说明修改点、影响范围、失败策略、测试矩阵和回退方式。
  11. 实施最小修改。 优先在现有边界内改动，避免同时重构无关模块。
  12. 验证正常与异常路径。 不只确认“点一下能成功”，还要测试失败、重复、并发和旧数据。
  13. 沉淀知识。 更新流程文档、数据模型、ADR 和测试，而不是把所有发现留在临时笔记里。

什么时候算“理解得足够”

你不需要能够解释整个项目。只要你能画出目标行为的完整闭环，指出主要数据与状态，列出关键副作用和不变量，说明修改点及其影响，并用测试验证这些判断，就已经足以进入当前变更。

15. 常见错误与停止条件

15.1 从目录第一行开始顺序读完整仓库

问题在于没有选择标准。你会花大量时间阅读与目标无关的工具代码、页面组件和旧实现。应改为场景驱动的纵向阅读。

15.2 只画函数调用图

函数调用不能说明数据含义、状态顺序和外部副作用。必须至少同时追踪数据、状态和不变量。

15.3 把文档当作绝对真相

文档应被视为一项证据，并与代码、测试和运行轨迹交叉验证。文档可能过期，代码也可能未被实际启用。

15.4 发现坏结构后立刻大规模重构

陌生项目中，你尚不知道哪些奇怪代码承担兼容、恢复或性能职责。先补测试和运行证据，再做局部改动；结构性重构应当作为独立变更。

15.5 只测试成功路径

真正的工程风险常发生在中途失败、重复执行、并发操作、旧数据和外部服务异常。涉及数据库与文件的流程尤其需要故障测试。

15.6 把所有发现都写进一份巨型文档

巨型文档难以更新。应按照整体架构、具体流程、数据模型、决策理由和测试契约分层维护。

15.7 什么时候应停止继续深入

当出现以下情况时，可以停止扩展理解范围，进入修改：

  • 目标行为的入口和最终副作用已经闭合；
  • 关键数据对象、状态和不变量已经明确；
  • 主要假设已经通过运行或测试验证；
  • 未知部分被隔离在稳定接口之后；
  • 你能写出具体测试矩阵和失败恢复策略。

相反，如果你还无法回答“文件写入失败后数据库是什么状态”“这个资源是否可能被共享”“同一个接口还有谁调用”，就不应急着修改。

16. 自检题与参考答案

16.1 自检题

  1. 为什么 README 和 API 文档通常更偏向黑盒视角？
  2. 灰盒模型与白盒模型分别解决什么问题？
  3. 为什么“先读完整个项目”通常不是高效策略？
  4. 什么是纵向切片？
  5. 控制流、数据流与状态流有什么区别？
  6. 为什么副作用必须被单独记录？
  7. 什么是不变量？它通常隐藏在哪里？
  8. 代码阅读为什么必须配合动态验证？
  9. 特征测试与普通目标测试有什么区别？
  10. 一份小型变更设计至少应包含哪些内容？
  11. ADR 主要保存什么信息？
  12. 对 InnoSpark 的 HTML 生成流程，至少应建立哪些状态和不变量？

16.2 参考答案

  1. 因为外部使用者最关心稳定功能、输入输出和使用方式，而内部实现允许在不改变契约的情况下变化。
  2. 灰盒模型描述主要阶段、职责和连接方式，帮助建立整体方向；白盒模型定位具体文件、函数、类型和存储操作，用于实际修改。
  3. 项目文件顺序不等于执行顺序，大量代码与当前变更无关；没有具体问题就无法判断哪些内容重要、何时理解足够。
  4. 从一个真实用户行为或系统事件进入，沿实际调用链一直追踪到最终数据、状态和外部副作用的一条端到端路径。
  5. 控制流描述谁调用谁；数据流描述对象怎样转换和传递；状态流描述核心对象在生命周期中处于什么阶段以及哪些转换合法。
  6. 数据库、文件、外部 API 和事件等副作用可能部分成功、失败或重复发生，决定了事务、补偿、幂等和恢复设计。
  7. 不变量是系统任何合法状态下都必须成立的条件。它常隐藏在校验、数据库约束、测试、异常处理、重试逻辑、命名规则和历史修复中。
  8. 静态代码可能包含未启用路径、条件配置和旧实现；运行轨迹能确认当前环境下真正的调用顺序、数据和副作用。
  9. 特征测试先忠实固定当前实际行为，即使该行为有缺陷；目标测试则描述修改后应达到的新行为。
  10. 当前与目标行为、修改点、影响范围、不变量、失败与恢复策略、验证矩阵以及回退方式。
  11. ADR 保存某项重要架构决定的背景、备选方案、选择理由和后果，解释“为什么设计成这样”。
  12. 至少包括创建、校验、语料准备、大纲生成、等待确认、HTML 生成、保存、完成和失败状态；不变量包括未确认不得最终生成、完成必须有有效文件、重试不得生成冲突制品、资源与数据库保持一致。

17. 本文结论与下一篇建议

面对一个内部文档不足的项目，你不需要在黑盒使用和“完全读懂源码”之间二选一。真正可行的方法是在两者之间建立一个逐步深入的理解层次：

外部行为
→ 主要处理阶段
→ 局部纵向流程
→ 数据与状态模型
→ 关键不变量
→ 具体实现与测试

这套方法的核心是证据驱动和范围控制：

  • 用具体变更限定理解范围；
  • 用真实场景而不是目录结构组织阅读；
  • 把调用、数据、状态和副作用分开记录；
  • 用不变量理解系统为何不能随意修改；
  • 用运行和测试纠正静态阅读中的猜测；
  • 把每次修改得到的稳定知识沉淀成分层文档。

因此，项目内部结构并不是由某一份架构文档“交给”你的。它是你根据代码、测试、运行轨迹和历史决策逐步重建出来的。成熟维护者的能力，不是一次性记住整个仓库，而是能够在有限时间内建立一个足够准确、能够指导当前变更、可以被证据验证的局部系统模型。

一、先读懂实验条目的共同结构

这六项虽然主题不同，但句法高度一致。每项都包含：

一个尚未被证明的假设

例如 Session Adapter 能隔离历史、数据库与 outbox 能共同提交、同一 documentId 能受控更新。

一个最小实验边界

只搭出足以验证假设的系统切片，不先完成全部产品功能。

可观察的通过标准

不是“感觉可行”，而是看不到越权内容、没有重复记录、重启后能恢复、延迟和 token 在预算内。

一个实施闸门

原文要求“在对应实现前完成”，意思是后续代码不得建立在未经验证的地基上。

因此，阅读任何技术实验时，先把它改写为：

我们准备依赖假设 H 完成功能 F。
如果 H 不成立，设计 D 将被推翻或出现严重故障 E。
所以先构造最小实验 S，观察指标 O。
通过后采用 D；失败则切换到备选方案 A，或者把能力登记为阻断。
实验计划不是实现步骤的缩写。它是一组“决策所需证据”的清单。理解这一点后，D-01～D-06 就不再是六个莫名其妙的附加任务，而是六个不同类型的架构风险。

二、D-01：双 AgentSession 隔离——“两个 Agent”不能只是两个名字

1. 需求表面上说了什么

系统里存在两个不同职责的 Agent：一个处理内容，一个处理关联。普通需求文档可能只写“分别由两个子 Agent 完成”。但设计者必须继续问：

  • 它们是否拥有不同的会话历史？
  • 它们分别能看见哪些数据？
  • 重启后怎样恢复各自状态？
  • 主 Agent 是否仍偷偷承载了所有大内容，从而让所谓拆分失去意义？

2. “会话隔离”至少有三层

隔离层次要防止什么如何观察
历史隔离内容 Agent 的消息被关联 Agent 自动继承，导致上下文污染恢复两个会话后，分别检查消息序列和摘要
数据可见性隔离Agent 通过工具或提示得到职责外数据为两个会话使用不同输入与工具权限，做越权读取测试
持久化隔离重启、检查点恢复或 session id 混用后串线保存、终止进程、恢复，再核对 task/session 映射

原文的两个标准非常具体：

  • 内容会话看不到候选目录；
  • 关联会话看不到原始来源，只看到合法文档。

这不是简单的“不要在提示词里告诉它”。若原始数据仍被放进同一共享历史，或者两个 Agent 调用同一个不做权限过滤的读取工具，那么模型即使暂时没有复述，也不能称为隔离。真正的设计需要在数据进入模型之前建立边界。

重要区别：上下文隔离不自动等于安全隔离。若威胁模型包括恶意提示、越权工具调用或敏感信息泄漏，只分开聊天历史远远不够，还要在工具权限、查询过滤、凭证和审计上隔离。

3. 为什么要求“主会话无大内容”

如果主会话先读完所有原始来源、候选目录和两个子任务的全部过程，再把一部分转交给子 Agent，那么系统虽然有三个会话，计算和风险仍集中在主会话：

  • 主会话 token 持续膨胀；
  • 本应隔离的信息已经在主会话汇合；
  • 主会话摘要错误会同时污染两个分支；
  • 恢复主会话成为整个任务的单点。

“主会话无大内容”说明主 Agent 更像调度器：保存任务标识、阶段、检查点和子会话引用，而不是保存所有工作材料。

4. 为什么实验要求固定模型

如果测试过程中同时更换模型，失败究竟来自 Session Adapter、提示、模型能力还是模型行为漂移就难以判断。固定模型是在控制变量：先验证会话基础设施，再单独评估模型选择。

5. 一次可理解的实验流程

  1. 创建一个 task，并在其下创建 content-session 与 relation-session。
  2. 向内容会话写入原始来源，但不提供候选目录。
  3. 向关联会话写入允许引用的文档集合，但不提供原始来源。
  4. 分别提出诱导问题，确认它们不能复述职责外数据。
  5. 让两个会话各产生不同历史和检查点。
  6. 终止进程后恢复，确认 task 能找到两条独立会话。
  7. 检查主会话只保留调度状态和结果引用。

如果失败，设计者要判断失败属于哪一层：Session Adapter 根本不支持一 task 多 session，持久化模型不能区分它们，还是工具层没有权限过滤。不同失败会导向不同设计，而不是一律“再改提示词”。

三、D-02：无向关联双端版本——一条边为什么会牵动两个文档

1. 无向关系的逻辑对象只有一条

若文档 A 与 B 互相关联，从用户语义看，A—B 与 B—A 是同一关系。所谓 canonical link，是为这条无方向关系定义唯一表示。例如可以把两个 documentId 排序后形成：

left_id  = min(documentA, documentB)
right_id = max(documentA, documentB)
canonical_key = (left_id, right_id, relation_type)

这里的具体字段只是示意。核心不变量是：

对同一对端点和同一关系类型，系统中最多存在一条当前有效的逻辑关联。

如果分别保存 A→B 与 B→A 两行，就必须长期保证两行同时创建、同时删除、属性一致。任何中途失败都会产生半条关系。只保存一条 canonical link，能把“关系事实”的源头统一起来。

2. 为什么仍然要更新两端版本

关系事实只有一条，不等于用户可见结果只影响一端。若 A 的页面展示“相关文档 B”，B 的页面也展示“相关文档 A”，那么新增或删除 link 会改变两个文档的可见表示。原文因此要求：

  • 两端关联修订均增加；
  • 两端 Bundle 和 Markdown 都重建。

这暗示系统可能区分：

  • 源事实：canonical link；
  • 文档修订：记录文档可见状态发生变化；
  • 派生表示：Bundle、Markdown 或其他 serving projection。

一个常见错误是把派生表示当成源事实，直接在 A 的 Markdown 和 B 的 Markdown 里各写一遍关联。这样删除、重建和并发冲突都会变得困难。

3. “并发反向操作”在担心什么

设两个请求几乎同时到达：

请求 1：给 A 添加关联 B
请求 2：给 B 添加关联 A

若应用先检查“有没有”，再插入，两边都可能在检查时看到不存在，然后各自插入，产生重复。安全设计通常需要把唯一性放到数据库约束中，而不是只靠应用层先查后写。PostgreSQL 的唯一约束与 INSERT ... ON CONFLICT 等机制，可以把并发下的唯一结果交给数据库原子裁决。

删除和更新还会涉及锁顺序。假如请求 1 先锁 A 再锁 B，请求 2 先锁 B 再锁 A，两者可能互相等待。原文要求“无死锁”，通常意味着所有事务都按稳定顺序取得两端资源，例如总是先锁较小 documentId 对应的对象，再锁较大的。

需要同时满足的两类规则：
数据库唯一约束防止“重复边”；统一锁顺序防止“两个事务各拿一端、互相等待”。二者解决的不是同一个问题。

4. 这个实验真正验证的不是一个接口

它同时验证一条完整链路：

关联命令输入 A、B
→
事务写 canonical link
→
版本两端 revision 增加
→
异步投影安排两端重建
→
Serving两端最终可见

通过标准必须检查数据库、修订号、任务数量和最终页面，而不是只看 API 返回 200。

四、D-03：核心事务与 outbox——封住“提交成功但后续任务丢了”的缝隙

D-03 是整组实验的可靠性核心。它针对的是一种常见双写：

第一处写：把文档新版本设为 current
第二处写：向队列发送“请重建 Bundle/Markdown”的任务

如果这两处不属于同一个原子提交，就会出现：

  • 数据库已更新，进程在发任务前崩溃：没有人重建投影；
  • 任务已发出，数据库随后回滚：worker 为一个不存在的版本工作；
  • 客户端重试或 relay 重试：同一投影任务被创建多次。

Transactional Outbox 的核心做法是：在同一个数据库事务里同时写入业务变化和一条持久化 outbox 事件。事务提交后，独立 relay/worker 读取 outbox，再投递或创建 projection job。这样“业务状态存在但没有任何待处理记录”的不可恢复缝隙被封住。

原文标准它保护的不变量
commit 前失败无 current 变化事务回滚时，外部不能看到半完成的新版本
commit 后 worker 丢失仍可恢复任务意图已经持久化，可被其他 worker 重放
重复消费只产生一个 projection job消费者具有幂等键或唯一约束
旧 serving 继续可读新投影未完成时，不把稳定旧版本提前撤下

这四条把事务边界、消息交付、幂等处理和无中断发布连成了一个整体。下一篇将专门用完整故障时间线解释。

五、D-04：候选召回预算——不要让大模型为检索层背锅

1. 关联建议通常不是让模型阅读整个知识库

当知识库变大，把所有 tag、node 和文档放进模型上下文既昂贵又不可行。常见流程是：

召回快速找候选
→
重排/过滤提高相关性
→
模型判断选择、解释或提议新节点
→
人工审阅接受或修改

召回层决定模型“有机会看到什么”。如果正确旧节点从未进入候选集，模型只能：

  • 错误选择一个较差候选；
  • 建议创建新节点；
  • 输出“没有合适节点”。

因此“模型频繁建议新节点”未必说明模型太爱创造，也可能说明检索层漏掉已有节点。

2. 为什么要同时测 precision、延迟和 token

指标回答的问题单独优化的危险
候选 precision送给模型的候选中，有多少是真正相关的过低会让上下文充满噪声，模型判断困难
候选 recall正确已有节点有多少被召回过低会制造虚假的“必须新建”
延迟真实规模下用户要等多久只追求精度可能采用无法交互的慢方案
token候选描述占多少上下文与成本扩大候选数会挤压原文、推理和输出空间

原文只明确写了 precision、延迟和 token，没有明确写 recall；但“若模型频繁建议新节点，先修召回”本身表明设计者关心召回缺失。这里应在正式实验文档中把指标定义补齐，例如：

  • 测试集怎样建立；
  • 正确候选是否可能不止一个；
  • 测 precision@k、recall@k 还是人工可接受率；
  • 知识库规模和 tag/node 分布；
  • 延迟的 p50、p95 预算；
  • 平均与上限 token。

3. 为什么“不提高新节点上限”是一条设计原则

若检索坏了，允许模型创建更多新节点，会把短期失败变成长期数据污染：同义节点越来越多，召回更困难，模型更容易继续新建。正确修复顺序应是：

先检查已有正确节点是否进入候选
→ 再检查候选描述是否足以辨认
→ 再检查模型选择能力与提示
→ 最后才讨论新节点策略

六、D-05：ReviewWorkspace 独立构建——用假后端检验真正的模块边界

1. “前端可独立运行”不是指能打开一个空页面

原文要求在不启动 InnoSpark 的环境中，使用 fake ReviewApi 完成内容预览、tag/related/node 审阅、ETag 冲突和发布确认。这是在验证：

  • ReviewWorkspace 是否只依赖一个明确的 API 契约；
  • 业务规则是否被偷偷放在主系统页面或内部数据库访问中；
  • 错误状态是否也是契约的一部分；
  • 未来能否复用、单独测试或替换宿主。

Fake API 的价值不是“省得先写后端”，而是迫使团队说明接口的完整语义。若前端必须调用十几个未公开内部函数、读取主进程内存或依赖某个全局状态，fake 很快就会暴露边界不成立。

2. 为什么 ETag 冲突必须进入独立实验

典型场景是：

  1. 审阅者甲打开版本 v5；
  2. 审阅者乙也打开 v5，并先发布修改，服务端变成 v6；
  3. 甲仍基于旧 v5 提交。

若服务端无条件接受，甲会覆盖乙的更新，形成 lost update。HTTP 的 ETag 与 If-Match 可以表达乐观并发控制：客户端提交时带上自己读取到的版本标记；若服务端当前标记不匹配，返回 412 Precondition Failed，而不是静默覆盖。

重点不是记住状态码：前端必须把冲突当作正常业务分支，向用户展示“当前内容已变化”，提供刷新、比较或重新应用修改的路径。只在后端返回错误而前端弹出“发布失败”，仍然没有完成设计。

3. 独立构建验证了什么解耦

被解耦的东西实验怎样证明
UI 与真实后端进程只启动静态前端和 fake API 仍能跑完整流程
UI 与数据库结构前端只使用 API DTO，不认识内部表
审阅流程与宿主应用导航可通过独立入口加载 workspace
成功路径与错误路径fake 可稳定模拟冲突、校验失败和发布确认

若实验成功，后端可以稍后实现真实 ReviewApi，前端则以契约测试保证二者对齐。若失败，应先修边界，而不是把前端“临时嵌进去”。

七、D-06：L2 受控更新——同一个 documentId 到底怎样表示“新版本”

这项最依赖项目内部上下文。我们只知道它要求根据 Stage 0 S-09 的实际能力，在三条路中选择：

  • upsert；
  • 版本化 manifest pointer；
  • 记录为 capability 阻断。

并且 P0 环境必须证明：同一 documentId 更新后，不会出现新旧两个活跃来源。

1. 三条路线分别意味着什么

路线一般含义优点主要风险
Upsert同一逻辑键存在则更新，不存在则插入调用者语义简单，活跃记录可保持唯一底层是否真的原子、历史版本放在哪里、缓存如何失效
版本化 manifest pointer内容版本不可变，另有一个指针声明当前活跃版本保留历史、回滚清晰、构建可先完成再切换指针所有读取路径必须遵守指针；切换和清理需设计
Capability 阻断确认底层当前不能安全更新，把能力列为阻塞而非伪装完成诚实地保护数据正确性功能延期，需要替代流程或依赖方改计划

2. “两个活跃来源”为什么危险

假设 documentId=42 的旧内容与新内容都被检索层视为 active：

  • 搜索可能同时返回两份相似文档；
  • 模型可能引用旧版本，或把两份内容当成两个来源；
  • 关联、标签和统计会分裂；
  • 用户无法判断哪一份是正式版本；
  • 后续更新可能继续复制，形成版本污染。

所以需要明确不变量：

对每个逻辑 documentId，在任何对外可读时刻，最多有一个被认定为 current/active 的来源；历史版本可以存在，但必须与活跃读取语义分离。

3. 为什么要在真实 P0 环境证明

本地 mock 能证明调用代码按预期执行，却不能证明外部系统的实际更新语义。真实环境可能：

  • 把更新实现为新增对象；
  • 异步删除旧索引，存在较长重叠窗口；
  • 缓存旧版本；
  • 只按内部对象 id 而非 documentId 唯一；
  • 不同查询入口使用不同“active”过滤。

因此 D-06 本质上是外部能力验证。若 S-09 没有证明所需能力，设计文档不能用“应该支持”替代证据。

八、六个实验怎样互相依赖

它们不是六个完全独立的待办。可以把依赖理解为三条链：

Agent 工作链D-01 会话隔离 → D-04 为关联 Agent 提供可控候选 → D-05 由人审阅 Agent 结果
数据正确性链D-02 canonical link 与双端版本 → D-03 可靠地安排双端投影 → D-06 确保下游来源只激活一个版本
模块边界链D-01 证明 Session Adapter 边界 → D-05 证明 ReviewApi 边界 → D-06 证明外部 L2 能力边界

若要排实施顺序，不应只按编号机械执行，而应看哪一项的失败会推翻最多下游设计。通常会话能力、核心数据不变量与外部更新能力属于高影响地基；界面细节和模型提示可以在边界稳定后迭代。

九、怎样把这组实验写得让项目负责人也能看懂

原条目对实现者很紧凑，但缺少背景。推荐每项补成下面结构：

编号与标题
关联需求：保护哪条用户能力或系统承诺
现有证据：Stage 0 已经证明了什么
未决风险：仍不知道什么，最坏后果是什么
候选设计：准备采用什么，以及备选方案
实验环境：哪些是真实组件，哪些是 fake/mock
步骤：怎样构造最小验证
通过标准：每一条如何测量和记录
失败解释：不同失败分别说明什么
决策规则：通过/失败后采用哪条路线
下游阻塞：哪些实现不得提前开始
证据归档：代码、日志、数据集、结论放在哪里

以 D-05 为例的可读改写

关联需求：审阅模块应当可以独立开发和复用，不依赖 InnoSpark 主进程内部状态。

风险：现有 UI 设想可能隐含读取主系统内部对象，导致所谓独立模块实际上无法脱离宿主。

实验：只启动 ReviewWorkspace 和一个按照 ReviewApi 契约实现的 fake server。

通过标准：完成内容预览、tag/related/node 修改、模拟 ETag 冲突、确认发布；浏览器网络请求中不得出现契约之外的内部接口。

决策：通过则冻结第一版 ReviewApi 契约并分别开发前后端；失败则先修改模块边界，不进入主系统集成。

这样写，读者即使不知道前端框架，也能判断实验是否必要、证据是否充分、失败后是否真的会改变设计。

十、自检题与参考答案

问题 1：为什么把两个 Agent 放在两个提示词中，不足以证明会话隔离？
参考答案

因为隔离还涉及历史持久化、工具权限、数据进入模型前的过滤、task/session 映射和重启恢复。提示词只是模型行为约束，不是完整的数据与权限边界。

问题 2：canonical link 与“两端都显示关联”是否矛盾？
参考答案

不矛盾。canonical link 是唯一源事实；A、B 两端的列表、Markdown 和 Bundle 可以是由同一事实构建的两个派生表示。

问题 3：为什么数据库唯一约束和统一锁顺序都需要？
参考答案

唯一约束防止并发创建重复逻辑记录；统一锁顺序降低两个事务互相持锁等待的死锁风险。它们解决不同故障。

问题 4：模型频繁创建新节点时，为什么先查召回？
参考答案

模型只能从可见候选中选择。若正确旧节点没被召回，模型的新建建议可能是检索缺失造成的假象；直接放宽新建会污染知识库并进一步恶化召回。

问题 5：fake ReviewApi 能证明真实后端正确吗？
参考答案

不能。它主要证明前端可依赖明确契约独立运行，并帮助完善成功与错误语义。真实后端仍需契约测试、集成测试和端到端测试。

问题 6：D-06 失败时为什么“记录能力阻断”也是合格结论？
参考答案

Spike 的目标是获得真实决策证据，不是强迫预设方案通过。若底层不能保证单一活跃来源，诚实阻断比以不可靠实现伪装完成功能更有价值。

本篇结论

D-01～D-06 分别验证了会话边界、关系与版本不变量、异步可靠性、检索质量预算、前后端契约边界和外部更新能力。它们共同说明：设计文档中的实验不是“多做一些测试”，而是在大规模实现前确认最可能推翻架构的假设。

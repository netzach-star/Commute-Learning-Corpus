先说结论： 你看到的那一段并不只是“设计组件怎么连接”，而是在规定：哪些高风险假设必须先通过小规模实验，才能允许后面的正式实现开始。它属于设计文档里的风险验证计划，也可以称为技术实验计划或 Spike 计划。

当你和 AI 讨论需求时，文字通常仍然接近人的生活语言：

  • 用户希望编辑文档关联；
  • 系统应当保存历史；
  • 两个 Agent 分别处理内容和关联；
  • 前端应当可以独立使用；
  • 更新知识库后不应出现重复内容。

这些句子容易理解，因为它们描述的是你想得到的能力。然而一旦进入设计阶段，问题就变了：

  • “两个 Agent 分别处理”是否真的意味着两个互不共享历史的会话？
  • 一条无向关联在数据库中保存一份还是两份？
  • 两个人同时从两个方向添加同一条关联会发生什么？
  • 数据库提交成功，但负责更新 Markdown 的后台进程死掉了，系统如何恢复？
  • 同一个文档更新后，检索系统会不会把新旧版本都当成活跃来源？

需求文档往往没有回答这些问题，因为它们不是用户目标本身；但如果设计阶段不回答，代码会用某种偶然方式替你回答。所谓“实现细节”，很多时候并不细：它会决定数据是否丢失、并发时是否重复、失败后能否恢复，以及将来还能不能改。

本文中心句： 设计不是把需求翻译成类、接口和数据库表；设计是在真正写大量代码之前，系统地决定边界、责任、数据、状态、失败、验证和演进方式。

一、一个项目至少有五层问题，而不是只有“需求”和“代码”

你之所以感到需求文档突然变成了另一种语言，一个重要原因是：AI 把中间几层压缩掉了。完整的软件工作通常可以拆成下面五层。它们未必分别对应五个文件，但对应五种不同的问题。

1. 背景与问题现实中到底发生了什么？为什么值得做？谁在什么场景下遇到什么困难？
↓ 把现实问题收束为可交付目标
2. 需求与验收系统必须提供什么能力？哪些不做？怎样证明用户目标已经满足？
↓ 把“想要什么”转化为“系统必须保证什么”
3. 设计与决策系统边界、组件职责、数据模型、状态、失败处理、权限和演进方式怎样安排？
↓ 对仍然不确定的高风险部分先做实验
4. 技术验证与实现关键方案是否可行？正式代码按什么顺序实现、测试和集成？
↓ 在真实环境中逐步放量并持续观察
5. 发布与运行怎样迁移旧数据、灰度上线、监控故障、回滚并长期维护？

1. 需求不是“所有细节的总和”

需求的核心任务是确定外部可观察的承诺。例如：

需求表达：
用户在文档 A 与文档 B 之间添加无向关联后，无论从 A 还是 B 查看，都应看到同一条关联；重复添加不应产生两条记录。

这句话已经比“支持文档关联”严格很多，但它仍然没有决定：

  • 数据库保存一条 canonical link，还是分别保存 A→B 与 B→A；
  • 文档页面中的关联列表是实时查询，还是提前构建好的投影；
  • 更新关联时是否产生文档修订；
  • 并发写入由数据库唯一约束、应用锁还是分布式锁处理。

这些都属于设计空间。多个设计可能满足同一个需求，但它们的复杂度、性能、故障模式和演进成本不同。

2. 接口与组件只回答设计问题的一部分

组件图能告诉你“系统有哪些大块”，接口能告诉你“这些大块允许怎样互相调用”。但一个系统即使组件图画得很漂亮，也可能存在：

  • 同一对象在不同组件中有两套互相矛盾的状态；
  • 数据库成功而搜索索引失败，产生永久不一致；
  • 后台任务被重复消费，生成多份结果；
  • 新版本上线后无法读取旧数据；
  • 服务重启后会话历史丢失；
  • 出现故障时没有日志、指标和追踪信息，无法定位。

这些问题不主要来自“接口签名写错”，而来自状态、时间、并发和失败。因此真正的设计文档必须超出静态组件图。

二、为什么项目要分阶段推进

“分阶段”常被误解为项目管理者喜欢制造流程，或者把一个本来能直接完成的任务拆成许多会议。确实存在过度流程化，但合理的阶段不是为了增加仪式，而是为了管理三种会不断变化的东西：

信息

早期你只知道问题和目标，后来才逐渐知道数据规模、接口限制、异常情况和真实用户行为。

风险

某些错误只影响一段代码，另一些错误会破坏数据模型、发布架构或全部历史内容。

修改成本

想法阶段改一句话很便宜；大量代码、数据和外部集成建立后，再改同一决定会牵动更多对象。

1. 阶段的本质是“在下一种成本发生前，先解决对应问题”

可以把项目推进理解为一系列逐渐变贵的承诺：

问题确认承诺值得做
→
需求基线承诺做什么
→
架构设计承诺怎样组织
→
技术实验证明关键假设
→
正式实现投入完整工程成本
→
发布运行承担真实数据与用户风险

每进入下一阶段，系统都会增加新的“沉没结构”：代码、测试、数据、接口依赖、用户习惯和运维配置。阶段门的意义是：在这些结构大量形成前，检查上一层最危险的问题是否已经得到足够回答。

不是所有问题都必须在前期完全解决。 软件设计不可能消除全部不确定性。阶段化的目标是把问题分成：现在必须决定的、可以通过实验验证的、可以推迟到实现时决定的，以及故意保留为开放点的。把所有细节都提前决定，同样会造成浪费。

2. 阶段必须有“进入条件”和“退出证据”

如果阶段只有名字，没有进入条件、产物和验收标准，它就只是日历上的标签。例如“进入开发阶段”不能只表示“我们讨论得差不多了”，而应有类似的证据：

  • 核心用户流程已经明确，并写成可验收行为；
  • 系统边界和不做范围已确认；
  • 关键数据对象及其生命周期已定义；
  • 高风险技术假设已经通过 Spike，或被明确登记为阻断项；
  • 主要故障场景和恢复策略已有答案；
  • 实现顺序不会要求后续推翻基础数据结构。

你提供的原文中，“每项必须在对应实现前完成”和每个 D 项后的“通过标准”，就是典型的阶段门。它在说：

这些能力目前还不能仅凭设计者的判断认定可行。先用受控实验取得证据；实验不通过，对应实现不得继续。

3. 为什么不直接在正式代码中边做边验证

当然可以边写正式代码边发现问题，但风险较高时，这种做法会把三个目标混在一起：

  1. 探索方案是否可行；
  2. 建立可维护的正式结构；
  3. 满足完整产品需求和异常处理。

探索代码为了快速获得答案，可以使用假数据、固定参数和临时接口；正式代码则需要长期维护、完整错误处理、可观测性和兼容性。如果一开始就要求探索代码同时达到正式质量，验证会变慢；如果把临时探索代码直接当作正式实现，又会把大量偶然决定固化进系统。

因此，合理的流程通常是：

提出高风险假设
→ 设计最小实验
→ 规定通过/失败标准
→ 运行实验并记录证据
→ 据此选择、修改或放弃正式方案
→ 再进入完整实现

三、从需求到设计，除了接口和组件，还必须加上什么

下面这部分是本文最重要的“设计地图”。不是每个项目都要建立同样长的文档，但设计者必须对这些问题有意识；项目越涉及持久化数据、多 Agent、并发、后台任务和多个展示投影，越不能只写组件与接口。

1. 目标、范围与设计约束

设计文档开头仍然要重述目标，但不是复制需求全文，而是明确本设计负责解决什么，不负责什么，以及有哪些已经不能随意改变的条件。

需要记录为什么存在缺失后的典型问题
本次设计目标让所有技术选择围绕同一结果，而不是各自优化文档写得很复杂，却没有覆盖最关键用户流程
非目标主动限制范围，防止每个相关问题都被吸进当前版本项目不断扩张，无法判断何时完成
既有资产说明哪些能力已经交付，避免重复建设原文强调“Stage 0 不重做”，正是在保护已有投入
技术与组织约束记录必须兼容的数据库、部署环境、权限和团队能力设计理论可行，但不适用于实际环境
假设与未知项区分事实、暂定判断和待验证问题推测被逐渐当成既定事实

2. 系统上下文与边界

组件设计之前，应先回答：系统外部有哪些人和系统？谁调用谁？哪些数据由本系统负责，哪些只是暂时读取？

例如原文提到 ReviewWorkspace、ReviewApi、InnoSpark、知识库与两个 Agent 会话。仅从片段无法知道它们的完整定义，但可以看出设计者关心一个边界问题：

D-05 的核心不是“做一个前端页面”。
它要证明审阅工作区能够只依赖规定好的 ReviewApi 运行，而不是偷偷依赖主系统的内部状态。只有这样，前端模块才真正独立、可测试、可复用。

系统边界存在的理由是控制依赖。边界不清时，一个模块表面上独立，实际启动、登录、数据格式和错误处理都依赖另一个巨大系统，最终无法单独测试或替换。

3. 核心概念与统一词汇

设计文档应建立术语表，尤其是项目内部名词。比如：

  • AgentSession 到底是模型的一次调用、持续会话、数据库记录，还是三者组合？
  • Bundle 包含哪些文件和元数据？
  • current 是数据库指针、当前修订号，还是当前发布对象？
  • projection job 是更新 Markdown、HTML、搜索索引，还是统一的派生视图任务？
  • L2、P0、S-09 在当前片段中没有定义，必须回到项目术语表或 Stage 0 文档查找。

没有统一词汇时，同一个词可能在不同章节中代表不同对象。AI 尤其容易在长文档中保持语言相似，却悄悄改变对象含义。

4. 数据模型、所有权与生命周期

接口描述一次调用，数据模型描述系统长期保存什么。设计需要明确：

  • 有哪些核心实体和值对象；
  • 每个对象的唯一标识是什么；
  • 谁有权创建、修改、发布和删除；
  • 对象是否可变，还是每次修改产生新版本；
  • 什么叫草稿、已发布、当前版本和历史版本；
  • 派生数据能否重建，源数据在哪里。

D-02 中的“一条 canonical link”和“两端关联修订均增加”，就是数据模型与生命周期决定：

  • 逻辑上 A—B 是一条无向关系，所以源数据只保存一条规范记录；
  • 但 A 和 B 各自展示的关联列表都发生变化，所以两端的派生版本都要更新。

如果不先决定“哪一个是源数据，哪一些是投影”，系统很容易保存三份看似相同的数据，后来却不知道以哪份为准。

5. 关键流程、状态机和不变量

静态组件图不说明一个对象怎样从开始走到结束。因此设计文档还要描述关键流程：

候选生成
→ 用户审阅
→ 发生冲突时重新加载或合并
→ 用户确认发布
→ 核心事务提交
→ 后台重建 Bundle / Markdown / 索引
→ 新版本成为 serving current

与此同时，要写出必须始终成立的不变量。不变量是设计中非常有力量的表达，因为它比“正常情况下怎样做”更严格。

不变量： 系统无论经历怎样的合法操作、并发和可恢复故障，都必须保持为真的条件。

结合原文，可以识别出一些候选不变量：

  • 同一对文档之间最多存在一条活跃 canonical link；
  • 内容会话不能读取关联候选目录；
  • 关联会话只能读取经过允许的文档，而不是原始来源；
  • 事务提交前失败，不得改变 current；
  • 同一个事件被重复消费，不得产生多个等价 projection job；
  • 更新 documentId 后，不得同时存在两个活跃来源。

一旦不变量明确，接口、数据库约束和测试都能围绕它们设计。

6. 一致性、事务、并发与幂等

这是很多需求文档不会提到、但设计文档必须面对的部分。因为现实执行不是一条永不失败的顺序：

  • 两个请求可能同时到达；
  • 同一消息可能被投递两次；
  • 数据库提交成功后进程可能立刻崩溃；
  • 后台派生任务可能比主事务晚几秒甚至几分钟；
  • 用户打开页面时可能看到旧版本。

设计需要明确：

问题要作出的设计决定
哪些修改必须一起成功或一起失败？事务边界
多个请求修改同一对象如何协调？乐观并发、ETag、数据库约束或锁
同一个任务执行两次是否安全？幂等键、唯一约束和去重规则
主数据与派生视图暂时不一致是否允许？一致性模型和可接受延迟
提交后后台任务丢失如何补回？outbox、重试和对账机制

D-02、D-03 和 D-05 都在处理这一组问题，而不是单纯验证接口能否调用成功。

7. 失败模型、恢复与降级

很多初学者的设计只描述成功路径：

收到请求 → 保存数据 → 更新页面 → 完成

真正的系统设计还要问每个箭头之间失败怎么办：

  • 在保存前失败：是否可以直接重试？
  • 保存成功但响应丢失：客户端重试会不会重复写入？
  • 新投影构建失败：旧版本能否继续提供服务？
  • 服务重启：会话能否恢复，还是从检查点重建？
  • 依赖系统不可用：当前功能是阻断、只读还是降级？

D-01 要求重启后恢复或重建；D-03 要求 worker 丢失后仍可恢复，并保持旧 serving 可读；这些就是恢复和降级策略。

8. 非功能需求与容量预算

“功能正确”并不等于“系统可用”。设计还要规定：

  • 延迟上限；
  • 吞吐与并发规模；
  • 存储增长；
  • 模型 token 成本；
  • 召回率、精确率和误建议比例；
  • 可用性、恢复时间和数据丢失容忍度。

D-04 的“precision、延迟和 token”就是三个不同维度的预算。如果只要求模型“能生成候选”，系统可能以极高 token 成本生成大量错误候选。技术上能运行，产品上仍不可接受。

9. 安全、权限与信息隔离

在多 Agent 系统中，“不同 Agent 使用不同提示词”不等于隔离。设计必须说明：

  • 每个 Agent 能访问哪些数据源；
  • 上下文由谁组装；
  • 会话历史是否共享；
  • 工具权限是否不同；
  • 敏感原始来源能否进入不需要它的会话；
  • 日志和检查点中是否泄漏不应保存的内容。

D-01 的验收标准本质上是一个信息流安全测试：内容会话和关联会话必须拥有不同的可见世界，而且这种隔离在恢复后仍成立。

10. 可观测性与运维

设计文档应说明出了问题怎样知道：

  • 哪些日志记录一次任务从创建到完成；
  • 哪些指标反映 outbox 堆积、投影失败、重复消费和召回质量；
  • 怎样追踪一个 documentId 在数据库、Bundle、Markdown 和检索源中的版本；
  • 怎样人工重放、对账或修复。

可观测性不是上线后再随手加日志。若核心对象没有稳定 ID、状态转换没有事件记录，后来很难补出完整追踪链。

11. 迁移、兼容、发布与回滚

一个新设计通常不是在真空中启动。原文明确说“Stage 0 不重做”，这意味着 V2 必须建立在已有能力之上。因此需要写明：

  • 旧对象怎样迁移到新模型；
  • 新旧版本是否需要同时读取；
  • 发布顺序是先改数据库、再上服务，还是相反；
  • 失败时回滚代码是否也要回滚数据；
  • 旧 serving 为什么仍可读，何时切换 current。

D-06 要求“同一 documentId 更新后不会产生新旧两个活跃来源”，就是发布后数据一致性的验收条件。至于 L2、P0 和 S-09 的确切含义，当前片段没有提供，不能仅凭名称判断。

12. 验证计划、开放问题与决策记录

最后，设计文档必须诚实地区分：

  • 已经确定的设计；
  • 有多个候选方案但尚未选择的部分；
  • 必须做实验才能知道的部分；
  • 当前能力不足而被登记为阻断的部分；
  • 已经做出的重要取舍及其理由。

这就是为什么原文在 D-06 中允许三种结果：upsert、版本化 manifest pointer，或者记录为 capability 阻断。一个技术实验不一定要证明原方案正确；它也可以产生“当前环境做不到，因此必须调整范围”的合法结论。

四、技术实验 Spike 为什么存在

Spike： 为回答一个具体技术未知项而进行的有时限、小范围实验。它的主要产物不是可交付功能，而是证据：某方案能否工作、在什么条件下工作、有哪些限制，以及正式设计该如何调整。

1. 什么问题值得做 Spike

不是任何不确定性都需要实验。适合 Spike 的通常是以下问题：

  • 一旦判断错误，会推翻核心数据模型或架构；
  • 仅靠阅读文档无法确认真实行为；
  • 依赖已有系统的具体能力，而不是抽象上“理论可行”；
  • 涉及并发、崩溃恢复、性能或第三方限制；
  • 正式实现成本很高，但最小验证成本较低。

例如“双 AgentSession 能否真正隔离并分别恢复”，就不能只根据 Session Adapter 的接口名称推断。必须创建两个会话、注入不同信息、重启并恢复，观察是否真的保持隔离。

2. 一个合格 Spike 包含什么

  1. 问题：我们到底不知道什么？不要写成宽泛的“研究会话系统”。
  2. 风险：这个未知项为什么会阻塞后续设计或造成昂贵返工？
  3. 最小环境：使用哪些真实组件，哪些部分可以用 fake 或固定数据代替？
  4. 操作步骤：怎样触发正常、并发、失败和恢复场景？
  5. 通过标准：哪些可观察结果出现才算方案成立？
  6. 失败后的决策：换方案、缩范围、补能力，还是登记阻断？
  7. 证据：代码、日志、测试结果、测量数据和结论保存在哪里？

3. Spike 与普通测试有什么区别

维度Spike正式测试
目标消除未知、支持设计决策持续验证已经承诺的行为
发生时间通常在对应实现前实现过程中及之后持续运行
代码质量可临时，但必须足以产生可信证据应稳定、自动化、可长期维护
结果可能证明方案不可行失败通常表示实现偏离规格或发生回归
范围围绕一个高风险问题的最小切片覆盖单元、集成、端到端和非功能要求
常见误区： Spike 不是“先随便写一版，以后再重构”的许可证。它必须有明确问题和结束条件。没有决策问题、没有通过标准、也没有证据记录的“探索”，很容易变成无人敢删的半成品。

五、把你提供的 D-01～D-06 翻译成人话

材料边界： 本节只依据你提供的片段解释这些实验在设计中的职责。片段没有定义 Stage 0、V2、V4、InnoSpark、L2、P0、S-09、Bundle 等对象的完整含义，因此下文不会擅自补成确定架构。
实验它真正担心什么为什么不能等正式实现后再发现实验通过后允许什么继续
D-01
双 AgentSession 隔离		 两个 Agent 是否真的拥有互相隔离的历史、数据可见性和恢复状态，而不是表面上分成两个名字 若底层 Session Adapter 不能隔离，整个多 Agent 权限模型和上下文设计都要推翻 继续实现内容 Agent 与关联 Agent 的独立工作流
D-02
无向关联双端版本		 一条关系如何只保存一次，却可靠地反映到两个文档的版本与投影中；并发反向操作会不会重复或死锁 这直接决定关系的数据模型、事务边界和锁顺序，晚发现会影响大量代码与历史数据 继续实现关联增删、文档修订和双端重建
D-03
核心事务与 outbox		 数据库状态已经提交，但后台投影任务丢失或重复时，系统能否恢复且不产生重复任务 这是数据正确性基础；若提交与任务投递之间存在不可恢复缝隙，系统会永久不一致 继续实现异步 Bundle、Markdown 或其他投影构建
D-04
候选召回预算		 在真实规模下，候选检索是否足够准、足够快、token 成本可接受；模型为何频繁创造新节点 若召回层质量太差，后面调大模型提示或放宽新节点上限只会掩盖根因并扩大成本 确定召回策略和模型可见候选集，再实现稳定关联建议
D-05
ReviewWorkspace 独立构建		 审阅前端能否仅依赖公开 ReviewApi 完成预览、审阅、冲突和发布，而不耦合主系统内部 若接口边界不够，前端完成后才发现必须嵌入主项目，会推翻模块化与复用目标 继续独立开发和测试审阅工作区
D-06
L2 受控更新		 已有系统到底支持怎样的同 documentId 更新语义，更新后能否保证只有一个活跃来源 若能力被错误假设，发布后检索可能同时读取新旧版本，形成难以察觉的重复和污染 选择 upsert、版本指针方案，或明确登记能力阻断

为什么这些实验放在“对应实现前”，而不是项目最开始一起做

原文写的是“每项必须在对应实现前完成”，而不是“项目启动时一次性完成全部实验”。这体现了一个重要原则：

风险验证也要按依赖顺序进行。 太早做实验时，相关设计尚未稳定，实验对象和标准可能不断变化；太晚做则已经投入大量实现成本。最合适的时间通常是：需求与候选设计已经足够清楚，但正式实现尚未依赖该假设。

因此，“分阶段”不是所有事情严格串行。实际项目中，需求细化、设计、Spike 和局部实现可能交错进行；关键是不能让一个尚未验证的高风险假设悄悄成为后面大量工作的地基。

六、怎样阅读 AI 突然交给你的设计文档

当 AI 从需求跳到大量技术名词时，不建议逐个名词搜索。先恢复文档的逻辑骨架。对任何一节，你可以连续问下面七个问题。

  1. 这节在保护哪一条需求？ 找不到对应需求，说明可能是过度设计，或者需求文档缺项。
  2. 它担心哪一种失败？ 数据丢失、重复、越权、延迟、成本、耦合，还是无法迁移？
  3. 它要决定什么？ 数据模型、事务边界、接口、部署方式，还是能力是否存在？
  4. 哪些是项目内术语？ 要求 AI 给出定义和来源章节，不要接受循环解释。
  5. 输入、操作、输出是什么？ 把抽象段落改写成一次完整流程。
  6. 通过标准如何被观察？ 是数据库记录、日志、页面行为、性能数据还是重启后的状态？
  7. 失败后改变哪个设计？ 如果失败也不影响任何决定，这个实验可能没有价值。

1. 让 AI 为每一节补“为什么存在”

你可以要求设计文档中的每个重要章节使用统一格式：

问题：当前存在什么不确定性或风险？
关联需求：它保护哪条用户目标或系统约束？
设计决定：我们准备怎样处理？
替代方案：还有哪些可行路径，为什么没选？
失败场景：什么情况下会出错？
验证方式：怎样证明该决定成立？
下游影响：哪些组件和实现依赖这个结论？

这种格式并不要求你先懂所有技术。即使不理解 outbox 的实现，你也能先理解：它要封住“数据库已经提交，但任务通知丢失”的缝隙。

2. 要求先给“阅读地图”，再给技术细节

一份适合项目负责人阅读的设计文档，应该先给出：

  • 本次设计解决的三到五个核心问题；
  • 系统上下文图；
  • 一条端到端主流程；
  • 核心数据对象及其关系；
  • 最重要的不变量；
  • 仍未解决的高风险问题与 Spike；
  • 推荐阅读顺序。

之后再展开数据库表、接口字段和并发细节。没有地图时，读者会在每个局部段落里理解句子，却不知道它们为什么同时存在。

3. 区分“我不懂术语”和“文档本身缺失”

以你提供的片段为例，以下两种情况必须分开：

情况处理方法
outbox、ETag、upsert 是行业技术概念可以要求从问题、机制和例子开始解释
L2、P0、S-09 是项目内部代号，但片段未定义不能靠常识猜；必须回到项目文档查定义或要求作者补交叉引用

这很重要：不是所有“看不懂”都应该归因于读者基础不足。设计文档若使用内部术语却不提供定义与链接，本身就是文档缺陷。

七、一份同时适合你和实现者阅读的设计文档结构

下面是一份推荐骨架。小项目可以合并章节，但不应在没有判断的情况下删掉相应问题。

章节要回答的问题主要读者
1. 摘要与阅读地图这次设计解决什么，先看哪几节所有人
2. 背景、目标与非目标为什么做、做到哪里停止项目负责人、产品、开发
3. 需求映射与验收每个设计问题保护哪条需求项目负责人、测试
4. 既有系统与约束Stage 0 有什么，什么不能重做架构与实现者
5. 术语与核心概念Session、Bundle、current 等究竟是什么所有新加入者
6. 系统上下文与边界外部参与者、系统及数据责任架构、前后端
7. 端到端流程一次任务怎样从输入走到发布所有实现者
8. 数据模型与生命周期保存什么、谁是源、怎样版本化后端、数据、测试
9. 组件与接口职责怎样分配、数据怎样传递实现者
10. 状态、不变量与并发什么必须始终为真，并发怎样处理后端、测试
11. 失败、恢复与降级每一步失败时系统保持什么状态后端、运维
12. 性能、安全与可观测性质量预算、权限和故障定位架构、运维、安全
13. 迁移、发布与回滚怎样从旧系统安全进入新系统开发、运维
14. 技术实验与通过标准哪些假设还需证据，失败后怎样决策项目负责人、实现者
15. 实现阶段与依赖顺序先做什么，哪些工作被什么阻塞项目负责人、开发
16. 开放问题与决策记录还有什么未知，重要取舍为何如此所有维护者

为什么还要写“实现阶段”，设计不是已经结束了吗

架构设计告诉你目标结构，实施计划告诉你怎样安全到达目标结构。两者不同。

例如最终设计需要：

  • 两个隔离会话；
  • canonical link；
  • 事务与 outbox；
  • 独立 ReviewWorkspace；
  • 受控 L2 更新。

但实现不能随意并行。如果会话隔离实验未通过，依赖它的两个 Agent 流程不应大规模开发；如果 canonical link 的并发策略未定，两端版本重建也没有稳定基础。实施阶段需要把设计依赖转化为工作依赖。

架构回答“完成后系统是什么样”，阶段计划回答“怎样以最小返工和可控风险走到那里”。

八、自检题与参考答案

问题 1：为什么“支持无向关联”仍不足以直接指导实现？
参考答案

因为它只说明外部能力，没有决定关系保存几份、唯一标识、并发去重、删除语义、两端版本更新和派生投影重建。多个设计都能满足表面需求，却具有不同故障模式。

问题 2：项目分阶段的核心目的是什么？
参考答案

不是制造流程，而是在代码、数据、集成和用户依赖大规模形成之前，先解决当前最昂贵的未知项。每一阶段都应有进入条件、产物和退出证据。

问题 3：Spike 的产物主要是功能代码吗？
参考答案

不是。Spike 的主要产物是支持设计决策的证据，包括测试代码、日志、测量结果、限制条件和结论。其代码可以被丢弃，结论必须被记录。

问题 4：D-03 为什么不仅是“加一个后台任务队列”？
参考答案

因为真正问题是数据库事务与异步任务之间的一致性缝隙：提交前失败不能改变 current；提交后 worker 丢失仍要恢复；重复消费不能重复生成投影任务；新投影失败时旧 serving 仍应可读。

问题 5：看到 L2、P0、S-09 不懂时，应先搜索行业定义吗？
参考答案

不应直接猜。它们看起来是项目内部代号，当前片段没有定义。应回到术语表、Stage 0 交付文档或相应章节查交叉引用；作者若未提供，就是文档需要补充。

问题 6：接口和组件之外，设计文档最容易被忽略的三类内容是什么？
参考答案

可选答案很多，例如：数据所有权与生命周期；状态、不变量和并发；失败恢复；非功能预算；安全权限；迁移发布；验证计划。关键是说明静态结构无法独自回答时间、状态和失败问题。

九、本篇结论与后续系列

现在可以重新理解你看到的“第 19 节”：它不是突然脱离需求去炫耀技术，而是在尝试把几个可能推翻系统基础的未知项放在正式实现之前验证。问题在于，它直接使用了项目内部名词和技术机制，却没有先给读者提供设计地图、风险来源与术语解释。

从需求进入设计后，至少需要补齐以下内容：

目标、范围与约束
→ 系统边界与统一词汇
→ 数据模型与生命周期
→ 端到端流程、状态机与不变量
→ 一致性、事务、并发和幂等
→ 失败、恢复与降级
→ 性能、安全和可观测性
→ 迁移、发布与回滚
→ 技术实验、验收证据与开放问题
→ 实现阶段和依赖顺序

接口与组件只是其中两项。它们描述系统“静态地由什么组成”；而真正让系统能够在现实中运行的，是对状态变化、并发冲突、局部失败和长期演进的处理。

建议的后续三篇：
  1. 从需求到设计（二）：逐条拆解 D-01～D-06——重点讲 Session 隔离、canonical link、ETag、召回预算和受控更新。
  2. 从需求到设计（三）：事务、outbox、幂等与最终一致性——用一次“发布文档并重建投影”的完整故障过程讲可靠性。
  3. 从需求到设计（四）：怎样审查 AI 生成的设计文档——建立需求追踪、术语检查、不变量检查、故障注入和实施依赖检查表。

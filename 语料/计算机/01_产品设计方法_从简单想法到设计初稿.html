0. 先给出中心结论：设计不是扩写想法

很多计算机项目以一句话开始：

“能不能做一个插件，把已经整理好的语料自动变成 HTML？”

这句话可以是灵感，但还不是需求，更不是产品设计。它里面至少隐藏了七个尚未证明的判断：

  1. 确实存在一群人需要把语料变成 HTML；
  2. 他们当前的做法存在明显成本或质量问题；
  3. 这个问题发生得足够频繁，值得专门做工具；
  4. HTML 是他们真正需要的交付形态，而不只是你熟悉的技术形态；
  5. 自动转换比模板、现有编辑器或人工整理更有优势；
  6. 使用者愿意改变现有流程，把新工具接入工作；
  7. 做成插件并嵌入主系统，是价值最高且代价合理的实现方式。

如果这些判断未经调查就被当成事实，后续工作越认真，反而越可能把一个错误方向做得更完整。代码能够证明“这个方案可以运行”，却不能证明“这个问题值得解决”。

错误路径：想到一个功能 → 补齐更多功能 → 画界面 → 写架构 → 开发 → 找人试用 → 发现用户并不在意。

更可靠的路径：记录初始想法 → 识别隐藏假设 → 调研真实场景 → 定义高价值问题 → 比较多种解决机制 → 验证最危险假设 → 收敛为设计初稿 → 再进入工程设计与开发。

因此，所谓“从一个简单想法构思出完整设计初稿”，本质上不是把一句话写长，而是建立一条从证据到决策的推理链。设计初稿的价值，也不在于看起来详细，而在于任何审查者都能追问：

  • 你为什么认为这个问题存在？
  • 为什么选这类用户和这个场景？
  • 为什么不采用更便宜的替代方案？
  • 你最不确定的地方是什么？
  • 接下来做什么实验，能最快证明你错了？

如果文档无法回答这些问题，它最多是一份方案说明，而不是设计。

1. 为什么“先做出来再说”经常得到低价值产品

1.1 工程问题与产品问题不是同一个问题

工程问题通常问：

  • 这个功能能否实现？
  • 数据从哪里进入，经过哪些模块，再输出到哪里？
  • 接口如何定义，状态如何保存，错误如何处理？
  • 性能、可靠性和维护成本是否可接受？

产品问题则先问：

  • 谁在什么情况下遇到什么困难？
  • 困难给他造成了什么后果？
  • 他现在怎样解决，为什么现有办法不够好？
  • 即使新方案更好，他为什么愿意迁移？
  • 解决这个问题对项目、团队或业务有什么意义？

前者可以在没有用户的情况下讨论，后者不行。工程能力越强的人，越容易犯一个特殊错误：因为自己擅长构建系统，便下意识地把不确定性理解成“实现细节尚未决定”，而不是“问题本身尚未成立”。

1.2 技术可行性会制造一种虚假的进展感

写代码时，进展非常可见：接口接通了、页面出现了、测试通过了、提交记录增加了。相比之下，前期调研经常显得模糊：访谈没有统一答案，用户描述互相矛盾，很多材料无法直接变成功能列表。

于是团队很容易选择心理上更舒服的工作——开发。问题是，开发阶段主要减少的是技术不确定性，而早期项目最危险的往往是下面几种不确定性：

不确定性核心问题错误后果
问题不确定性用户真的有这个问题吗？做出没人需要的功能
价值不确定性问题重要到足以促使用户行动吗？用户觉得“不错”，但不会使用
行为不确定性新方案能进入真实工作流吗？演示时好用，实际中被绕开
可用性不确定性用户能否正确理解并完成任务？功能存在，但学习成本过高
可行性不确定性技术、数据与组织条件允许吗？方案价值高但无法稳定交付
持续性不确定性维护、质量控制和责任边界是否成立？一次演示成功，长期运行失败

如果团队一开始只处理最后两项，前四项就会以“产品价值不高”的形式在项目后期集中暴露。

1.3 前期调研不是为了写一份市场报告

另一个常见误解是：调研就是搜索同类产品、整理行业规模、列一张竞品表。它们有用，但不能替代对真实行为的理解。

你真正需要知道的不是“市面上有没有类似产品”，而是：

  • 使用者在开始任务前拥有什么材料；
  • 任务由什么事件触发；
  • 他按什么步骤完成；
  • 在哪一步停顿、返工、放弃或寻求帮助；
  • 任务完成后，什么结果才算合格；
  • 失败由谁承担，质量由谁判断；
  • 现有工具为什么没有解决这个问题。

调研的目标是改变你的决策，而不是装饰你的文档。如果调研结束后，原始想法、目标用户和方案范围完全没有变化，需要警惕：你可能只是在寻找支持既有想法的材料。

2. 把模糊想法改写成一组可证伪的假设

2.1 不要把初始想法当作结论

收到一个想法后，第一步不是给它取项目名，而是写一张初始假设卡。它的作用是把你脑中混在一起的“观察、推断和方案”拆开。

初始假设卡

目标角色：谁可能使用或受益？
触发场景：在什么具体时刻，他开始处理这件事？
当前任务：他真正想完成什么结果？
当前做法：现在怎样完成？使用哪些材料、工具和协作关系？
疑似困难：哪一步可能慢、贵、难、易错或不可控？
预期后果：如果困难解决，什么指标或行为会改变？
初始方案：你暂时想到的解决机制是什么？
关键假设：哪些判断一旦错误，整个项目就失去价值？
已知证据：目前有什么真实材料支持，而不只是个人感觉？

注意，这张卡允许大量内容写成“未知”。把未知暴露出来，比用听起来合理的话把空白填满更专业。

2.2 把一句功能描述拆成因果链

以“把完整语料转换为适合自学的 HTML”为例，可以暂时写成：

特定用户拥有完整语料
↓
当前制作网页学习材料耗时或质量不稳定
↓
一个受约束的自动排版与交互生成机制能够降低成本
↓
输出仍能满足阅读、教学与维护要求
↓
用户愿意把该机制放入现有工作流并持续使用

这条链上每个箭头都是假设。产品失败不一定是最后的代码有 bug，也可能是：

  • “拥有完整语料的人”并不经常需要 HTML；
  • 真正成本不在排版，而在内容重构与质量审查；
  • 用户需要的是可编辑模板，不是全自动生成；
  • 自动输出看起来漂亮，却不适合独立学习；
  • 接入主项目的维护成本高于节省的时间；
  • 最终决策者不是使用者，而是导师、教师或平台维护者。

只有把因果链写出来，你才知道接下来调查什么。否则所谓“调研”很容易变成漫无目的地看产品和论文。

2.3 给假设排序：先查最致命、最未知的

假设不是一视同仁。可以用两个问题排序：

  1. 如果它是错的，项目会不会失去主要价值？
  2. 我们现在是否缺少可靠证据？

“用户是否真的经常需要该结果”通常比“按钮放左边还是右边”更致命；“生成质量是否能达到最低标准”通常比“以后能否支持更多主题色”更未知。优先研究高致命、高未知的假设。

不要用开发难度决定研究顺序。一个假设很容易实现，不代表它值得先验证；一个功能很难实现，也不代表它具有价值。

3. 第一次发散：研究真实场景，而不是立刻研究功能

设计过程常常需要两次“发散—收敛”。第一次发散的目标是扩大对问题的理解：谁遇到问题、问题如何发生、现有办法为何存在。第二次发散才是探索不同解决方案。英国 Design Council 的 Double Diamond 用 Discover、Define、Develop、Deliver 描述了类似节奏；重要的不是记住四个词，而是避免在还没理解问题时就提前收敛到一个方案。

3.1 先画任务边界

你需要把“用户使用产品”放进更长的任务链中。例如，一个 HTML 生成插件可能只覆盖中间一段：

选题 → 搜集资料 → 写完整语料 → 审核内容 → 生成页面 → 检查公式与移动端显示 → 发布或导入平台 → 收集反馈 → 修订

如果只盯着“生成页面”这一步，会错过三个可能更关键的问题：

  • 输入语料本身缺少结构标记，导致生成不稳定；
  • 真正耗时的是渲染检查和反馈修订，而不是第一次生成；
  • 最终页面需要进入另一个平台，接口与版本管理才是阻塞点。

因此，要先确定研究范围：从哪个触发事件开始，到哪个可观察结果结束。范围太窄会错认问题，范围太宽则无法行动。

3.2 找到不同角色，而不是笼统地说“用户”

一个系统中常有多种角色：

角色关心的结果可能承担的成本
直接操作者任务是否更快、更省心学习和迁移成本
内容作者表达是否准确、可控修改与返工
最终读者是否易读、能学会认知负担与误解
项目负责人交付价值、进度和风险资源和责任
维护者兼容性、稳定性、可扩展性长期维护
决策者或付款者整体收益是否超过投入预算与机会成本

“使用者喜欢”并不等于“系统有价值”。如果维护者拒绝承担接入成本，或者最终读者得不到更好结果，直接操作者觉得方便也未必足够。

3.3 桌面调研：回答环境问题

桌面调研适合回答：

  • 现有解决方案有哪些类型？
  • 行业或项目已经形成哪些惯例和接口？
  • 类似方案通常在哪些环节失败？
  • 有哪些技术、版权、安全、隐私或组织约束？
  • 用户为什么可能已经满足于现有工具？

竞品分析不要只列功能。更有效的是比较它们所服务的任务、目标角色、输入输出、工作流位置和取舍。例如：

替代方案主要优势主要代价适合谁为何仍可能不够
手写 HTML控制力强耗时、依赖前端能力高要求作者难规模化
固定模板填充稳定、可预测表达形式受限内容结构统一者复杂语料适配差
通用大模型直接生成灵活、启动快风格漂移、质量不稳定探索性任务缺少可审查约束
人工设计服务质量上限高成本高、速度慢少量高价值内容难以持续生产

3.4 访谈和观察：回答行为问题

访谈最容易被做成“向别人介绍想法并收集赞美”。这几乎没有证据价值。不要问：

“如果有一个自动生成漂亮 HTML 的插件，你会不会用？”

人们通常愿意礼貌地回答“可能会”。应该问过去发生过的具体事件：

  • 上一次制作类似材料是什么时候？
  • 从拿到语料到最终交付，你逐步做了什么？
  • 哪一步花费时间最多？
  • 上一次出现严重返工是什么原因？
  • 你试过哪些工具？为什么后来不用？
  • 谁判断结果合格？他看什么？
  • 如果这一步做不好，实际后果是什么？
  • 你是否为解决它投入过时间、预算或额外协作？

过去行为比未来承诺更可靠。最好让受访者展示真实材料：输入文档、旧页面、修改记录、报错截图、交付规范。观察“他实际做什么”，而不只听“他认为自己怎么做”。

3.5 调研样本不必很大，但必须有差异

早期目标不是统计推断，而是发现主要模式和反例。三位完全相同背景的同事，可能不如五位处在不同角色、不同熟练度和不同任务频率的人有价值。

要主动寻找否定证据：

  • 谁根本没有这个问题？
  • 谁有问题却不愿改变？
  • 谁已经用极低成本解决了？
  • 谁的要求与初始方案冲突？
  • 在哪些场景下，人工处理反而更合理？

设计的目标不是证明自己最初正确，而是尽快发现自己哪里错。

4. 从材料中提炼问题：事实、解释与假设必须分层

4.1 原始材料不等于结论

调研结束后，常见错误是直接写：“用户需要一键生成”“用户希望更多模板”“用户觉得编辑困难”。这些句子可能混合了受访者原话、你的概括和你的方案。

建议把材料分为三层：

层次含义例子
事实可追溯的行为、原话或材料受访者上次用 90 分钟手动调整公式和移动端布局
解释你对事实的归纳跨设备渲染检查可能是主要时间成本
假设尚待验证的因果判断如果自动检查并给出修复建议，交付时间会明显降低

这三层不能互相伪装。事实可以支持解释，却不能自动证明解释；多个相似事实能够提高假设可信度，却仍需要实验。

4.2 用任务时间线定位真正摩擦

把一个完整任务按时间展开，并为每一步记录：

  • 输入是什么；
  • 操作者做什么决策；
  • 使用什么工具或协作者；
  • 输出是什么；
  • 耗时、失败和返工发生在哪里；
  • 操作者最担心什么；
  • 谁在下一步消费这个输出。

你可能发现，受访者口头抱怨“写 HTML 麻烦”，但任务时间线表明真正的损失来自：

  • 每次都要重新解释页面规范给模型；
  • 输出结构不可预测，无法自动接入主项目；
  • 内容作者和前端开发者之间反复确认；
  • 页面能打开，但教学效果没人定义；
  • 修改内容后无法稳定保留布局。

这五种问题对应完全不同的产品方向。只根据一句“HTML 很麻烦”无法设计。

4.3 把抱怨改写成机会，而不是功能

机会描述应该站在使用者的任务和结果上，不预设解决方案。例如：

功能式表述：用户需要一个模板选择器。

机会式表述：当作者处理不同类型的数理语料时，需要快速获得与学习任务匹配的页面结构，同时不必重新说明全部视觉和交互规范。

功能式表述会让后续探索被“模板选择器”锁死；机会式表述允许多个方案：自动分类、规则继承、示例驱动、分层 Skill、少量参数化模板，甚至可能是流程调整而不是新功能。

可以把机会组织成一棵树：

目标结果：让完整语料更快成为适合独立学习、可稳定维护的网页材料
├─ 机会 A：作者难以把教学意图映射为页面结构
├─ 机会 B：模型生成风格和组件不稳定
├─ 机会 C：公式、目录和移动端显示需要重复检查
└─ 机会 D：内容修订后，页面难以低成本同步更新

这种结构迫使你区分“我们想达到的结果”“用户遇到的机会”和“可能采用的解决方案”。

5. 判断一个问题是否值得解决

不是所有真实问题都值得做成产品。有人确实每年会痛苦地做一次任务，但频率太低；有人每天遇到小麻烦，却已经有足够好的替代方法；还有些问题很严重，但与你的项目能力和目标无关。

5.1 六个价值维度

可以从六个维度判断：

  1. 严重程度：失败会造成多少时间、金钱、质量、风险或情绪成本？
  2. 发生频率：问题多久出现一次？是每次任务必然发生，还是偶发？
  3. 覆盖范围：多少目标用户遇到？是核心用户还是边缘用户？
  4. 现有替代：当前办法有多差？用户是否已经形成低成本习惯？
  5. 行动意愿：用户是否曾投入时间、预算、脚本或协作去解决？
  6. 战略与能力匹配：解决它是否发挥项目独特能力，且符合长期方向？

这不是为了算出一个看似精确的总分。早期证据通常不支持精确数字。更好的做法是为每项写出证据与不确定性：

维度当前判断证据不确定性
严重程度中高三次任务均发生 1—2 小时返工样本来自熟悉前端的作者，普通作者可能更高
频率中项目每周生产 2—3 篇材料是否长期保持该生产量未知
替代方案一般已有通用模型和固定模板通过优化提示词是否已足够尚未验证
行动意愿有迹象团队已手写规范并多次人工检查是否愿意承担插件接入成本未知

5.2 “用户说喜欢”不是价值证据

价值证据强弱大致可以这样理解：

礼貌赞同
＜ 主动询问
＜ 愿意花时间试用
＜ 愿意迁移真实任务
＜ 愿意提供数据或协作资源
＜ 愿意承担预算、责任或组织变更

越接近真实代价的行为，证据越强。内部项目不一定有付款，但仍可观察：用户是否愿意把下一次真实交付交给原型、是否允许接入工作流、是否持续反馈、是否愿意放弃旧方案。

5.3 明确“不做”的条件

成熟的前期设计必须允许项目被否定。可以提前写停止条件：

  • 目标用户很少执行该任务，且现有方法已足够；
  • 主要成本来自内容生产而不是 HTML 转换，而项目明确不处理内容；
  • 输出质量必须依赖大量人工设计，无法形成可复用机制；
  • 主项目接入和维护成本显著超过独立工具带来的收益；
  • 最终读者学习效果没有改善，只有页面更好看；
  • 同类能力已被主系统低成本覆盖，扩展没有独特价值。

停止不是失败。早期用少量调研否定一个方向，比用数周开发证明它不重要更成功。

6. 第一次收敛：写出可执行的问题定义

经过发散调研后，你需要暂时收敛。好的问题定义必须足够具体，使团队知道下一步研究什么；又不能偷偷把方案塞进去。

6.1 问题定义的五个部件

问题定义模板

目标角色：一个明确角色，而不是“所有用户”。
关键场景：由什么事件触发，处在什么工作流中。
待完成任务：角色真正想获得的结果。
核心障碍：当前为何难以完成，以及造成什么后果。
目标变化：解决后应出现什么可观察改善。

例如：

当持续生产数理自学语料的内容作者已经完成正文，需要把它交付为可在移动端独立阅读的网页时，他们必须重复解释页面规范、手动检查公式与结构，并在内容修订后反复同步修改，导致交付时间长且质量不稳定。我们希望减少从“内容定稿”到“通过渲染检查”的人工步骤，同时保持作者对内容和关键呈现规则的控制。

这比“做一个 AI HTML 插件”更有设计价值，因为它指出角色、场景、任务、障碍和目标，却没有把解决方式锁死。

6.2 同时写清楚范围与非目标

设计初稿最容易膨胀的原因，是没有明确边界。问题定义后应马上写：

  • 输入边界：假设语料是否已经完整、结构化、审核过？
  • 输出边界：是单个 HTML、组件树、可编辑工程，还是发布后的页面？
  • 用户边界：服务内容作者、教师、学生还是平台维护者？
  • 质量边界：保证语法正确、视觉一致、教学有效，分别到什么程度？
  • 系统边界：独立工具、插件、主项目内模块，哪一层属于当前设计？

非目标同样重要。例如：

  • 不负责修改原始语料的知识内容；
  • 不追求替代专业视觉设计师处理所有高定制页面；
  • 第一版不支持任意前端框架和发布平台；
  • 不以“生成更多动效”为主要价值指标；
  • 不在证据不足时直接支持所有 K12 学科。

非目标不是给未来设限，而是保护当前验证能够得到清晰结论。

6.3 定义成功指标，但不要过早追求单一数字

早期可以同时定义三类指标：

指标层次回答的问题例子
结果指标用户最终是否更成功？从内容定稿到通过检查的时间下降
行为指标用户是否真正采用？真实语料任务中持续使用，而非只演示一次
质量护栏改善是否以牺牲重要质量为代价？公式错误率、关键内容遗漏率、移动端可读性不恶化

“生成成功率”可能只是系统内部指标。如果生成速度更快，却增加审核负担，产品并没有创造价值。

决策门 1：是否已经有资格进入方案探索？

至少应能回答：

  • 目标角色和关键场景是否明确？
  • 是否观察到多次真实任务，而不只是听到抽象意见？
  • 核心问题是否能用现有行为和材料证明？
  • 现有替代为什么不够好？
  • 如果问题解决，什么结果会改变？
  • 有哪些证据可能推翻当前判断？

如果大部分答案仍是“凭感觉”，不应开始完整技术设计。

7. 第二次发散：先比较解决机制，再讨论具体功能

7.1 不要把初始想法当作唯一方案

问题明确后，才进入方案空间。此时至少提出三类不同机制，而不是三个界面版本。例如，面对“页面生成不稳定且反复解释规范”的问题，可能有：

  1. 固定模板机制：把内容填入少量稳定页面结构；
  2. 规则与 Skill 机制：通过分层约束指导模型生成，并自动检查结果；
  3. 组件编排机制：模型只选择和组合受控组件，不直接自由生成完整页面；
  4. 人工辅助机制：先分析语料并推荐结构，由作者确认后再生成；
  5. 流程机制：不是生成新页面，而是建立统一中间格式和转换流水线。

这些机制的技术结构、可控性、表达能力和维护成本不同。如果一开始就把“插件 + 多层 Skill”写进需求，就很难认真比较它与组件系统或中间格式是否更合适。

7.2 用同一组标准比较方案

标准要问的问题
用户价值它直接减少哪一段成本或改善哪一结果？
覆盖程度它解决核心问题，还是只处理表面症状？
学习成本用户要改变多少现有习惯？
可控性错误是否可预测、可发现、可修复？
表达能力能覆盖多少类型的语料和页面？
技术风险依赖哪些模型、数据、接口和主项目改动？
维护成本规则、模板、组件和兼容性如何演进？
验证成本能否用低成本原型得到关键证据？

比较时要把“现在验证核心价值”和“未来完整产品”分开。有些方案长期更优，却不适合最早验证；可以先用人工或半自动原型验证价值，再决定最终架构。

7.3 方案描述应先写机制，再写功能

一个清晰的方案概念至少包含：

  • 核心机制：它为什么有可能解决问题；
  • 输入：用户和系统提供什么；
  • 关键转换：信息怎样被分析、决策和处理；
  • 输出：用户得到什么可用结果；
  • 控制点：用户在哪些环节确认、修改或回退；
  • 失败处理：系统不确定或出错时怎样暴露；
  • 系统关系：它与主项目和现有流程怎样连接。

例如，“多层 Skill”不是价值本身。它的机制可能是：

把长期稳定的整体设计原则、某类页面的结构约束和单次任务的局部要求分层保存，使模型在不同抽象层级上获得一致约束；生成后再用结构检查器验证必须项，从而降低每次重新提示和输出漂移的成本。

这句话解释了它如何工作、解决什么问题以及仍需要什么检查，比“设计三个文件夹”更接近真正方案。

8. 用最低成本原型验证最危险的假设

8.1 原型不是低质量成品，而是实验装置

原型的目标不是展示团队已经做了多少，而是让一个关键问题得到答案。不同问题需要不同原型：

待验证问题合适的低成本方法没必要先做什么
问题是否真实访谈、观察、任务材料分析完整界面
用户是否重视结果让用户把真实任务交给人工服务或半自动流程正式插件接入
输出是否有用手工制作几份代表性输出进行盲评通用生成引擎
交互是否易懂纸面流程、可点击原型、模拟对话后端与数据库
模型是否可控小样本提示实验、结构化输出检查大规模系统重构
主项目能否接入最小接口桩、一次完整请求链路全部功能
维护是否可持续模拟规则升级和旧页面回归测试扩展到所有场景

8.2 按风险顺序实验，而不是按模块顺序开发

工程计划习惯按模块分：前端、后端、数据库、模型、接口。但发现阶段更应按假设分：

  1. 用户是否真的为该任务付出显著成本？
  2. 理想输出是否能带来可观察改善？
  3. 受控生成机制能否稳定接近理想输出？
  4. 作者能否理解并修正系统结果？
  5. 扩展接入主项目是否比独立流程更有价值？

如果第 1 项不成立，没有必要验证第 5 项。把风险顺序和开发顺序混为一谈，是“技术完成度很高、产品证据很少”的主要原因。

8.3 每个实验必须提前写清判定规则

实验卡

要验证的假设：……
为什么它最危险：……
实验对象：哪些用户、哪些真实材料、哪些场景。
实验方法：给出什么，观察什么。
成功信号：什么行为或结果支持假设。
失败信号：什么结果会迫使我们修改或放弃。
限制：这个实验不能证明什么。
下一决策：不同结果分别对应什么动作。

例如：

假设：对已经完成内容的作者，主要可节省成本来自页面结构与渲染检查，而不是内容重写。
方法：选择五篇真实语料，用人工模拟的“理想生成服务”完成页面，记录作者原流程和新流程的时间、返工次数及满意度。
支持信号：至少多数任务显著减少交付时间，且内容审核负担没有上升。
失败信号：作者大部分时间仍花在内容重构，或理想页面也无法改善任务。
限制：该实验不能证明模型能够自动达到同样质量。

没有预先判定规则，实验结果很容易被事后解释成支持原方案。

决策门 2：是否已经有资格写 MVP 和工程方案？

  • 至少一个核心价值假设是否得到真实任务支持？
  • 目标用户是否愿意改变行为，而不只是表示喜欢？
  • 最危险的技术假设是否有最小验证？
  • 失败模式是否已经出现并被记录？
  • 方案为何优于现有替代，是否有证据而非口号？

9. 第二次收敛：MVP 不是缩小版成品

9.1 MVP 的任务是完成一次最小价值闭环

MVP 常被误解为“把计划中的十个功能砍到三个”。更准确的理解是：用最小范围，让一个目标角色在一个真实场景中完成一次核心任务，并产生足以验证价值的结果。

最小闭环应包含：

真实输入 → 核心处理 → 可用输出 → 用户实际使用 → 结果被观察 → 反馈能够进入下一轮

如果只有生成按钮和展示页面，却没有真实输入、质量检查和后续使用，就不是闭环。

9.2 用“必须证明什么”决定范围

假设第一阶段最需要证明：

受约束的生成流程能够把完整数理语料稳定转成移动端可读 HTML，并显著减少作者从内容定稿到通过检查的时间。

那么 MVP 可能只需要：

  • 支持一种已确认的语料类型；
  • 接受一种稳定输入格式；
  • 提供一套整体规则和一套页面结构；
  • 生成完整 HTML；
  • 自动检查目录、公式、必需结构和移动端溢出；
  • 允许作者查看问题并重新生成或局部修正；
  • 记录人工耗时和错误。

它可能不需要：

  • 大量主题皮肤；
  • 所有学科模板；
  • 复杂账户系统；
  • 完整可视化编辑器；
  • 自动发布到多个平台；
  • 全面重构主项目。

是否需要接入主项目，也应由验证目标决定。若独立脚本已经能验证核心价值，过早接入只会增加变量。只有当“嵌入现有工作流”本身是关键假设时，才应尽早做最小接入。

9.3 把需求分为三层

层次含义例子
结果需求用户要得到什么改变减少从定稿到可交付页面的时间
能力需求系统必须具备什么能力识别结构、应用约束、生成并检查 HTML
实现需求当前版本采用什么具体方式通过分层 Skill、组件模板和校验器实现

这三层分开后，未来才能更换实现而不丢失需求。例如，分层 Skill 可能被组件编排替代，但“稳定应用页面规则”的能力需求仍然存在。

10. 一份完整设计初稿应当包含什么

设计初稿不是最终规格书。它的作用是让导师、产品、设计、工程和使用者能够审查同一条逻辑：问题是否成立、方案为何合理、哪些风险仍未解决、下一步是否值得投入。

10.1 推荐结构

  1. 一句话摘要：为谁，在什么场景，解决什么问题，用什么核心机制，预期改变什么结果。
  2. 背景与触发：项目为何出现，当前流程和环境是什么。
  3. 调研方法：看了哪些材料、访谈或观察了谁，有哪些局限。
  4. 关键事实：可追溯的行为、数据、原话和任务材料。
  5. 问题定义：目标角色、场景、任务、障碍、后果和目标结果。
  6. 价值判断：严重度、频率、替代方案、行动意愿和战略匹配。
  7. 范围与非目标：当前解决什么，不解决什么。
  8. 方案候选与比较：至少列出主要替代机制及取舍。
  9. 选定方案的核心机制：解释信息和控制如何流动。
  10. 用户流程：从触发到结果的完整步骤，包含失败与回退。
  11. 系统边界：输入、输出、组件、接口、依赖和主项目关系。
  12. MVP 范围：完成哪一个最小价值闭环。
  13. 成功指标与质量护栏：怎样判断值得继续。
  14. 关键假设与证据状态：已验证、部分验证、未验证分别是什么。
  15. 风险与失败模式：产品、技术、使用、维护和组织风险。
  16. 验证计划：接下来每个实验如何影响决策。
  17. 待决问题：必须由导师或团队决定的事项。
  18. 决策记录：为什么选择当前方向，放弃了哪些选项。

10.2 系统部分要描述“流”，而不是堆组件名

对于计算机项目，设计初稿中的系统结构至少要回答：

  • 一次真实请求从哪里开始；
  • 每个阶段接收什么数据，输出什么数据；
  • 哪些决策由用户做，哪些由系统做；
  • 不同层的规则怎样组合，冲突时谁优先；
  • 模型生成结果如何被检查；
  • 错误在哪里暴露，用户如何恢复；
  • 扩展与主项目通过什么接口解耦；
  • 未来替换模型、模板或校验器时，哪些部分不应变化。

可以画成一次请求链：

完整语料
→ 输入校验与结构识别
→ 选择页面类型和适用规则
→ 组合全局约束、类型约束、单次任务约束
→ 生成受控 HTML
→ 静态结构检查与实际渲染检查
→ 返回页面、问题报告和可修订入口
→ 作者确认后交付或进入发布流程

这比写“采用 Agent、Skill、模板、React、数据库”更有解释力。工具名只有在说明接口与取舍时才重要。

10.3 给每个关键需求附上来源

需求最好能够追溯：

需求来源证据强度当前决策
内容不能被模型擅自改写项目边界与作者访谈高生成层只处理呈现结构
必须适合移动端阅读真实阅读场景高纳入自动与视觉检查
需要多层规则对生成漂移的方案推断中先原型验证，不当作永久架构
需要大量动画开发者偏好低不进入 MVP

这样导师质疑某个功能时，你能回到证据，而不是陷入“我觉得有用”和“我觉得没用”的争论。

10.4 明确初稿的置信度

设计初稿中可以给结论标记：

  • 已证实多次真实行为或实验直接支持；
  • 较可信有一致证据，但样本和场景有限；
  • 工作假设当前为了推进而暂时采用；
  • 待决缺少证据或需要负责人决策。

设计初稿不需要假装确定。真正专业的文档会把不确定性结构化，而不是隐藏。

11. 以 InnoSpark 扩展为例重新走一遍

下面是基于你目前描述的重构示例，不代表已经完成真实用户调研；其中“可能”“假设”必须在后续用项目材料验证。

11.1 原始想法

为 InnoSpark 做一个扩展，把已经有完整语料的内容转换成合适的 HTML 演示或学习文稿，并通过 Skill 指导模型生成。

11.2 先拆出关键假设

  1. InnoSpark 的目标用户会持续拥有“内容完整但尚未网页化”的语料；
  2. 他们需要的不是普通文档或幻灯片，而是 HTML 学习材料；
  3. 当前转化过程的主要瓶颈在呈现设计与实现，而不是内容重写；
  4. 自动化输出可以在可接受人工审核成本下达到质量要求；
  5. 用户愿意接受一定结构约束，以换取稳定性；
  6. 扩展嵌入主项目比独立工具更能改善工作流；
  7. 分层 Skill 是控制输出的有效机制，而不是把复杂性从代码转移到提示词；
  8. 最终学习效果至少不低于现有材料。

你这次导师反馈“产品价值不高”，很可能不是在否定代码质量，而是在指出前 1—6 项没有充分证据。此时继续精细化 Skill 结构，只能优化第 7 项，无法补上价值链前半段。

11.3 应优先调查的真实任务

  • 谁在 InnoSpark 中生产内容？频率是多少？
  • 现有输入长什么样，结构是否稳定？
  • 内容最终给谁使用：课堂演示、学生自学、复习还是项目展示？
  • 不同用途对页面结构有什么本质差异？
  • 现在从语料到交付物需要哪些人工步骤？
  • 哪一步最耗时，哪一步最容易造成返工？
  • 现有通用模型、Markdown 渲染、模板或其他插件为何不足？
  • 主项目维护者愿意接受多大的接入面和长期维护责任？
  • 导师判断“有价值”的标准是什么：用户量、节省时间、学习效果、平台差异化，还是技术探索？

11.4 可能出现的三种重新定位

方向 A：页面生成器

如果证据表明作者确实频繁需要把已完成语料变成网页，且主要成本是页面实现，那么核心产品可以是受控 HTML 生成与校验。

方向 B：学习材料编排器

如果真正问题是“同一语料怎样适配自学、复习、预习等学习任务”，那么价值核心不是 HTML，而是把教学意图映射为信息结构。HTML 只是输出媒介，产品需要更强的教学结构模型。

方向 C：内容交付流水线

如果最痛的环节是版本、渲染检查、主项目接入和修订同步，那么产品可能应定位为从语料到可发布页面的流水线，而不是单次生成插件。

这三个方向都能使用你已完成的部分代码，但它们的用户、价值指标、系统边界和后续开发重点不同。前期调研的意义，正是决定你在做哪一种产品。

11.5 一个更谨慎的设计初稿摘要

我们暂定服务于持续生产数理自学材料的内容作者。在内容已经完成且不允许被系统擅自改写的前提下，作者仍需把语料组织为移动端可读网页，并重复处理页面规则、公式渲染、结构检查和后续修订同步。项目拟通过受控的页面编排规则、生成机制和自动校验，减少从内容定稿到可交付页面的人工成本。第一阶段不证明“可以生成任意漂亮网页”，而是验证：在一种高频语料类型上，系统能否稳定完成最小交付闭环，并显著降低总耗时而不增加内容错误。是否必须嵌入 InnoSpark 主项目、是否采用多层 Skill 作为长期架构，将通过独立原型与最小接入实验比较后决定。

这段摘要比原始想法保守，但更强，因为它明确了当前要证明的价值，也保留了否定和调整方案的空间。

12. 一套可以直接执行的十步工作流

第 1 步：用一页纸记录初始想法

写初始假设卡，不超过一页。不要急着写完整需求，也不要隐瞒未知。

第 2 步：列出关键假设并排序

把问题、价值、行为、可用性、技术和维护假设分开。优先处理“错了就不值得做”且“目前最缺证据”的假设。

第 3 步：画出现有任务链和角色图

确定触发事件、完整流程、输入输出、决策者、使用者、维护者和最终受益者。不要只研究产品直接接触的一步。

第 4 步：做定向桌面调研

比较替代方案的任务、机制、工作流位置和取舍；查清技术与组织约束。不要以功能数量判断竞品强弱。

第 5 步：调查真实任务

访谈和观察若干有差异的角色，要求他们讲最近一次经历并展示材料。记录事实、原话和时间线。

第 6 步：合成机会并判断价值

把事实、解释、假设分层；建立任务时间线和机会树；从严重度、频率、替代、行动意愿和战略匹配判断优先问题。

第 7 步：写问题定义、范围和非目标

让团队先对“解决谁的什么问题”达成一致。定义结果指标、行为指标和质量护栏。

第 8 步：提出多个解决机制并比较

至少保留一个“不做新产品或只改流程”的选项。比较用户价值、可控性、表达能力、技术风险、维护和验证成本。

第 9 步：做最低成本的关键实验

每个原型只服务于一个关键问题。优先验证价值，再验证可用性和技术；提前写成功、失败和下一决策。

第 10 步：收敛为设计初稿并召开审查

把证据链、问题、方案、MVP、系统流、指标、风险和待决项放进同一份文档。审查会议不应只问“还缺什么功能”，而应问：

  • 哪条关键判断证据最弱？
  • 有没有更便宜的方式解决同一问题？
  • 当前 MVP 能证明什么，不能证明什么？
  • 什么结果出现时，我们应该停止或转向？
  • 工程投入是否与证据强度匹配？

一个实用节奏：不要等所有调研结束后才写文档。设计初稿应从第一天就存在，但每一节标记证据状态，并随着调研不断改写。文档不是最后的汇报材料，而是贯穿发现和决策的工作台。

13. 常见失败模式：哪些文档看起来专业却没有设计价值

13.1 只有宏大背景，没有具体任务

“AI 时代教育数字化需求快速增长”不能证明某个插件值得做。背景只能说明方向可能重要，不能代替用户场景和行为证据。

13.2 竞品表列了几十个功能

功能数量不能说明竞争关系。用户比较的是完成任务的整体成本，包括学习、迁移、协作、风险和维护。

13.3 用户画像充满年龄、职业和性格标签

与设计决策无关的人口统计信息价值很低。更重要的是任务频率、熟练度、上下游关系、失败代价和决策权限。

13.4 把用户意见直接变成功能需求

用户说“希望多几个模板”，可能表达的是“我无法控制输出”“不同任务需要不同结构”或“我不想重复提示”。要继续追问原因和过去行为。

13.5 用漂亮原型掩盖问题证据不足

高保真页面容易让评审转而讨论颜色和按钮，从而忽略产品是否值得存在。原型精度应该与待验证问题匹配。

13.6 把所有风险都写成技术风险

“模型可能生成错误 HTML”是风险；“用户不愿把真实任务交给系统”“维护者不愿接入”“最终读者没有更好学习结果”同样是风险，而且可能更致命。

13.7 把架构选择写成不可动摇的需求

“必须用多层 Skill”“必须嵌入主项目”“必须使用某框架”通常是实现假设。除非它来自硬约束，否则应该保留替代方案。

13.8 MVP 只有功能，没有价值闭环

能生成页面不等于用户任务完成。必须包含真实输入、质量判断、使用结果与反馈。

13.9 调研只找支持者

如果样本全部来自对项目友好、技术背景相似的人，你很难发现迁移成本和真实反对意见。主动寻找不需要、不会用和已经解决的人。

13.10 设计文档没有停止条件

没有停止条件的项目会把任何结果解释成“还需要继续迭代”。设计初稿必须说明什么证据会让团队缩小、转向或终止。

14. 自检题与参考答案

14.1 自检题

  1. 为什么“做一个自动生成 HTML 的插件”还不是问题定义？
  2. 问题不确定性与技术不确定性有什么区别？为什么早期顺序很重要？
  3. 访谈中，为什么“你会不会用”通常是弱证据？应该怎样改问？
  4. 事实、解释和假设三者如何区分？
  5. 一个真实问题为什么仍可能不值得做成产品？
  6. 机会描述与功能描述有什么区别？
  7. 为什么要提出多个“解决机制”，而不只是多个界面版本？
  8. 原型与低质量成品的根本区别是什么？
  9. MVP 为什么不是计划功能的缩小集合？
  10. 一份设计初稿至少要让评审追踪哪条逻辑链？
  11. 对 InnoSpark 扩展而言，哪些结论目前仍应被视为假设？
  12. 什么情况下，最合理的结论是暂时不继续开发？

14.2 参考答案

  1. 它预设了目标用户、真实困难、输出媒介和解决方式，却没有说明谁在什么场景遇到什么后果，也没有证据证明问题与价值。
  2. 问题不确定性问“是否值得解决”，技术不确定性问“是否能够实现”。若先解决后者，可能高质量地实现一个不重要的方向。
  3. 未来意愿容易受礼貌和想象影响。应询问最近一次真实任务、具体步骤、投入、失败和替代方案，并观察材料与行为。
  4. 事实可追溯到行为、原话或材料；解释是对事实的归纳；假设是尚待验证的因果判断。三者证据强度不同。
  5. 它可能低频、低严重度、已有廉价替代、用户不愿迁移、覆盖人群太小，或不符合项目战略和能力。
  6. 机会描述表达用户任务中的障碍和期望结果，不预设方案；功能描述直接指定某种实现。
  7. 不同机制代表不同因果路径与系统取舍。只比较界面，无法判断是否有更简单、更稳定或更低维护的解决方式。
  8. 原型是为回答一个决策问题设计的实验装置；低质量成品只是功能不完整，却未必能产生清晰证据。
  9. MVP 要完成一个最小价值闭环，并验证最关键判断；它可以包含人工环节，也不必覆盖未来产品的所有模块。
  10. 从真实证据，到问题定义，到方案选择，到 MVP 范围，到指标与风险，再到下一步验证的完整推理链。
  11. 目标用户是否高频需要 HTML、主要成本是否在呈现、分层 Skill 是否有效、主项目接入是否必要、学习效果是否提升等都仍需验证。
  12. 当目标问题不重要、现有替代足够、核心价值实验失败、接入维护成本超过收益，或项目无法在边界内创造独特价值时，应缩小、转向或停止。

15. 本文结论

从简单想法到完整设计初稿，不是一条“把功能越想越细”的直线，而是两次发散和两次收敛：

初始想法
→ 拆成可证伪假设
→ 发散研究角色、场景、任务与替代方案
→ 收敛为高价值问题
→ 发散比较多种解决机制
→ 用最低成本原型验证关键风险
→ 收敛为 MVP、系统边界和设计初稿

完整设计初稿并不意味着所有问题已经确定。它意味着：

  • 你知道哪些是事实，哪些是推断，哪些只是工作假设；
  • 你能解释为什么选这个问题，而不是只解释怎样实现；
  • 你比较过替代方案，而不是把最初灵感当成必然答案；
  • 你用实验降低了最危险的不确定性；
  • 你定义了最小价值闭环、成功指标、质量护栏和停止条件；
  • 工程团队能看到一次请求怎样流过系统，导师能看到投入为何值得。

对你这次 InnoSpark 项目，最重要的教训不是“以后要多写调研报告”，而是：在写大量代码之前，先把项目看作一组可能错误的判断；让每一步工作都服务于减少某个关键不确定性。

当你能在早期坦然地证明一个想法不值得做，或者把它改造成另一个更有价值的问题时，你才真正开始具备产品与系统设计能力。

下一篇建议

可以继续写一篇实践型文章：以当前 InnoSpark 扩展为真实案例，建立一份“项目重新调研与设计初稿模板”，逐项填写目标角色、任务链、关键假设、访谈提纲、实验卡、方案比较表和设计初稿目录。

参考资料

  • Design Council, The Double Diamond：问题探索与方案探索中的发散—收敛结构。
  • IDEO, Design Thinking Process：以人的真实需要为起点，并通过构思、实验与实施推进设计。
  • Strategyzer, Value Proposition 与 Value Proposition Canvas：从用户任务、困难与收益理解价值主张。
  • Teresa Torres, Opportunity Solution Trees：把目标结果、机会与解决方案分层组织，避免从目标直接跳到功能。
  • Eric Ries, The Lean Startup：用可检验假设和反馈循环降低早期产品不确定性。
  • Steve Blank, The Four Steps to the Epiphany：在扩大执行前，先通过客户发现检验问题、用户和商业假设。

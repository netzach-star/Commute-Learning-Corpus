一、AI 设计文档为什么特别容易“看起来完整”

大模型很擅长生成形式完整的技术文本：标题齐全、术语专业、组件命名一致、接口字段很多。这带来一种危险错觉：

文字密度不等于设计闭环，术语正确不等于项目假设成立，章节齐全也不等于实现者知道发生故障时该怎么办。

AI 生成设计常见的四类问题：

1. 补全成“行业常见答案”

项目材料没有说明时，模型按常见架构自动补出消息队列、缓存、微服务或版本策略，却没有标出它是推断。

2. 局部合理、整体不一致

某节说对象不可变，另一节又让接口原地更新；某节说异步发布，验收却要求瞬时一致。

3. 把技术名词当作机制

写“采用 outbox 保证一致性”“使用 ETag 解决并发”，却不说明事务边界、幂等键或冲突后的用户流程。

4. 把开放问题写成既定事实

外部系统是否支持同 documentId 更新尚未验证，文档却直接基于 upsert 设计全部链路。

所以审查的重点不是找错别字，也不是要求更多技术细节，而是追踪：

事实来自哪里
→ 设计决定解决什么
→ 必须始终满足什么
→ 失败时留下什么状态
→ 怎样证明决定成立
→ 实现按什么依赖顺序推进

二、四层审查框架：从“做对事”到“能安全演进”

层次核心问题典型缺陷
需求与范围层这是在解决已确认的问题吗？哪些明确不做？过度设计、遗漏关键场景、把猜测当需求
结构与语义层边界、术语、数据源、流程和状态是否一致？组件职责重叠、多个 source of truth、内部代号无定义
正确性与运行层并发、失败、重试、权限和容量下仍成立吗？双写丢任务、重复副作用、越权、无恢复路径
证据与演进层哪些结论已证明？怎样迁移、发布、回滚和记录决策？外部能力靠想象、Spike 无结论、上线后不可回退

审查顺序应从上往下。若需求和边界未定，先争论数据库字段通常没有意义；若核心不变量不存在，接口再详细也不能证明系统正确。

三、需求追踪：要求每个重要设计回答“它在保护什么”

1. 建立需求—风险—设计—证据矩阵

最实用的审查工具不是更复杂的架构图，而是一张追踪表：

需求/约束主要风险设计决定验证证据状态
两个 Agent 不共享职责外内容历史串线、工具越权独立 session 与可见性边界D-01 恢复与越权测试待验证
无向关联不重复且两端可见重复边、半边、死锁canonical link、双端 revision、统一锁序D-02 并发实验待验证
发布后投影任务不丢数据库与任务双写裂缝事务 + outbox + 幂等 jobD-03 故障注入待验证

这张表能发现两种问题：

  • 孤儿设计：一个复杂组件找不到关联需求或风险，可能是过度设计；
  • 裸需求：一条关键承诺没有设计与证据，可能只停留在愿望。

2. 要求区分四种陈述

标签含义例子
已确认事实已有代码、实验、官方契约或用户决定支持Stage 0 已有 Session Adapter
设计决定团队在多个方案中选择的一条路线无向边只保存一条 canonical link
待验证假设实现依赖但证据不足L2 可能支持同 documentId upsert
开放问题尚未决定，不能让实现偷偷决定冲突后是拒绝、合并还是人工审阅

AI 最容易把后三类混写。你可以要求每个章节在段落旁标注这些标签，尤其是外部能力与性能结论。

四、术语、边界与数据所有权：先确保所有人说的是同一个系统

1. 内部术语必须可追溯

L2、P0、S-09、Bundle 一类词若没有定义，不能要求读者自己猜。术语表至少写：

  • 一句话定义；
  • 对象类型：服务、数据对象、环境、阶段还是实验编号；
  • 谁创建、谁拥有、谁读取；
  • 生命周期和唯一标识；
  • 首次定义或权威章节链接。
不合格：“L2 更新后重建 Bundle。”
合格方向：“L2（此处给出项目定义）保存可检索来源；Bundle 是由某个 DocumentVersion 生成的派生包。发布服务在 current 变化后触发 Bundle projection。”

2. 画系统上下文，不先画内部类图

上下文图首先回答：

  • 用户、Agent、ReviewWorkspace、主系统、数据库、L2 等参与者各是谁；
  • 哪些在本系统控制内，哪些是外部依赖；
  • 跨边界传递什么数据；
  • 哪个边界涉及信任、权限或失败。

若连系统边界都不清楚，讨论“某个 service interface”容易把外部能力误当内部函数。

3. 每种数据只能有明确的权威来源

审查时对每个核心事实问：

  • canonical link 的真相存在哪里？
  • Markdown 是源内容还是派生物？
  • 哪个 revision 表示文档内容，哪个表示关联变化？
  • current、active、serving 是否是同一个概念？
  • 候选目录由谁生成，是否可以人工修改？

若两个组件都能独立修改同一事实，却没有冲突规则，就存在双主问题；若派生物可以反向修改源对象，生命周期会变得模糊。

五、状态机、不变量与并发：静态组件图看不到的正确性

1. 要求作者写出最重要的不变量

不变量是系统在所有合法状态下都必须成立的命题。根据 D-01～D-06，可以提炼：

  • 两个 AgentSession 的历史与可见数据不串线；
  • 同一无向关系最多一条 canonical link；
  • 关系变化后两个受影响文档都有对应修订与重建意图；
  • 提交前失败不改变 current；
  • 已提交的派生工作不会因 worker 丢失而永久消失；
  • 同一逻辑 projection job 不重复；
  • 同一 documentId 最多一个 active source；
  • 用户基于旧 ETag 提交时不会静默覆盖新状态。

如果设计文档没有不变量，测试只能验证作者想到的例子，无法判断遗漏了哪些组合状态。

2. 把对象写成状态机

以 projection job 为例：

pending → processing → ready → serving
              ↓          ↓
            retry      failed
              ↑          ↓
           lease_expired  manual_repair

审查问题包括：

  • 谁有权触发每条转移？
  • 转移是否原子？
  • 进程在转移中崩溃，持久状态是什么？
  • 能否从 failed 回到 pending？
  • ready 与 serving 为什么分开？
  • 重复请求某条转移是否安全？

3. 给并发操作做“交叉表”

操作 A操作 B可能同时发生吗预期语义
发布文档 v6发布同一文档 v7是检测 revision/ETag 冲突，或定义串行顺序
添加 A—B添加 B—A是只形成一条 canonical link
删除 A—B重建 A 的投影是投影绑定明确目标 revision，不读漂移 current
用户审阅 v5另一用户发布 v6是旧 ETag 提交被拒绝并进入冲突流程

这张表常比泛泛写“支持并发”更有价值。

六、故障、恢复与可观测性：每个外部调用都要问“中间死了怎么办”

1. 设计评审中的故障六问

  1. 调用前失败，是否留下状态？
  2. 调用成功但确认丢失，调用者怎样判断？
  3. 重试会不会重复副作用？
  4. 长期失败时是否阻塞主流程？
  5. 旧结果是否仍可服务？
  6. 运维人员怎样知道系统卡在哪里？

对每个关键流程，要求给出失败矩阵，而不是只列“异常处理”。例如 outbox worker 失败、L2 更新超时、ReviewApi 返回 ETag 冲突，都不是同一种错误。

2. 恢复路径必须来自持久状态

若“重启后继续”依赖某个进程内布尔变量或聊天上下文，恢复并不可靠。设计应说明：

  • 检查点存在哪里；
  • 恢复扫描的查询条件；
  • lease 怎样过期；
  • 重复恢复如何幂等；
  • 哪些状态需要人工判定。

3. 可观测性不是“多打印日志”

至少要能回答：

  • 一次 publish 命令产生了哪个 version、outbox event 和 projection job；
  • 某文档为何仍在 serving 旧版本；
  • 两个 AgentSession 当前分别处于哪一步；
  • 候选召回耗时、候选数量、token 和接受率是多少；
  • ETag 冲突是正常并发还是异常激增；
  • 是否出现同 documentId 多 active source。

OpenTelemetry 将 traces、metrics、logs 作为主要信号。具体工具可以变化，但设计必须先定义事件关联字段和关键指标。

七、外部能力、Spike 与证据：不允许“应该可以”成为架构地基

1. 列出所有外部能力假设

例如：

  • Session Adapter 能在同一 task 下恢复两个独立 session；
  • L2 支持同 documentId 更新或可通过 manifest pointer 控制 active；
  • ReviewApi 可以用 ETag 进行条件更新；
  • 真实知识库规模下召回延迟与 token 可接受。

对每一项标注证据等级：

等级证据能否作为 P0 地基
0模型推测、口头印象不能
1文档声称支持，但未验证项目配置高风险
2最小本地实验通过可用于继续设计
3真实环境与并发/故障条件通过可用于关键发布决策
4生产监控持续证明可形成稳定能力基线

2. Spike 必须绑定决策

审查每个 Spike 时问：

  • 失败后会选择什么备选方案？
  • 若所有结果都不会改变设计，为什么做？
  • 通过标准能否自动或客观观察？
  • 实验是否使用了足够真实的规模和环境？
  • 结论、限制和原始数据存在哪里？

3. 记录 Architecture Decision Record

重要决定不应只留在某次 AI 对话里。ADR 可以用很短的格式记录：

标题：无向关联采用单条 canonical link
状态：accepted / superseded
背景：为什么需要决定
候选方案：双向两行、单边 canonical、图数据库边……
决定：选择哪一个
理由：哪些不变量、实验与约束支持
后果：得到什么，付出什么
关联：需求、D-02 证据、迁移与测试

ADR 的价值不仅是以后回忆；写下上下文、选择和后果会迫使团队暴露分歧。决定变化时新增 superseding 记录，而不是把历史原因抹掉。

八、实施阶段、迁移与回滚：架构图不是到达架构的路线

1. 阶段按风险依赖，而不是按文件夹

不应因为代码仓库先有 backend、frontend、worker 三个目录，就按目录平行推进。更合理的是：

  1. 验证 Session 与 L2 外部能力；
  2. 固定核心数据模型和不变量；
  3. 完成事务、outbox、幂等与投影状态机；
  4. 在 fake API 上独立完成审阅流程；
  5. 接入真实召回和模型，测质量预算；
  6. 做迁移、灰度、监控和回滚演练。

这种排序让高风险失败发生在投入大量 UI、提示和集成工作之前。

2. 每阶段必须有退出证据

阶段不合格的“完成”合格退出证据
会话隔离代码中创建了两个对象越权测试、重启恢复、主会话体积记录
关系数据UI 能添加关联反向并发无重复、无死锁、双端投影正确
异步发布正常路径能生成 Markdown故障注入、重复消费、旧 serving 持续可读
召回几个手工示例看起来不错真实规模数据集、precision/recall、p95 延迟和 token
L2 更新API 返回成功查询证明同 documentId 只有一个 active source

3. 迁移与回滚要在设计期出现

审查问题：

  • 旧 link 数据如何 canonicalize，发现重复怎么办？
  • 旧文档没有 revision/ETag 时怎样初始化？
  • outbox 上线时，已有 current 是否需要补建 projection？
  • 新旧 worker 是否会同时消费？
  • L2 指针切换失败能否回到旧 active source？
  • 回滚应用版本时，新数据库结构是否仍兼容？

没有迁移和回滚的设计，只描述了一个理想的全新世界，不是现实中的实施设计。

九、用这套框架审查 D-01～D-06：原片段还应该补什么

实验已有优点建议补充
D-01可见性、主会话体积、模型固定、恢复都有标准隔离威胁模型；工具权限；session/task 标识规则；恢复证据和敏感数据审计
D-02明确 canonical、双端版本、双端重建、并发结果link 唯一键；删除与重复命令语义；锁顺序；revision 定义；失败注入点
D-03覆盖提交前后、worker 丢失、重复消费、旧 servingoutbox 状态机；幂等键；重试/死信；投影 ready/serving 切换；监控指标
D-04要求真实规模并同时看质量、延迟和 token测试集、precision/recall 定义、k 值、p95 预算、新节点基准率和误差分析
D-05把独立运行、冲突和发布纳入端到端流程ReviewApi 契约版本；fake 与真实 API 契约测试；错误模型；认证是否在实验边界内
D-06明确三条决策路线，并要求真实环境证明单 activeL2/P0/S-09 定义；active 查询口径；缓存与索引收敛窗口；回滚与历史版本策略

这里的结论不是原片段“写得差”。它本来可能只是设计文档中的紧凑实验索引，完整定义散落在其他章节。真正的审查动作是确认交叉引用存在；若不存在，再要求补写，而不是单独把这一节无限扩张。

十、让 AI 交付一个“可审查设计包”，而不是一篇不可追踪的长文

推荐交付物

  1. 两页阅读地图：目标、边界、主流程、数据源、不变量、最大风险。
  2. 设计正文：系统上下文、数据、状态、接口、失败、性能、安全与运维。
  3. 需求追踪矩阵：需求—风险—设计—测试。
  4. 术语表：所有内部代号和核心对象。
  5. Spike 清单：假设、通过标准、决策规则、阻塞项。
  6. ADR 目录：重要选择及被替代历史。
  7. 实施与迁移计划：阶段依赖、退出证据、灰度和回滚。
  8. 开放问题：责任人、截止决策点和默认阻塞行为。

一条可直接用于 AI 的审查指令

不要继续扩写实现细节。先对当前设计做可审查性审计：
1. 列出所有已确认事实、设计决定、待验证假设和开放问题；
2. 建立需求—风险—设计—验证矩阵；
3. 列出核心数据对象、唯一 source of truth、状态机和不变量；
4. 对每条跨组件流程给出并发与故障矩阵；
5. 标出所有项目内部术语及权威定义位置；
6. 标出依赖外部系统能力的结论和现有证据等级；
7. 给出 Spike、迁移、灰度、回滚和可观测性缺口；
8. 不得把未验证能力改写成既定事实。
最后只列 P0 阻断项、建议修改章节和需要新增的证据。

什么时候可以批准进入实现

  • 核心需求与非目标已经确认；
  • 系统边界、术语和 source of truth 无重大歧义；
  • 关键不变量、状态机和冲突语义明确；
  • 高影响外部能力已经验证，或明确阻断；
  • 关键故障有恢复路径与可观测信号；
  • 阶段有退出证据，迁移与回滚不是空白；
  • 实现者可以从设计定位每个决定的理由和测试。
审查不是证明文档里每个技术选择都完美，而是确认：重要决定可追踪、重要风险被看见、未知项没有伪装成事实、实现失败时有明确反馈路径。

十一、自检题与参考答案

问题 1：为什么 AI 文档“章节齐全”仍可能不完整？
参考答案

完整性取决于需求追踪、数据与状态语义、失败恢复、证据和演进闭环，而不是标题数量。AI 可以轻易生成模板章节，却在各节中混入未验证假设或互相冲突的语义。

问题 2：看到一个复杂组件时，首先应问什么？
参考答案

它保护哪条需求、消除哪种风险。如果找不到关联，可能是过度设计，也可能是需求文档漏掉了系统约束。

问题 3：为什么内部术语缺定义属于设计缺陷，而不只是读者基础不足？
参考答案

内部代号无法从行业知识可靠推断。没有唯一权威定义，不同实现者会赋予不同含义，造成接口、数据和测试不一致。

问题 4：不变量和验收用例有什么区别？
参考答案

验收用例验证若干具体场景；不变量声明所有合法状态都必须满足的命题，可用于系统化生成更多并发、失败和恢复测试。

问题 5：为什么外部 API 文档写“支持更新”仍不一定足够？
参考答案

项目所需语义可能更强，例如同 documentId 更新后单一 active、缓存收敛、并发原子性和回滚。必须在真实配置和数据路径验证。

问题 6：设计审查是否应要求所有开放问题在写代码前解决？
参考答案

不必。关键是识别哪些问题会改变地基、必须阻塞；哪些可以局部实现中决定；以及每个开放问题最晚何时决策、由谁负责、默认行为是什么。

系列结论

从需求到设计的真正跃迁，是从“用户想要什么”进入“系统在时间、并发、失败和演进中必须持续保证什么”。分阶段、Spike、事务、outbox、ETag、召回预算与能力阻断不是脱离需求的技术装饰；它们是把需求变成可靠系统所需的证据和约束。

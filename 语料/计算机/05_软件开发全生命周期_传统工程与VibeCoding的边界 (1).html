Vibe Coding 的主要作用域：在“发现”阶段快速做原型，在“构建”阶段快速生成局部实现。AI 辅助工程可以覆盖七个环节，但每个环节的完成证据仍不能省略。

一、传统开发流程究竟是什么

1.1 它不是“瀑布模型”的同义词

日常讨论常把“传统开发”想象成一条僵硬流水线：先写完需求，再写完设计，再一次性编码，最后交给测试。那只是生命周期活动的一种编排方式，而且现代项目很少严格如此。

2026 年发布的 ISO/IEC/IEEE 12207:2026 把软件从构想到开发、运行、支持和退役都纳入生命周期，同时明确这些过程可以并发、迭代、递归地应用；它并不指定必须使用瀑布、Scrum 或某种工具。敏捷开发同样不会删除需求、设计、测试和运行，只是把它们压缩进更小、更频繁的循环。

本文所说的“传统软件开发”：不是“没有 AI 的开发”，而是软件工程长期形成的一组必要职能——发现问题、定义边界、设计结构、构建、验证、发布、运行与演化。团队可以按瀑布、迭代、敏捷或持续交付来安排它们，但不能靠换一个流行名称让这些问题消失。

1.2 流程的本质是把风险提前暴露

一份需求文档、一张架构图、一次代码审查或一套自动测试都不是为了“显得专业”。它们共同解决一个更根本的问题：软件在现实中失败的方式远多于“代码无法运行”。

  • 它可能实现了一个没有人需要的功能；
  • 可能对正常路径有效，却会损坏异常输入；
  • 可能单机演示顺利，接入真实数据库后丢数据；
  • 可能第一次上线成功，但没人知道出故障时怎样回滚；
  • 可能今天工作，三个月后无人敢修改。

因此，成熟流程不断追问的不是“文档写完了吗”，而是“我们现在凭什么相信可以进入下一步”。文档、代码、测试报告和监控数据都只是这种信任的载体。

1.3 完成标准不是“做过”，而是“有足够证据”

活动完成

开过需求会、画过架构图、写过测试、点过部署按钮。

它只能证明动作发生过。

阶段完成

关键需求可验证、主要风险已有实验、变更通过质量门槛、发布可观测且可回滚。

它证明剩余风险已低到当前项目可以接受。

这里的“足够”由风险决定。一个仅自己使用、数据可随时重建的周末脚本，不需要银行支付系统的审查强度；但二者都要回答相同种类的问题。区别在证据门槛，不在于低风险项目可以假装风险不存在。

二、用“不确定性向量”理解生命周期

为了避免把流程背成术语表，可以把项目的未知量压缩成五类：

U= ( U价值, U边界, U结构, U集成, U运行 ) U=(U_{\text{价值}},U_{\text{边界}},U_{\text{结构}},U_{\text{集成}},U_{\text{运行}})
  • 价值不确定性：这个问题是否真实，解决后是否产生足够收益？
  • 边界不确定性：系统应做什么、不做什么，什么结果才算正确？
  • 结构不确定性：数据、组件和接口怎样组织，关键取舍是什么？
  • 集成不确定性：局部代码组合后，是否仍满足行为与质量要求？
  • 运行不确定性：真实环境、流量、故障和长期变化会怎样影响系统？

生命周期各阶段不是把同一件事重复七遍，而是在压低不同坐标上的不确定性。某阶段可以结束，意味着这一坐标的剩余风险低于当前项目愿意承担的阈值，并且有可复核的证据。

这也直接解释了 Vibe Coding 的边界：它主要降低“把局部意图翻译成代码”的成本，有时还能用原型降低价值和交互不确定性；但它不会仅凭代码生成速度就自动降低其余四类未知量。

三、发现：判断问题是否真实、是否值得做

本阶段解决价值、可用性、可行性与现实约束的不确定性。
常见失败因为“技术上能做”就默认“有人需要”。

3.1 先研究现在发生了什么

发现阶段不是给已有想法寻找赞美，而是调查用户当前怎样完成任务、哪里真正痛苦、痛苦出现多频繁、现有替代方案为何不够。产品社区常用价值、可用性、可行性与商业可行性四类风险检查想法；对于个人内部工具，“商业可行性”可以改写为维护成本、平台规则、隐私和持续使用意愿。

贯穿案例：语料转 HTML 插件。

“我想做一个把文章转成漂亮 HTML 的插件”还不是问题定义。更好的起点是：现有语料在手机通勤阅读时，公式渲染、层级导航和长表格频繁失效；手工修复每篇需要 30 分钟；目标是把稳定转换时间降到 3 分钟以内，并保持内容不被第二次改写。

3.2 本阶段的产物不是功能清单

  • 目标用户与具体任务；
  • 现有工作流和可观察痛点；
  • 问题规模、频率与基线成本；
  • 成功指标与停止条件；
  • 最危险的假设，以及验证这些假设的低成本实验。

原型在这里很有价值，但它是实验仪器，不是半成品。它用于回答“这种交互能否让读者更快掌握结构”“自动布局是否比固定模板更稳”，而不是因为原型能点几下就宣布产品成立。

结束门槛：可以进入规格阶段，当且仅当——
  • 能够指出明确用户、明确任务和可观察痛点；
  • 有至少一种来自真实行为的证据，而不只有口头认可；
  • 成功指标、失败条件和不做的理由都可陈述；
  • 价值最高且风险最大的假设已经被验证，或被明确登记为后续风险。

这并不要求先做大规模市场调研。个人工具可能只需观察自己一周；涉及付费用户或组织流程时，证据门槛才相应提高。

四、规格：把愿望转成可判断真假的行为约束

本阶段解决“大家口中的同一句话是否指同一个系统”。
常见失败功能名看似明确，异常路径、质量要求和边界全靠猜。

4.1 需求不是“做一个上传功能”

需求必须使未来的结果可以被判断。Joel Spolsky 在经典的《Painless Functional Specifications》中区分了面向用户行为的功能规格与描述内部实现的技术规格。这个区分今天依然重要：先固定系统应该表现为什么，再讨论如何实现。

完整规格至少包括四类内容：

  1. 功能行为：正常输入、操作和输出；
  2. 失败行为：空文件、超大文件、非法公式、写入失败时发生什么；
  3. 质量属性：速度、可靠性、安全、可访问性、兼容性、可维护性；
  4. 边界与优先级：第一版做什么、明确不做什么、以后可能做什么。

4.2 把模糊词改成验收条件

模糊要求问题可验收改写
生成速度要快 “快”没有尺度 对 20,000 字、20 个公式的语料，在指定测试机器上 95% 转换于 10 秒内完成
HTML 要好看 审美无法直接测试 桌面与 390px 宽度无页面级横向溢出；标题层级、目录、代码块与表格满足模板规范
不要修改内容 “修改”边界不明 允许拆分段落和添加导航；禁止改写论点、公式、例子与引用；转换前后正文文本差异生成报告

验收条件不必把所有实现钉死。它固定的是可观察行为和不可违反的约束，为设计留下选择空间。

4.3 可追踪性：每个实现为什么存在

成熟项目会保留一条轻量映射：

用户问题 → 需求编号 → 设计决策 → 实现变更 → 测试证据 → 运行指标

“可追踪”不是要求巨大表格，而是当某个测试失败或某段代码无人理解时，能够反查它服务于哪个约束。AI 生成大量代码时，这条链反而更重要，因为“生成得出来”不能解释“为何应该存在”。

结束门槛：可以进入设计阶段，当且仅当——
  • 核心用户流程与关键失败路径都已写出；
  • 每条核心需求可以通过演示、测试或指标判断；
  • 性能、安全、数据、兼容性等质量属性不是空白；
  • 第一版边界、明确排除项和优先级已经确定；
  • 未决问题有负责人或验证计划，而不是藏在模糊语言里。

  2. 为什么一个能运行的 Vibe Coding 原型不能证明需求阶段已经结束？

1. 它首先只是方案请求。需要继续问：用户要完成什么任务、为什么现有 HTML/打印功能不够、使用频率与失败成本是什么。

五、设计：把行为约束变成可演化的系统结构

本阶段解决组件、数据、接口与质量属性怎样共同成立。
常见失败把技术栈名称当架构，或在没有风险分析时追求“完整设计”。

5.1 架构不是文件夹树

架构关心的是那些错误后代价高、影响范围大或难以回退的决策：系统边界、数据归属、组件责任、接口协议、部署形态、一致性策略、安全边界。具体类名和函数通常属于更局部的设计。

Google 的设计文档实践强调目标、实现策略、关键决策及其取舍，也要求考虑安全、隐私、存储等横切问题。设计文档的价值不是预言未来所有代码，而是让高代价决策在编码前接受挑战，并留下“当时为什么这样选”的记录。

5.2 五张最小地图

  1. 边界图：插件、主项目、模型服务、文件系统分别负责什么；
  2. 组件图：输入解析、内容计划、页面生成、校验、保存怎样分工；
  3. 数据图：原始语料、结构化中间状态、HTML、资产和日志由谁拥有；
  4. 流程图：一次生成请求如何流过各组件，失败怎样返回；
  5. 部署图：哪些部分在用户本机、主项目进程、远程模型或浏览器中运行。
案例中的关键决策。

如果 HTML 只是导出物，而结构化文档才是源文件，那么“用户局部修改页面”应先改结构化块，再重新渲染 HTML。若反过来直接编辑 HTML，下一次生成就可能覆盖人工修改。这不是 CSS 细节，而是源数据归属的架构决策。

5.3 用实验处理高风险设计

设计阶段不需要证明所有实现细节，但必须优先攻击最危险的假设。例如：

  • 模型能否稳定输出符合 Schema 的结构化文档？
  • MathML 在目标阅读环境是否可靠？
  • 两层嵌套是否足以表达常见语料结构？
  • 一次生成 30,000 字 HTML 是否超过模型或宿主限制？

这种为降低技术风险而写的短实验常称为 spike。它与产品原型不同：产品原型验证用户与交互假设，技术实验验证架构可行性。两者的代码通常都允许抛弃。

5.4 ADR：记录决定，而不是记录所有思考

架构决策记录（Architecture Decision Record，ADR）通常只需说明：背景、决定、替代方案、理由、后果和状态。它解决的是半年后团队只看到“用了某方案”，却不知道当时约束是否仍成立的问题。

结束门槛：可以进入有计划的构建，当且仅当——
  • 关键请求流、数据流、状态变化与外部依赖可以完整走读；
  • 组件责任和接口边界明确，不依赖同一个“万能模块”；
  • 性能、安全、可靠性和可维护性要求有相应设计策略；
  • 最危险的技术假设已有实验结果；
  • 高代价决策记录了替代方案与取舍；
  • 仍未决定的事项不会阻塞下一小批实现。

六、切片：把大设计变成可以快速验证的小闭环

本阶段解决先做什么、怎样限制在制品与集成风险。
常见失败按技术层横向分工，直到最后一天才第一次得到可运行系统。

6.1 垂直切片优于“先把后端全写完”

一个垂直切片从用户入口穿过必要组件，到达一个可观察结果。例如第一片不是“完成所有解析器”，而是“输入一段无公式 Markdown，生成带标题和正文的本地 HTML，并能在浏览器打开”。第二片再加入目录，第三片加入公式，第四片加入移动端校验。

这样安排有三个效果：

  • 每一片都能验证需求、架构与集成，而非只证明局部代码存在；
  • 错误方向只浪费一个小批次；
  • 变更更容易审查、回滚和交给 AI 处理。

Google 的工程实践也强调小而自包含的变更，因为它们更容易推理、审查、合并和回滚。DORA 则把小批量工作视为持续交付的重要基础。

6.2 Definition of Done 不是任务名称

“实现公式渲染”只是任务目标。完成定义应同时包含行为、测试、文档和运行准备，例如：

  • 行内与块级公式都转换为 MathML；
  • 指定公式样例在桌面和手机宽度下通过渲染检查；
  • 非法公式返回定位信息，不生成静默错误页面；
  • 自动测试加入流水线；
  • 转换约束写入开发文档。
结束门槛：某个实现批次可以开始，当且仅当——
  • 该批次有单一、可演示的用户或系统结果；
  • 输入、输出、依赖与验收条件明确；
  • 规模足够小，几小时到数天内能完成并集成；
  • 优先级由风险和价值决定，而不只是“哪个模块好写”；
  • 完成定义包含测试、文档、可观测性或迁移要求。

七、构建：产出的是可审查、可集成的变更，不只是代码

本阶段解决怎样把一小块已知意图可靠地编码进现有系统。
常见失败把“本机能跑”当作“工程实现完成”。

7.1 编码只是构建的一部分

一次成熟变更通常同时涉及源代码、测试、配置、数据库迁移、依赖、构建脚本、接口文档和日志。构建系统要保证同一版本能被重复构造成同一类产物；版本控制要使每个变更可追踪、可比较、可回退。

2026 年 Thoughtworks 的文章《What Is Code?》指出，代码既是给机器的指令，也是问题领域的概念模型。AI 让“产生机器指令”变便宜，却没有使名称、边界、不变量和共享理解失去价值。相反，清晰代码还会成为下一次模型工作的高质量上下文。

7.2 代码审查审的不是格式

审查要检查：

  • 变更是否真的满足对应需求；
  • 设计是否与现有边界一致；
  • 异常、并发、资源释放和数据迁移是否正确；
  • 测试是否覆盖真正风险，而非只追求数字；
  • 可读性、可维护性、安全与性能是否退化；
  • 是否引入不必要依赖或扩大变更范围。

Google 的代码审查标准把目标概括为“让代码库整体健康度随时间改善”，而非追求一次提交的绝对完美。这也解释了为什么大量生成代码会形成新的瓶颈：生成速度可以远高于人类建立理解和责任的速度。

结束门槛：一个代码变更可以合并，当且仅当——
  • 构建、静态检查和相关自动测试通过；
  • 验收条件逐项有实现或测试证据；
  • 至少一位有责任能力的人完成审查；
  • 变更足够小，影响范围可以解释；
  • 配置、迁移、文档和观测点同步更新；
  • 没有未解释的高风险警告，也没有以“AI 生成”为理由跳过理解。

自检二：设计、切片和构建的边界

  1. “使用 React + SQLite + Docker”为什么还不能称为架构设计？
  2. AI 一次生成了完整插件且所有单元测试通过，为什么仍不能直接进入发布？
展开参考答案

1. 它只列出技术选择，没有说明系统边界、组件责任、数据归属、接口、质量属性策略及取舍。

2. 单元测试只验证被测试的局部行为；还需检查组件集成、真实依赖、验收流程、性能与安全，并建立可重复发布、监控和回滚能力。

八、验证：把“我觉得能用”变成分层证据

本阶段解决实现是否满足规格，以及规格是否真的解决用户任务。
常见失败只测试开发者想到的正常路径，或把测试数量当可信度。

8.1 Verification 与 Validation

Verification：是否按规格造对

Schema 是否遵守？错误输入是否拒绝？公式是否正确转换？性能是否达到阈值？

Validation：规格中的产品是否值得使用

读者是否真的更容易理解文章？生成流程是否比原工作流省时？结果是否符合真实阅读任务？

测试通过主要提供 Verification 证据；真实用户试用、可用性观察和运行指标提供 Validation 证据。二者缺一都会出现“正确实现了错误产品”或“看起来有用但内部不可靠”。

8.2 为什么需要不同层次的测试

证据层回答的问题案例
单元测试一个函数或小模块在受控输入下是否满足局部规则标题层级转换、文件名规范化
集成测试真实组件、数据库、文件系统或外部服务连接后是否仍正确解析器输出能否被渲染器完整消费
契约测试接口双方对字段、错误和版本的理解是否一致主项目传入的任务对象与插件 Schema
端到端测试从真实入口到最终结果的关键旅程是否成立选择语料→生成→保存→浏览器打开
非功能测试速度、安全、容量、可访问性和故障恢复是否达标大文件、恶意 HTML、移动端溢出、磁盘写满
探索性测试规格没有预见的失败方式是什么混合公式、异常编码、极深列表、长链接

测试金字塔不是“单元测试越多越好”的教条，而是提醒团队：快速、定位清楚的低层测试应承担大部分重复反馈，少量高层测试确认真实链路。真正的覆盖对象应是风险和行为，不只是代码行。

8.3 质量门槛必须与规格相连

如果需求说“不得改写原文”，验证就要比较内容；如果设计说“HTML 是导出物”，验证就要确保重新渲染可重复；如果发布要求可回滚，测试就要覆盖旧版本恢复。脱离需求与设计的测试，容易只证明开发者写下的实现与自己相符。

结束门槛：候选版本可以进入发布，当且仅当——
  • 核心需求与测试/演示证据之间有清晰映射；
  • 关键用户旅程和失败路径通过；
  • 性能、安全、数据完整性与兼容性达到预设阈值；
  • 已知缺陷被分级，剩余风险由有权负责的人接受；
  • 在接近生产的环境中完成必要验证；
  • 没有用“测试都绿了”掩盖未测试的真实风险。

九、发布：控制从旧状态到新状态的变化

本阶段解决怎样把正确候选版本安全、可重复地交给真实环境。
常见失败把“构建成功”误当作“用户已安全获得新版本”。

9.1 构建、发布与部署是三件事

  • 构建：从源代码和依赖产生版本化制品；
  • 发布：决定某个制品已获准供目标用户或环境使用；
  • 部署：把制品和配置实际安装到运行环境。

小工具中三者可能由一个命令完成，但逻辑上仍不同。区分它们后，才能回答“线上到底运行哪个版本”“这个版本由什么源码和依赖产生”“出现问题怎样退回”。

9.2 CI/CD 解决的是反馈与可重复性

持续集成（CI）要求成员频繁合并小变更，并由自动构建和测试尽快发现集成错误。持续交付进一步让通过验证的版本随时具备安全发布条件。它们不是某个云服务名称，而是缩短反馈时间、减小批次和降低发布风险的工程机制。

Google SRE 的发布工程实践强调可重复构建、版本化制品、自动测试、金丝雀发布和回滚。风险越高，发布越应渐进；低风险本地插件也至少应保留版本、备份和失败恢复。

9.3 发布计划关注“出错后怎么办”

  • 配置和密钥由谁提供，是否与代码分离；
  • 数据库或文件格式如何迁移，是否向后兼容；
  • 先给少量用户还是一次性全部启用；
  • 上线后看哪些指标和日志；
  • 触发回滚的条件是什么，回滚是否真的可执行；
  • 用户数据在回退时如何保持一致。
结束门槛：一次发布可以宣布完成，当且仅当——
  • 生产制品与已验证制品是同一个可追踪版本；
  • 部署、配置和迁移过程可重复，关键步骤不依赖临场记忆；
  • 上线后冒烟测试与关键指标正常；
  • 回滚或前向修复路径可用；
  • 监控、告警、运行手册和责任人已经就位；
  • 发布记录能够回答“何时、由谁、改变了什么”。

十、运行：软件真正开始接受现实检验

本阶段解决真实负载、真实失败和长期变化下怎样持续提供价值。
常见失败项目把上线视为终点，故障与维护交给“未来的自己”。

10.1 监控不是收集所有日志

监控应围绕用户可感知的服务状态：成功率、延迟、吞吐、资源饱和、关键任务完成率。Google SRE 用服务水平指标（SLI）度量行为，用服务水平目标（SLO）表达可接受范围。个人插件也可以有轻量 SLO，例如“99% 合法语料能生成可打开 HTML”“转换失败不得损坏原文件”。

日志回答一次事件发生了什么，指标回答系统整体趋势，追踪回答请求如何跨组件流动，告警则决定何时需要人介入。把四者混成“多打印几行日志”，无法支持故障定位。

10.2 事故与复盘把运行证据送回设计

发生故障后，目标不只是修复当前症状，还要理解：

  • 哪个假设不成立；
  • 为何测试与审查没有提前发现；
  • 为何影响扩大；
  • 监控何时发现，是否足够快；
  • 应修改需求、架构、测试、发布还是运行手册。

这正是生命周期形成闭环的地方：生产故障不是运维阶段的孤立问题，而是前面某类证据不足的表现。

10.3 维护与演化占据软件的大部分生命

软件会面对新需求、依赖升级、平台规则变化、安全漏洞、数据增长和人员更替。重构、技术债治理、兼容策略、弃用与迁移都属于工程工作。项目真正的终点不是“最后一个功能上线”，而是系统退役、用户迁移、数据按规则保留或删除、责任被正式解除。

“运行阶段结束”需要分两层理解：
  • 一次版本稳定：核心指标达到目标，严重故障关闭，遗留问题进入计划；
  • 整个产品结束：替代方案就绪，用户和数据完成迁移，外部依赖与权限撤销，文档和责任完成归档。

只要仍有真实用户、数据或外部依赖，维护责任就没有因为“暂时不开发新功能”而消失。

自检三：为什么上线不是完成

  1. 一个本地插件没有服务器，是否就不需要运行阶段？
  2. 测试全部通过但没有回滚能力，发布阶段是否完成？
展开参考答案

1. 仍需要，只是门槛更轻。操作系统升级、依赖变化、文件损坏、隐私、错误日志、版本恢复和用户反馈都属于运行与维护问题。

2. 没有。验证说明候选版本满足已测试约束；发布还要控制真实环境状态变化，并能在失败时恢复。

十一、全生命周期完成标准总表

下面这张表是本文对“每部分解决什么问题，到什么程度算结束”的压缩回答。实际项目可以并行或迭代这些活动，但不应跳过相应问题。

十二、引入 Vibe Coding：先把词义说清

12.1 严格定义来自“不再关心代码”

Andrej Karpathy 在 2025 年提出这个词时，重点不是“用自然语言让 AI 写代码”，而是“forget that the code even exists”：总是接受变更、不读 diff、把报错继续交给模型，直到运行效果看起来满意。他同时把适用情境限定在可抛弃的周末项目。

Simon Willison 随后专门指出：所有 Vibe Coding 都是 AI 辅助编程，但并非所有 AI 辅助编程都是 Vibe Coding。如果开发者审查生成代码、充分测试并能够解释它，这仍是软件开发，只是实现工具发生了变化。

本文采用的严格定义：Vibe Coding 是一种由人描述效果、模型生成和修改实现、人主要通过运行结果而非代码与工程证据来反馈的开发方式。其区分标准不是是否用了 AI，而是人是否放弃了对内部实现的直接理解与验证责任。

12.2 为什么不能把 Agent 编程都叫 Vibe Coding

同一个编码 Agent 可以在三种完全不同的制度中工作：

工作方式人的输入验证方式责任状态
Vibe Coding 效果描述与连续修正 “看起来能用” 内部实现基本不被理解
AI 辅助编程 具体任务、代码上下文、约束 读 diff、测试、审查 开发者对变更负责
Agentic Engineering 规格、计划、仓库规则与质量门 自动反馈回路 + 人类风险审查 人设计并治理执行系统

三者可能使用同一模型和编辑器。真正不同的是规格强度、反馈信号与责任结构。

十三、Vibe Coding 真正擅长解决什么

13.1 把“试一个想法”的边际成本压低

传统上，一个交互想法可能因为搭环境、写样板和查 API 而不值得验证。Vibe Coding 能迅速做出可操作原型，让人更早看到真实界面和行为。在发现阶段，这会提升实验数量，尤其适合比较页面结构、信息层级和交互流程。

但正确姿势通常是“借原型学习，然后重新决定是否保留”，不是默认把实验代码一路推到生产。

13.2 个人、一次性、低后果自动化

例如一次性清洗公开 CSV、给本地照片生成索引、制作只在浏览器沙箱运行的小计算器。它们的共同特征是：

  • 错误影响范围小；
  • 结果容易人工检查；
  • 数据有备份或可重建；
  • 没有密钥、支付、敏感隐私和外部用户；
  • 未来无人维护也不会造成持续损失。

13.3 已知模式的界面与胶水代码

表单、CRUD 页面、格式转换、API 适配和样板配置常有大量公开范式。模型在这些任务上容易产生一个不错的起点。对熟悉系统的工程师，它还能把机械实现交给模型，把注意力留给边界和风险。

13.4 学习与建立直觉

初学者可以通过“提出需求—运行—观察—追问”快速接触可计算对象；有经验的开发者则能用低风险实验认识模型在哪些任务上稳定、在哪些地方会循环犯错。这里的学习价值不要求产物成为长期软件。

适合严格 Vibe Coding 的六个判据：
  1. 失败后果低；
  2. 正确性容易从外部观察；
  3. 变更容易撤销；
  4. 生命周期短或允许整体重写；
  5. 数据、权限和费用风险低；
  6. 没有多人协作与长期维护负担。

六项越不满足，越应从 Vibe Coding 升级为有规格、有测试和有责任人的 AI 辅助工程。

十四、它不能替代什么：生成代码不等于消除不确定性

14.1 不能决定该解决哪个问题

模型可以总结访谈、列风险和生成原型，但它不能凭空创造真实用户行为证据，也不能替你承担投入机会成本。若起点是错误问题，更快生成只会更快堆积无价值软件。

14.2 不能自动消除需求歧义

“支持导入 Word”“不要修改内容”“生成效果要专业”都包含大量隐含决定。模型必须选择一种解释才能继续生成；若人不显式澄清，歧义不会消失，只会被偷偷固化成代码。

14.3 不能仅靠局部反馈完成架构取舍

架构选择涉及未来变化、数据归属、团队能力、成本、安全与故障影响。模型能提出方案，但无法单凭“页面跑起来了”判断哪个长期代价可接受。局部可运行性对系统级正确性是很弱的证据。

14.4 不能替代生产验证与责任

生成代码可能通过已有测试，却绕过测试没有表达的约束。安全、隐私、无障碍、迁移、容量和灾难恢复常需要专门证据。部署后真正承担损失的是用户和维护者，不是模型。

14.5 不能自动形成共享概念模型

代码不仅驱动机器，也承载团队对领域的共同理解。若每次修改都由模型在无人理解的代码上继续叠加，系统会积累“认知债务”：外部功能暂时可用，但人和模型都越来越难预测改动影响。最终，任何小需求都变成全库搜索、试错和回归。

最危险的误判：把“生成阶段没有遇到困难”当成“整个项目没有风险”。Vibe Coding 经常把成本从编码前移走，却把它后移到审查、集成、故障和维护；这些成本出现得晚，因此在原型阶段很容易被忽略。

十五、从 Vibe Coding 到 AI 辅助工程：AI 可以贯穿流程，但不能取消门槛

把 Vibe Coding 的边界看清后，不应走向另一个极端——认为 AI 只能写一点样板代码。更合理的结构是让 AI 在七个环节中承担候选生成、信息整理和机械执行，而由人定义目标、证据与风险阈值。

环节AI 适合承担仍需人的判断或现实证据
发现 整理访谈、归纳痛点、生成原型与实验方案 接触真实用户；判断证据质量与机会成本
规格 把散乱想法改写为场景、失败路径和验收条件 确认意图、优先级、政策和不可让渡约束
设计 提出备选架构、检查遗漏、生成图和 ADR 草稿 选择取舍；核验平台现实；承担长期后果
构建 检索代码、实现小切片、重构、补文档和测试 控制范围；审查语义；确认概念模型一致
验证 生成测试、执行工具、归类失败、寻找边界情况 判断测试是否测到真实风险；进行独立安全/用户验证
发布 生成流水线、检查清单、发布说明与自动化脚本 授权变更；控制密钥、数据迁移和回滚决策
运行 分析日志、关联异常、起草复盘与修复候选 定义 SLO；判断事故影响；对用户与业务负责

15.1 从“人盯每一行”转向“人设计反馈回路”

2026 年 Martin Fowler 站点上的《Humans and Agents in Software Engineering Loops》提出一个有用区分：人不一定要永远逐行介入最内层代码循环，但应“站在循环之上”，设计规格、质量检查和反馈机制。另一个相关概念是 harness engineering：给 Agent 提供规则、参考资料、静态分析、测试、日志和浏览器等传感器，使错误尽量在到达人类前自我暴露。

这不是绕开传统工程，恰恰是把传统工程的可执行部分编码进 Agent 的工作环境：

规格与约束（前馈） → Agent 生成 → 编译/测试/静态分析/运行观测（反馈） → 自动修正 → 人审查高风险决定

真正前沿的变化不是“不要测试，模型自己会修”，而是把测试、架构约束和运行证据变成模型可以及时读取的闭环。

十六、为什么“代码生成更快”不必然等于“项目交付更快”

16.1 总交付时间不是打字时间

T总= T发现+ T规格+ T设计+ T生成+ T审查+ T验证+ T发布+ T返工与事故 T_{\text{总}}=T_{\text{发现}}+T_{\text{规格}}+T_{\text{设计}}+T_{\text{生成}}+T_{\text{审查}}+T_{\text{验证}}+T_{\text{发布}}+T_{\text{返工与事故}}

AI 直接压低的是其中若干项，尤其是生成时间。若生成量同时扩大，审查、集成和返工可能上升；若小批量、自动测试和清晰规格也同步改善，总时间才更可能下降。

16.2 实证结果为什么看似矛盾

METR 2025 随机对照研究：

16 名熟悉大型开源仓库的开发者完成 246 个真实任务，允许使用当时的 AI 工具时平均多花 19% 时间。研究者强调这只是早期 2025、成熟仓库、高质量要求这一特定情境，不能外推到所有开发者与任务。

METR 2026 更新：

后续数据出现了加速迹象，但参与者选择退出“禁用 AI”的实验条件、任务选择偏差和并行 Agent 计时困难，使估计不可靠。研究团队认为 2026 工具很可能比 2025 更有帮助，却没有给出可信的统一加速比例。

DORA 的组织层结论：

2025 年报告把 AI 描述为“放大器”：基础系统健康时放大优势，批次过大、反馈慢、治理弱时也会放大问题。此前的生成式 AI 报告还观察到更高 AI 使用与较差的交付吞吐和稳定性相关，并把大批量生成、审查压力和反馈回路不足列为解释。相关性不等于单一因果，但它否定了“局部生成速度自动转化为组织吞吐”的简单推论。

这些结果并不证明 AI 无效。它们说明“AI 是否提速”不是模型的单一属性，而是任务类型、代码库成熟度、隐含要求、开发者经验、上下文质量、批次大小和验证系统共同决定的函数。

十七、给个人与小团队的三模式流程

你不需要把每个小工具都做成大公司的流程，也不应把每个项目都当周末原型。最实用的办法是在开始前明确选择模式，并在风险变化时升级。

模式适用条件最低工程门槛代码处置
A：探索性 Vibe Coding 低后果、无敏感数据、可人工检查、可随时重做 隔离环境、备份、费用上限、明确实验问题 默认可抛弃；不要无审查升级为生产
B：AI 辅助小工具 自己长期使用，错误有损失但可恢复 简明规格、版本控制、关键测试、日志、安装与恢复说明 读关键 diff；能解释核心数据和控制流
C：生产工程 他人使用、敏感数据、付费、联网、合规或高维护成本 完整风险驱动生命周期、分层验证、审查、CI/CD、监控、回滚与责任人 生成代码与人工代码使用同一质量标准

17.1 推荐的双循环

探索循环：快速且允许抛弃

问题假设 → Vibe 原型 → 用户/自己试用 → 学到什么 → 修改问题与规格。

它优化学习速度，不承诺代码资产。

交付循环：小批量且证据驱动

可验收规格 → 风险设计 → 小切片 → Agent 实现 → 自动验证 → 人审查 → 渐进发布 → 运行反馈。

它优化可持续交付，不追求一次生成全部。

17.2 语料转 HTML 插件应该怎样分配 AI

  1. 先用 Vibe Coding 探索：快速生成三种自学页面，观察哪种能减少回翻和移动端阅读负担；原型可以完全抛弃。
  2. 固定规格：明确 HTML 是导出物还是源文件、允许怎样改写内容、公式和资产怎样保存、删除语义是什么。
  3. 做风险设计：确定结构化中间格式、渲染器边界、模型输出 Schema、失败恢复和主项目接口。
  4. 让 Agent 实现小切片：一次只增加一个可验收能力，自动运行格式校验、快照、链接和移动端检查。
  5. 人审高风险项：内容是否被篡改、数据是否丢失、主项目集成是否污染状态、删除是否可恢复。
  6. 从运行中改进：记录失败样例，把可自动判断的问题沉淀成测试和规则，而不是每次重新提醒模型。
最终不是“传统开发还是 Vibe Coding”的二选一：探索阶段允许高自由度生成；一旦代码开始承载他人数据、长期维护或真实责任，就逐步把发现、规格、设计、测试、发布和运行机制接回来。AI 越能生成，越值得把验证做成机器可执行的反馈回路。

综合自检：判断应使用哪种模式

你准备做一个工具：读取自己的聊天记录，调用付费模型总结，再自动覆盖项目中的长期记忆文件。界面和主要流程已经能通过 Vibe Coding 跑通。它能否继续按模式 A 使用？至少要补哪些工程环节？

展开参考答案

不能。它涉及隐私、外部 API 费用、持久文件覆盖和长期信息污染，失败影响不低且不一定容易从界面观察。至少应升级到模式 B；若给他人使用，则接近模式 C。

需要补：数据与隐私边界、费用和速率限制、输入/输出规格、覆盖前备份、幂等与并发设计、失败恢复、内容差异与人工确认、关键测试、日志与审计、版本回滚，以及模型或接口变化后的维护策略。

十八、结论压缩

  1. 传统软件开发不是一条僵硬流水线，而是七类不可回避的问题：发现、规格、设计、构建、验证、发布、运行。
  2. 每个阶段的结束标准都是风险与证据，而不是文档或会议数量。
  3. 敏捷、迭代和持续交付没有删除这些环节，只是让它们在小批量反馈循环中反复发生。
  4. 严格的 Vibe Coding 是不审查内部代码、主要凭外部效果迭代的开发方式。它适合低风险、易验证、可逆、短生命周期的项目。
  5. Vibe Coding 最擅长降低原型和局部实现成本，不能自动解决价值、需求歧义、架构取舍、生产验证和长期责任。
  6. AI 辅助工程比 Vibe Coding 广得多。AI 可以参与全生命周期，但应由规格、工具、测试、监控和人类风险判断形成约束闭环。
  7. 代码生成更快不等于交付更快。总效果取决于批次大小、审查、集成、返工和运行风险是否同时被控制。

用一句话概括：

Vibe Coding 降低“把想法暂时变成程序”的门槛；软件工程负责把这个程序变成值得构建、可以验证、敢于发布并能够长期承担责任的软件。

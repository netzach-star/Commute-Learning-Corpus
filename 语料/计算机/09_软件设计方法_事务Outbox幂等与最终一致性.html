一、为什么“数据库保存成功，再发一个任务”不是可靠流程

先设想一个最朴素的发布函数：

publish(document, newContent):
    newVersion = database.insert_version(newContent)
    database.set_current(document.id, newVersion.id)
    queue.send(RebuildProjection(document.id, newVersion.id))
    return success

看起来顺序合理：先保存，再通知 worker。但计算机系统的每一步之间都可能发生进程崩溃、机器断电、网络超时或依赖服务不可用。

崩溃位置数据库队列结果
插入版本前旧状态无任务请求失败，通常可重试
插入版本后、更新 current 前可能留下孤立版本无任务是否可接受取决于事务边界
更新 current 后、发任务前新版本已激活无任务永久缺少投影重建
任务发送后、客户端收到成功前新版本已激活已有任务客户端重试可能再次发送

第三行是最危险的缝隙：业务状态已经改变，但系统中没有任何持久记录告诉后台“还欠一次重建”。进程重启后无法仅从当前状态判断任务是否已经发过。

可靠系统的关键不是承诺“程序不会在那一行崩溃”，而是让任意一行崩溃后，仍然能从持久状态判断接下来该做什么。

二、事务究竟保证什么：把一组数据库变化变成一个可见决定

1. 原子性不是“所有系统一起成功”

数据库事务通常保证：事务内的数据库写入要么一起提交，要么一起回滚。以文档发布为例，可以把下面内容放在同一 PostgreSQL 事务中：

  • 插入不可变的新 DocumentVersion；
  • 更新 Document.current_version_id；
  • 记录修订元数据；
  • 插入一条 outbox 事件。

若其中任何一步在提交前失败，事务回滚，外部读者仍看到旧 current。这对应 D-03 的“commit 前失败无 current 变化”。

但数据库事务不能自动把外部消息队列、文件系统、搜索服务和远程 API 都纳入同一个本地原子提交。若你在事务内调用外部服务，会遇到：

  • 远程服务成功，但本地事务随后回滚；
  • 远程调用超时，实际可能已成功，调用者不知道；
  • 长时间等待外部服务，数据库锁被长期持有；
  • 不同系统没有共同事务协调协议。

2. 提交点是一条语义边界

COMMIT 之前新版本、current 变化和 outbox 对其他事务不可视或尚未成立；失败可以整体撤销。
COMMIT 成功系统正式承诺“这个业务变化存在”，同时也承诺“有一条持久化工作意图等待处理”。
COMMIT 之后后台工作可以延迟、重试甚至换机器执行，但不应丢失。

因此，事务不负责完成所有派生工作，而负责把“业务事实”和“后续工作意图”一起可靠地写入。

三、双写问题：为什么两个看似可靠的写入合在一起就不可靠

所谓 dual write，不是指在数据库里更新两张表——同一数据库事务可以原子处理多张表。它通常指一次业务操作必须写入两个不能共享原子事务的系统，例如：

  • 数据库 + 消息队列；
  • 数据库 + 搜索索引；
  • 数据库 + 对象存储；
  • 数据库 + 外部 SaaS API。

无论顺序怎样安排，都至少有一个故障窗口：

先写数据库，再发消息

数据库成功后消息可能失败，导致下游永远不知道变化。

先发消息，再写数据库

消息成功后数据库可能失败，下游处理一个并不存在的业务事实。

“失败就重试”也不够，因为超时意味着结果未知：第一次可能已经成功，只是确认响应丢了。盲目重试会产生重复。这就是为什么 outbox 与幂等必须一起出现。

四、Transactional Outbox：把外部发送改造成可恢复的内部状态机

1. 核心结构

在业务数据库中增加一张 outbox 表或等价事件存储。一次发布事务大致做：

BEGIN;
  INSERT INTO document_version (...);
  UPDATE document SET current_version_id = :new_version;
  INSERT INTO outbox (
      event_id,
      event_type,
      aggregate_id,
      aggregate_version,
      payload,
      status
  ) VALUES (..., 'DocumentPublished', ..., 'pending');
COMMIT;

之后由 relay/worker 独立执行：

读取已提交且 pending 的 outbox
→ 投递消息或创建 projection job
→ 记录已投递/已处理状态
→ 失败则重试

由于业务变化和 outbox 行处于同一事务：

  • 事务失败：两者都不存在；
  • 事务成功：两者都存在；
  • worker 崩溃：outbox 仍在，其他 worker 可继续；
  • 服务重启：扫描 pending/超时任务恢复。

2. Outbox 解决了什么，没有解决什么

问题Outbox 是否解决还需要什么
数据库成功但通知永久丢失基本解决可靠 relay、监控 backlog
消息重复投递不会自动消除幂等消费者、去重键
不同事件顺序不会自动保证全部全局顺序按 aggregate/version 排序与冲突策略
下游处理永久失败不会自动修复业务错误重试预算、死信、人工修复
所有系统瞬时一致不保证接受并设计最终一致窗口

AWS 对 Transactional Outbox 的官方说明同样强调：它用于解决数据库写入与事件通知的双写不一致，但消息可能重复，因此消费者仍应设计为幂等。

3. Relay 如何安全抢任务

多个 worker 并行时，需要避免大家长期处理同一行。常见方案包括：

  • 事务内用行锁领取一批任务，并使用 SKIP LOCKED 跳过已被其他 worker 领取的行；
  • 将状态从 pending 原子更新为 processing，并记录 lease 到期时间；
  • 使用数据库变更流/CDC 读取已提交事件；
  • 不在“读取后标记”之间留下无保护竞争。

具体选择依赖数据库和吞吐要求，但必须回答：worker 在处理前、处理中、处理后崩溃，各自怎样恢复。

五、幂等：为什么“至少一次”交付要求重复也安全

1. 为什么无法简单承诺只执行一次

考虑 worker 已经成功创建 projection job，但在把 outbox 标记为 done 前崩溃。恢复后，它看到 outbox 仍是 pending，于是再次处理。系统无法从“没有收到确认”判断第一次究竟失败还是已成功。

实际工程中更稳健的承诺通常是：

  • 任务不会静默丢失；
  • 任务可能被处理多次；
  • 多次处理的可观察结果等同于一次。

最后一条就是幂等性。

2. 幂等不是“代码里先查一下”

若 projection job 的逻辑唯一键是：

(document_id, target_version, projection_type)

则数据库应建立唯一约束。消费者创建任务时使用原子插入/冲突处理：

INSERT projection_job (...)
VALUES (...)
ON CONFLICT (document_id, target_version, projection_type)
DO NOTHING;

即使两个 worker 同时处理同一 outbox，数据库也只允许一个逻辑任务存在。应用层的“SELECT 后再 INSERT”无法独自防止并发竞争。

3. 三层幂等

层次幂等键示例保护什么
命令层client_request_id客户端超时重试不重复创建业务版本
事件消费层event_id同一 outbox 事件重复交付不重复执行副作用
投影构建层document + version + projection type同一版本的同一种派生物只有一个当前构建任务/结果
不要把幂等误解为“所有重复请求都返回完全相同的 HTTP 文本”。更重要的是业务效果不被重复叠加，例如不会多生成一个版本、不会多增加一次修订、不会多发一份发布记录。

六、不可变对象、current 指针与 projection：为什么旧 serving 应继续可读

1. 区分源对象与派生对象

项目片段提到“不可变对象”“current”“projection job”“旧 serving”。可以用一个通用模型理解：

DocumentVersion不可变的源版本；一旦发布，其内容不原地改写。
Current Pointer声明哪个源版本是当前业务版本。
Projection根据某个源版本生成的 Bundle、Markdown、索引或页面数据。
Serving Pointer声明当前对外提供哪一份已经完成且验证过的投影。

源版本 current 与 serving projection 不一定必须在同一瞬间切换。假如新版本已经被业务接受，但构建 Markdown 需要十秒，可以有两种策略：

  • 强一致发布：所有投影先构建成功，再一次切换业务 current；
  • 异步发布：业务 current 先提交，旧 serving 暂时继续提供，完成后再切换 serving pointer。

D-03 的“旧 serving 继续可读”更接近第二种安全降级：不能因为新投影未完成，就让读者得到 404、空页面或半成品。

2. 为什么不可变版本有利于恢复

  • worker 可以随时根据 version id 重新构建，不依赖不断变化的当前内容；
  • 失败后知道目标输入究竟是哪一版；
  • 回滚可以切回旧指针，而不是试图反向修改一大堆字段；
  • 并发发布可通过版本号和前置条件检测冲突。

代价是需要管理版本生命周期、存储增长、垃圾回收和“哪个指针代表哪种 current”。设计文档必须明确命名，避免 current 同时指源内容、投影和搜索索引的不同状态。

七、逐点故障演练：系统在每个崩溃位置应该留下什么

故障点允许留下的持久状态恢复动作用户可见行为
事务开始前无新状态客户端可安全重试仍读旧版本
事务内任一步失败全部回滚修复错误或重试current 不变化
COMMIT 成功后 API 进程崩溃新版本 + current + outbox客户端重试通过 request id 去重；worker 继续不会多生成版本
worker 领取前崩溃pending outbox其他 worker 扫描旧 serving 可读
worker 构建中崩溃processing/lease 或仍 pendinglease 过期后重试旧 serving 可读
投影已写入，完成标记前崩溃可能已有同版本投影幂等写入或覆盖同一确定键不会出现两份活跃投影
投影完成，切换 serving 前崩溃新投影 ready、旧 serving active恢复任务执行原子指针切换短暂仍见旧内容
切换成功，确认响应丢失新 serving active重复切换必须幂等最终看到新内容

故障注入不应只“杀进程一次”

一个可信实验应记录：

  • 在哪个精确提交点注入失败；
  • 重启后扫描到哪些 outbox/job；
  • 重试次数与最终状态；
  • 数据库唯一约束是否触发；
  • 是否存在孤立 current、重复 projection 或不可读窗口；
  • 日志、指标和 trace 是否能解释恢复过程。

八、并发、唯一约束与死锁：事务不是自动正确

1. 事务内仍会有并发冲突

两个事务可以同时尝试发布同一文档，或同时从 A、B 两端修改同一关系。设计必须选择语义：

  • 后提交者覆盖前者；
  • 检测版本冲突并拒绝；
  • 可以自动合并某些字段；
  • 命令按文档串行化。

这不是数据库隔离级别能替你决定的产品语义。数据库提供锁、版本和约束，设计者仍需定义什么算冲突。

2. 乐观并发控制

更新命令可以携带 expected_revision：

UPDATE document
SET current_version_id = :new, revision = revision + 1
WHERE id = :id AND revision = :expected;

若影响行数为零，说明文档已被其他事务修改，调用者应重新读取或进入冲突处理。HTTP 层可用 ETag/If-Match 表达类似语义。

3. 死锁与统一锁顺序

事务 T1 锁 A 等 B，事务 T2 锁 B 等 A，就形成死锁。PostgreSQL 文档建议所有事务以一致顺序获取同一组对象的锁。对于无向关联，可先 canonicalize 端点，再按稳定顺序锁定两端。

数据库通常能检测死锁并中止一个事务，但“数据库会处理”不等于设计完成。应用需要：

  • 尽量减少死锁概率；
  • 把被中止事务视为可重试错误；
  • 确保重试具有幂等键；
  • 监控死锁频率，发现设计退化。

九、怎样分阶段实现并证明 D-03 通过

阶段 A：先固定不变量

  • commit 前失败时 current 不改变；
  • 每个已提交、需要派生工作的版本都有至少一条持久工作意图；
  • 同一逻辑 projection job 至多一条；
  • 未 ready 的新投影不能替换稳定 serving；
  • 所有重试不会重复增加业务修订。

阶段 B：单进程实现事务与 outbox

先不接真实消息队列，只让本地 worker 扫描 outbox。验证提交和回滚边界，避免同时调试太多系统。

阶段 C：实现幂等 worker

建立 projection 唯一键、状态机、lease/重试规则和确定性输出路径。对同一 event 连续消费十次，结果仍只产生一个逻辑 projection。

阶段 D：加入进程崩溃与并发

在事务前后、worker 各阶段注入崩溃；启动多个 worker；同时发布同一文档或反向修改 link；检查死锁与重复。

阶段 E：加入真实外部依赖与监控

接真实对象存储、索引或队列，记录：

  • outbox backlog；
  • 事件从提交到投影 ready 的延迟；
  • 重试和死信数量；
  • 幂等冲突次数；
  • 旧 serving 持续时间；
  • 按 document/version 串联的 trace。

OpenTelemetry 将 traces、metrics 与 logs 视为主要可观测信号；在这类异步链路中，事件 id、document id、version 和 job id 应能跨服务关联。

通过 D-03 的证据不应只有“测试绿了”。还应保存故障注入矩阵、数据库快照或查询、重复消费记录、恢复延迟，以及设计结论：采用何种事务边界、幂等键和 serving 切换语义。

十、自检题与参考答案

问题 1：为什么数据库事务不能直接保证消息队列发送成功？
参考答案

本地数据库事务只原子管理其参与的数据库状态。外部队列通常不与其共享同一提交协议；调用可能成功、失败或超时未知，因此会留下双写窗口。

问题 2：Outbox 的关键不是“多一张表”，而是什么？
参考答案

把业务变化与后续工作意图放进同一原子提交，使事务成功后一定存在可恢复的待处理记录，事务失败时两者都不存在。

问题 3：为什么 outbox 之后仍需要幂等？
参考答案

relay 或 worker 可能在副作用成功、确认状态写回前崩溃，因此恢复后会重复处理。可靠方案通常至少一次交付，消费者必须让重复具有同一业务效果。

问题 4：“旧 serving 继续可读”保护什么？
参考答案

保护可用性和原子发布体验：新投影构建失败或延迟时，系统仍提供最后一个完整稳定版本，而不是空白或半成品。

问题 5：唯一约束能完全避免死锁吗？
参考答案

不能。唯一约束保护重复记录；死锁来自多个事务以不同顺序等待彼此持有的锁。还要统一锁顺序、缩短事务并正确重试。

问题 6：“Exactly once”为什么常被称为一种端到端效果，而不是简单传输属性？
参考答案

消息基础设施即便减少重复，也无法覆盖消费者在副作用完成与确认之间崩溃的所有情况。最终业务只生效一次通常依赖唯一键、幂等写和状态机的共同设计。

本篇结论

D-03 要证明的是一条端到端不变量链：提交前没有半状态；提交后工作意图不丢；重复处理不重复产生业务效果；新派生物未完成时旧 serving 仍稳定可读。事务、outbox、幂等和不可变版本不是四个独立名词，而是共同封闭一次异步发布的全部故障窗口。

你现在的起点：已经知道 Docker 大概用于“把程序和运行环境一起打包”，但尚未建立内部机制，也没有实际运行过容器。本篇因此不从命令手册开始，而从一个现实失败开始：为什么同一份代码在你的电脑上能运行，交给别人却常常失败？

一、Docker 到底解决什么问题：代码不是一个可以独立运行的东西

开发者常说“把代码发给你了”，但一段代码真正运行时，依赖的不只是源文件。它还隐含依赖：

  • 操作系统及其内核能力；
  • 语言运行时，例如 Python、Node.js 或 Java 的具体版本；
  • 系统动态库、编译工具与证书；
  • 第三方依赖包；
  • 环境变量、配置文件和启动命令；
  • 数据库、缓存、消息系统等外部服务；
  • 目录权限、网络端口和文件位置。

所以“在我的电脑上能跑”只能证明：代码与我电脑当前环境的组合能跑。它没有证明同一份代码在同事电脑、测试服务器和生产机器上也能跑。

Docker 的核心价值不是“虚拟出一台小电脑”，而是把应用运行所需的文件系统、启动方式和隔离配置描述成可重复构建、可分发、可启动的对象。

从工程角度看，Docker 主要提供五种能力：

可重复构建

用 Dockerfile 描述环境，不靠“我记得安装过什么”。

可分发

把镜像推送到 Registry，其他机器按相同内容拉取。

进程隔离

让不同应用看到相对独立的进程、网络和文件系统视图。

生命周期管理

统一创建、启动、停止、删除、查看日志和限制资源。

多服务编排

用 Compose 一次声明应用、数据库、网络与持久化卷。

环境一致性

开发、测试和 CI 尽量使用同一份镜像与启动契约。

注意“尽量”二字。容器仍然依赖宿主机 CPU 架构、内核、存储和网络；它不是把所有现实差异彻底抹平，而是把大量原本散落在机器里的环境差异收束为明确配置。

二、先看完整系统地图：Docker 不是一个单独程序

docker CLI接收你的命令
→
Docker API传递请求
→
dockerd管理对象
→
containerd / runc管理并启动容器进程
→
Linux 内核提供 namespace、cgroup、网络与文件系统

横向箭头表示控制请求；镜像层、挂载和网络配置会在创建容器时一并交给运行时。Docker 官方文档把 Engine 描述为客户端—服务器结构：CLI 通过 API 控制长期运行的 daemon，daemon 管理镜像、容器、网络和卷。

当你输入：

docker run --name demo -p 8080:80 nginx:alpine

终端里执行的 docker 只是客户端。真正长期管理容器的是 Docker daemon，即 dockerd。现代 Docker Engine 还使用 containerd 管理容器生命周期，默认再由符合 OCI 规范的 runc 创建底层容器进程。

部件主要职责不应误解为
Docker CLI把命令转换成 API 请求，展示结果容器本身
Docker daemon管理镜像、容器、网络、卷和构建任务你的应用进程
Registry保存和分发镜像，例如 Docker Hub 或私有仓库正在运行的服务器
containerd / runc管理生命周期并调用内核机制创建进程普通初学操作必须直接使用的命令
Linux 内核真正提供进程、namespace、cgroup、挂载和网络能力Docker 自己重新实现的操作系统
macOS 和 Windows 上的特殊点：Linux 容器需要 Linux 内核。Docker Desktop 会在轻量 Linux 虚拟机中运行 Docker Engine，再把端口、文件和 API 请求转接到宿主机。因而在 Mac 上输入 Docker 命令时，CLI 看起来在本机，真正的 Linux 容器进程却位于 Docker 管理的 VM 中。

三、镜像、容器和仓库：最容易混淆的三个对象

1. 镜像不是“压缩后的容器”

镜像（image）是一个只读、可分层、可分发的应用模板。它包含文件系统内容以及默认启动命令、环境变量、工作目录等元数据。

镜像更接近“程序运行环境的不可变版本”，而不是一个已经在运行的系统。你可以从同一个镜像创建许多彼此独立的容器。

2. 容器是一个受隔离的运行实例

容器（container）可以理解为：镜像的只读层 + 一个容器自己的可写层 + 网络、挂载、资源限制等运行配置 + 至少一个正在运行或曾经运行的进程。

Docker 官方入门文档直接强调：容器本质上是在宿主机上运行的进程，只是它拥有独立的文件系统、网络和进程树视图。容器停止后，进程结束，但容器对象及其可写层可以暂时保留；容器被删除后，未放进卷或绑定挂载的数据通常也随之删除。

3. Registry 是镜像仓库服务

docker pull nginx:alpine 中：

nginx镜像仓库名；省略 Registry 时通常从默认仓库解析。
alpinetag，表示一个人为命名的镜像版本标签。tag 不是不可变化的数学身份。

镜像真正的内容身份通常由 digest 表示。生产系统若要求严格可重复性，会更关注不可变 digest，而不是可能被重新指向的 tag。

类比Docker 对象类比的边界
类的定义镜像镜像还携带完整文件系统层，不只是代码结构
类的实例容器容器是进程与隔离配置，不是普通内存对象
包仓库RegistryRegistry 分发的是镜像层和元数据

四、一次 docker run 内部发生什么

现在沿着下面的命令走一遍：

docker run -d --name hello-web -p 127.0.0.1:8080:80 hello-docker:v1

步骤 1：CLI 解析参数并调用 Docker API

docker 客户端不会自己创建 namespace。它把“基于什么镜像、叫什么名字、怎样映射端口、是否后台运行”等参数发送给 daemon。

步骤 2：daemon 检查镜像是否存在

若本地没有 hello-docker:v1，daemon 会尝试从 Registry 拉取；若镜像由你刚刚构建，则直接使用本地镜像层。

步骤 3：准备容器文件系统

Docker 将镜像的只读层叠在一起，并在最上方创建该容器独有的可写层。容器进程看到的是合并后的完整目录树，而不是一堆分散层。

步骤 4：准备隔离与资源控制

运行时为进程配置多个 Linux namespace，使其看到独立的进程编号、网络设备、挂载点、主机名等；同时可配置 cgroup，限制或统计 CPU、内存等资源。

步骤 5：准备网络和端口转发

容器接入 Docker 网络，获得内部地址。参数 -p 127.0.0.1:8080:80 表示：只在宿主机回环地址的 8080 端口监听，把连接转发到容器的 80 端口。

步骤 6：应用挂载和环境配置

若命令带有 --mount、-v 或环境变量参数，Docker 在启动进程前完成对应挂载与配置。

步骤 7：启动镜像规定的主进程

镜像的 ENTRYPOINT 与 CMD 共同决定默认进程。这个进程在容器中通常成为 PID 1。它结束时，容器通常就进入停止状态。

步骤 8：收集状态、标准输出和退出码

Docker 记录容器状态，并通过日志驱动处理进程的标准输出和标准错误。docker logs 不是进入容器翻日志文件，而是在读取 Docker 所收集的日志流。

CLI 参数镜像、端口、挂载
→
API 请求发送给 daemon
→
容器配置文件系统、网络、资源
→
内核运行创建隔离进程
→
可观察结果端口、日志、退出码

五、容器隔离的操作系统原理：不是模拟硬件，而是限制进程的视野

1. Namespace：让进程看到“自己的世界”

Linux namespace 把原本全局的内核资源包装成不同视图。一个 namespace 中的进程看起来拥有自己的资源实例，而另一组进程看见另一套视图。容器常用的隔离包括：

namespace隔离内容容器内的直观效果
PID进程编号和进程树容器只看到自己的进程，主进程可能显示为 PID 1
mount挂载点和文件系统视图容器看到自己的根目录
network网卡、IP、路由、端口空间每个容器可以拥有自己的 eth0 和内部 IP
UTS主机名与域名容器可以有独立 hostname
IPC共享内存、信号量等进程间通信默认不与其他容器共享 IPC 对象
user用户和组编号映射容器内 root 可映射为宿主机非特权用户

关键不是“容器里真的存在另一套内核”，而是同一个 Linux 内核根据进程所属 namespace 返回不同视图。

2. cgroup：隔离视野之外，还要控制资源

仅靠 namespace，一个容器仍可能耗尽整台机器的内存或 CPU。控制组（cgroup）用于统计、限制和分配进程组资源。例如：

docker run --memory 256m --cpus 0.5 some-image

这类参数最终需要内核 cgroup 执行。Docker 提供易用接口，但资源控制不是 Docker 凭空创造的。

3. 为什么容器通常比虚拟机轻

维度容器传统虚拟机
隔离层次操作系统进程与内核资源视图虚拟硬件与完整 guest OS
内核多个容器通常共享宿主 Linux 内核每台 VM 有自己的 guest 内核
启动主要是创建进程与隔离配置需要启动完整操作系统
镜像体积主要包含用户态文件通常包含完整系统磁盘
隔离强度通常弱于独立 VM，需谨慎配置虚拟化边界通常更强
“容器轻量”不等于“容器天然安全”。容器共享内核，错误的特权模式、危险挂载、暴露 Docker socket 或有漏洞的内核都可能破坏隔离。不要把 Docker 当作绝对安全沙箱。

六、分层文件系统与写时复制：为什么镜像可以复用

Docker 镜像由多层组成。Dockerfile 中会改变文件系统的指令通常产生新的层。假设：

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY app.py .
CMD ["python", "app.py"]

可以粗略理解为：

基础层Python 用户态环境
+
依赖描述层requirements.txt
+
依赖安装层site-packages
+
应用代码层app.py

多个镜像若共享相同基础层，本地只需存一份内容。构建时，如果某一层的输入没有变化，构建器也可能复用缓存。

写时复制（copy-on-write）

镜像层保持只读。容器若要修改来自下层的文件，存储驱动会先把该文件复制到容器的可写层，再修改副本。Docker 官方对经典 overlay2 存储驱动的描述就是：查找下层文件、执行 copy_up、随后只修改上层副本。

这解释了三个现象：

  • 从同一镜像启动多个容器很快，因为它们共享只读层；
  • 每个容器仍可拥有自己的修改，因为最上层可写层不同；
  • 不应把数据库长期数据只放在容器可写层，因为删除容器会删除该层。
Docker 新版本还支持由 containerd snapshotter 管理镜像和容器数据。初学阶段不必记住存储后端产品清单，但要记住稳定抽象：镜像由不可变内容层构成，容器获得自己的可写视图；持久数据应脱离容器生命周期。

七、容器网络与端口映射：容器里的 80 端口不等于你电脑的 80 端口

1. 容器拥有独立网络 namespace

容器内的应用可以监听 0.0.0.0:80，但这个 80 端口位于容器自己的网络空间。宿主机浏览器不会自动知道如何连接它。

2. -p 发布端口

docker run -p 127.0.0.1:8080:80 nginx:alpine
127.0.0.1只允许宿主机本地连接；省略时常会绑定所有宿主机接口。
8080宿主机端口，浏览器访问 localhost:8080。
80容器端口，Nginx 在容器内部监听。

因此 8080:80 不是“把容器端口改成 8080”，而是创建一条外部入口到内部端口的转发关系。

3. 用户自定义 bridge 网络与服务发现

同一宿主机上的多个容器通常接入 bridge 网络。Docker 官方文档指出，用户自定义 bridge 会为容器提供按名称解析。Compose 默认也会为一个应用创建网络，并让各服务通过服务名发现彼此。

所以第二个项目中，Web 应用连接 Redis 时写：

REDIS_HOST=redis

这里的 redis 不是你电脑的 DNS 域名，而是 Compose 服务名。Docker 网络内部 DNS 会把它解析到 Redis 容器当前地址。不要把容器 IP 硬编码进代码，因为容器重建后 IP 可能变化。

4. EXPOSE 不等于发布

Dockerfile 中的 EXPOSE 80 主要表达镜像预期使用哪个端口，是一种元数据和文档。它本身不会自动让宿主机访问容器；真正发布端口仍需 -p 或 Compose 的 ports。

八、容器数据为什么会消失：可写层、volume 与 bind mount

方式数据由谁管理典型用途主要风险
容器可写层随容器对象管理临时文件、缓存、可丢弃输出删容器即丢，难以迁移和备份
named volumeDocker 管理宿主机存储位置数据库、Redis、应用持久数据容易忘记清理；需单独备份策略
bind mount直接使用宿主机指定路径开发源码、配置、需要人工编辑的文件强依赖宿主目录结构和权限；可能把敏感目录暴露给容器

Docker 官方建议：由容器生成并使用的持久数据通常优先考虑 volume；开发时把本地源码即时映射进容器，bind mount 更直观。

volume 的生命周期独立于容器

docker volume create demo-data
docker run --mount type=volume,src=demo-data,dst=/data some-image

删除这个容器后，demo-data 仍可保留并挂给新容器。第二个项目会用这个机制保存访问计数。

bind mount 是宿主目录的直接入口

docker run --rm \
  --mount type=bind,src="$PWD",dst=/usr/share/nginx/html,readonly \
  -p 127.0.0.1:8080:80 nginx:alpine

此时容器看到的网页目录直接来自当前宿主目录。你修改 index.html，容器立刻看见变化；但容器也因此依赖本地目录位置和权限。

挂载会遮蔽容器目标目录原有内容。如果你把一个空目录挂到应用目录，镜像里原先复制进去的文件会暂时不可见。初学者常把这个现象误以为镜像文件被删除了。

九、Dockerfile 与构建缓存：把手工安装过程变成可重复说明书

1. Dockerfile 描述的是构建过程

Dockerfile 不是启动脚本，也不是容器清单。它的主要产物是镜像。常见指令：

指令作用初学注意
FROM选择基础镜像基础镜像也是依赖，应考虑版本与来源
WORKDIR设置后续操作和默认运行目录比反复 cd 清楚
COPY从 build context 复制文件不是任意读取整台电脑
RUN构建期间执行命令并形成结果层容器运行时不会再次自动执行
ENV设置镜像默认环境变量不要把密钥写进镜像层
EXPOSE声明预期容器端口不等于宿主端口发布
CMD提供默认启动命令或参数运行时可覆盖
ENTRYPOINT定义镜像主要可执行入口与 CMD 的组合需单独理解

2. build context 为什么存在

docker build -t hello-docker:v1 .

最后的点表示当前目录是构建上下文。构建器可以从这个上下文读取被 COPY 引用的文件。若把整个大型项目、虚拟环境、Git 历史和密钥都放入上下文，构建会变慢，也可能造成泄漏。因此使用 .dockerignore 排除无关内容。

3. 构建缓存为何要求把稳定部分放前面

下面这种顺序：

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .

意味着仅修改 app.py 时，依赖描述未变，安装依赖的层更可能复用缓存。若一开始就 COPY . .，任何代码变化都可能使后续依赖安装层失效。

4. 镜像不是源代码版本控制替代品

Git 记录源代码历史；镜像记录某次构建产物。二者应通过 commit、CI 构建和镜像标签/digest 建立关联，而不是只保留一个“latest”镜像就认为版本管理完成。

十、为什么需要 Docker Compose：一个应用通常不止一个容器

真实应用可能需要：

  • Web 服务；
  • 数据库；
  • 缓存；
  • 后台任务 worker；
  • 共享网络、环境变量和持久数据。

若全靠多条 docker run，你必须手工记住网络、名字、端口、挂载和启动顺序。Compose 让你在一个 YAML 文件中声明应用栈的服务、网络和卷，然后用统一命令管理生命周期。

services:
  web:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      REDIS_HOST: redis
    depends_on:
      - redis

  redis:
    image: redis:7-alpine
    volumes:
      - counter-data:/data

volumes:
  counter-data:

这里的抽象关系是：

service一种长期角色的运行定义
→
container该 service 的具体实例
→
network服务间通信范围
→
volume脱离容器的持久数据
depends_on 主要表达启动依赖，不自动证明下游服务已经可用。Redis 容器进程已启动，不代表它恰好已准备接受请求。因此第二个项目的 Web 程序包含短暂重试；更正式的系统还会使用 healthcheck 和更明确的恢复策略。

Compose 不是什么

Compose 很适合单机开发、测试和小规模部署，但它不是自动跨多台机器调度、故障迁移和扩缩容的完整集群编排器。那是 Kubernetes、Swarm 或云平台编排系统要解决的另一层问题。

十一、Docker 的边界与常见误解

误解 1：容器就是轻量虚拟机

容器主要隔离进程并共享内核；在 Mac/Windows 上虽然背后有 Linux VM，但每个容器并非各自启动一台 VM。

误解 2：镜像能保证处处完全一致

CPU 架构、宿主内核、外部服务、时钟、网络和挂载仍会造成差异。

误解 3：把程序放进容器就安全了

镜像漏洞、root 权限、特权容器、敏感挂载和暴露 daemon socket 都可能带来严重风险。

误解 4：每个进程都应该拆成容器

拆分边界应跟随部署、扩展、故障和所有权需要，不是为了增加容器数量。

误解 5：数据库放进 volume 就完成备份

volume 只改变生命周期，不自动提供一致性备份、异地恢复或灾难演练。

误解 6：Compose 文件就是生产架构

它描述单机应用栈，但生产还涉及安全、秘密管理、监控、容量、升级和回滚。

什么时候 Docker 反而可能增加成本

  • 只有一个极简单的本地脚本，且没有环境分发需求；
  • 应用强依赖图形桌面、特殊硬件或复杂宿主集成；
  • 团队没有维护镜像、安全更新和存储清理的能力；
  • 把容器化当作架构重构替代品，试图用 Docker 掩盖应用本身的问题。

十二、微型项目一：把一个静态网站构建成自己的镜像

目标：在 30—60 分钟内亲手经历“Dockerfile → image → container → port → logs → inspect → stop/remove”，建立最小闭环。

1. 项目文件

01-static-site/
├── Dockerfile
├── .dockerignore
└── index.html

Dockerfile：

FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80

index.html 可以是任意简单页面。配套压缩包中已经提供完整版本。

2. 构建镜像

cd 01-static-site
docker build -t hello-docker:v1 .

观察输出中哪些步骤执行，哪些步骤显示缓存命中。然后检查：

docker image ls
docker image inspect hello-docker:v1

3. 启动容器并访问

docker run -d \
  --name hello-web \
  -p 127.0.0.1:8080:80 \
  hello-docker:v1

浏览器打开 http://localhost:8080。

4. 不只看结果，要观察内部对象

docker ps
docker logs hello-web
docker top hello-web
docker exec hello-web nginx -T
docker inspect hello-web

你要回答：

  • 容器使用哪个镜像？
  • 容器主进程是什么？
  • 宿主端口与容器端口各是多少？
  • 容器加入了哪个网络？
  • 为什么在容器内看到 Nginx 配置，却不需要在宿主机安装 Nginx？

5. 修改页面，理解镜像不可变

编辑 index.html 后刷新浏览器，你会发现运行中的容器没有变化，因为文件已经在构建时复制进镜像。重新构建：

docker build -t hello-docker:v2 .
docker run -d --name hello-web-v2 -p 127.0.0.1:8081:80 hello-docker:v2

同时访问 8080 和 8081，你会看到两个版本并存。这比“直接覆盖服务器目录”更接近不可变交付思路。

6. 清理

docker stop hello-web hello-web-v2
docker rm hello-web hello-web-v2
docker image rm hello-docker:v1 hello-docker:v2

7. 加餐：用 bind mount 体验开发模式

docker run --rm \
  --mount type=bind,src="$PWD",dst=/usr/share/nginx/html,readonly \
  -p 127.0.0.1:8080:80 \
  nginx:alpine

这次修改本地 HTML 会立即影响容器。比较两种模式：

模式文件来源适合
构建进镜像镜像不可变层交付、测试、发布、版本并存
bind mount宿主当前目录本地开发与即时编辑
项目一验收标准：你不仅能打开网页，还能用自己的话解释 build 产生什么、run 产生什么、8080:80 的两端分别属于谁，以及为什么修改源文件不会自动修改已经构建的镜像。

十三、微型项目二：Flask + Redis 访问计数器

目标：在 1—2 小时内体验两个容器如何通过 Compose 网络互相发现、为什么只有 Web 服务发布端口、数据如何通过 named volume 脱离容器生命周期。

1. 项目结构

02-counter-compose/
├── app.py
├── requirements.txt
├── Dockerfile
├── compose.yaml
└── .dockerignore

2. 应用逻辑

Web 容器收到请求后，对 Redis 中的 visits 加一，再返回 JSON。关键连接代码是：

redis_client = Redis(
    host=os.getenv("REDIS_HOST", "redis"),
    port=6379,
    decode_responses=True,
)

默认主机名是 redis，与 Compose 的 Redis 服务名一致。

3. Compose 文件

services:
  web:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      REDIS_HOST: redis
    depends_on:
      - redis

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - counter-data:/data

volumes:
  counter-data:

逐项解释：

web.build根据当前目录 Dockerfile 构建 Web 镜像。
web.ports只有 Web 服务需要让宿主浏览器访问，因此发布 8000。
REDIS_HOST=redis通过 Compose 内部 DNS 使用服务名连接。
redis.image直接使用现成 Redis 镜像，不必自己重写其 Dockerfile。
counter-data命名卷挂到 Redis 数据目录，使数据不随容器重建消失。

4. 启动整个应用

cd 02-counter-compose
docker compose up --build -d
docker compose ps

多次访问：

curl http://localhost:8000/
curl http://localhost:8000/
curl http://localhost:8000/

返回中的 visits 应逐次增加。

5. 观察日志、网络和数据

docker compose logs -f web
docker compose exec redis redis-cli GET visits
docker network ls
docker volume ls

还可以查看 Compose 创建的具体网络：

docker network inspect 02-counter-compose_default

实际网络名前缀通常来自项目目录，也可用 docker compose ls 和 docker compose ps 确认，不必死记示例名。

6. 验证“容器可替换，数据仍存在”

docker compose down
docker compose up -d
curl http://localhost:8000/

down 会删除 Compose 创建的容器和默认网络，但默认不删除命名卷。重新创建 Redis 容器后，访问计数应延续。

7. 再验证删除 volume 的后果

docker compose down -v
docker compose up -d
curl http://localhost:8000/

这次计数应重新开始，因为 -v 删除了命名卷。这个实验比背诵“volume 用于持久化”更重要：你亲眼看到了容器生命周期和数据生命周期的分离。

8. 故障实验

停止 Redis：

docker compose stop redis
curl http://localhost:8000/

Web 请求会失败。然后恢复：

docker compose start redis
curl http://localhost:8000/

这说明 Compose 解决了“怎样声明和启动多个服务”，但不会让依赖故障自动消失。应用仍需超时、重试、健康检查、降级和错误处理。

项目二验收标准：你能解释为什么 Web 可以通过 redis:6379 连接数据库、为什么 Redis 无需发布宿主端口、为什么 down 后计数保留而 down -v 后重置，以及 Compose 解决了哪些问题、没有解决哪些问题。

全文压缩：Docker 没有把应用变成一台小型虚拟机。它把应用文件和启动契约做成分层镜像，由 daemon 调用容器运行时，借助 Linux namespace、cgroup、挂载和网络创建一个受隔离的进程；volume 把数据生命周期从容器中分离，Compose 再把多个容器组织成一个可重复启动的应用栈。

十五、自检题与参考答案

1. 镜像和容器最核心的区别是什么？

镜像是只读、可分发的模板；容器是基于镜像创建的运行实例，额外拥有可写层、网络、挂载、资源配置和进程状态。

2. 为什么说容器不是完整虚拟机？

Linux 容器通常共享宿主内核，主要通过 namespace 改变进程看到的资源视图，并用 cgroup 控制资源；传统 VM 则虚拟硬件并启动独立 guest OS 内核。

3. -p 8080:80 两个端口分别属于谁？

8080 属于宿主机监听入口，80 属于容器网络 namespace 内应用监听端口。Docker 建立转发。

4. 为什么删除容器后数据库数据可能消失？

若数据只写在容器可写层，该层随容器删除；使用 volume 或适当 bind mount 才能把数据生命周期与容器分开。

5. 为什么 Dockerfile 中先复制 requirements，再复制应用代码？

依赖描述变化频率通常低于应用代码。这样代码修改时更可能复用依赖安装层缓存，减少重复下载和安装。

6. Compose 中 Web 为什么用主机名 redis？

Compose 默认网络提供按服务名的内部 DNS。服务可以使用稳定名字通信，而不用依赖重建后可能变化的容器 IP。

7. EXPOSE 80 为什么不能代替 -p？

EXPOSE 主要声明镜像预期端口；-p 才在宿主机创建可访问的发布入口。

8. Docker 解决了哪些问题，却没有解决哪些问题？

它擅长可重复构建、镜像分发、进程隔离、生命周期与单机多服务组织；不会自动解决应用架构、数据备份、安全漏洞、跨机器调度、容量、监控和灾难恢复。

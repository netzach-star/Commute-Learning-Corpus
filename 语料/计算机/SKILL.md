# 计算机语料规则

先遵循项目根目录 `SKILL.md`，再应用本文件。

## 1. 动态学习画像

最后整理：2026-07-25。以下状态随学习推进更新。

### 已确认基础

- 数学系本科阶段，数学训练较强，但不得据此推断已经熟悉软件工程术语和行业流程；
- 熟悉常见编程语言、常规编码与 Git；
- 已学习 408 基础课程，包括数据结构、操作系统、计算机网络和计算机组成原理；
- 能开发小工具和 Agent 类项目，不需要从编程语法入门重新讲起；
- 知道 Docker 大致用于打包应用及其运行环境、提高环境一致性，但尚未系统理解其内部原理，也没有实际操作经验。

### 当前薄弱点

- 主要短板不是某一门基础课，而是把模糊想法逐步变成成熟软件项目的工程经验；
- 不能默认熟悉产品分析、用户研究、需求规格、架构决策、测试策略、验收、发布、交付和维护中的行业术语与隐含流程；
- 缺少现代软件开发、产品设计、工程协作、文档体系、测试发布与长期运维的系统经验；
- 数学能力和 AI 工具经验不能作为计算机工程术语已经掌握的证据。

### 当前学习主线

- 从背景与问题确认开始，逐步学习用户与需求分析、市场和产品价值判断、系统设计、实施、测试、验收、发布和维护；
- 理解代码库时，建立黑盒、灰盒和白盒三个层次；
- 学会把工程阶段写成 AI 可以执行、验证和验收的明确规格；
- 通过 Docker 等微型项目补足“知道用途但未建立机制与实操经验”的工具能力；
- 将具体项目经验抽象为可迁移的系统模型、设计原则、故障模型和验证方法。

## 2. 画像更新规则

用户说明已经掌握某个工程阶段、正在推进某类项目、完成某项实践、暴露新的薄弱点或改变学习目标时：

1. 在同一轮更新本节并修改日期；
2. 使用“已确认基础 / 正在学习 / 当前不应默认 / 当前目标”等清楚状态；
3. 删除与用户最新陈述冲突的旧判断，不保留互相矛盾的快照；
4. 不因用户能写代码、会用 Git、做过 AI 项目，或仅仅读过一篇文章，就推断其已经具备未确认的软件工程经验；
5. 不得把数学成熟度外推为软件工程术语经验。

## 3. 目标、难度与质量基线

计算机文章优先帮助读者建立可迁移的系统模型，而不是记住产品名和工具清单。提高难度应表现为：

- 给出完整的问题分解与依赖关系；
- 解释设计机制、权衡、不变量和失败模式；
- 明确结论在什么条件下成立、何时失效；
- 给出足以支持判断的真实工程细节与证据；
- 将方法放回完整生命周期或系统结构中；
- 说明如何通过测试、日志、指标、故障注入或实验验证理解。

不得用未解释的缩写、框架名、职位名和流程术语制造“难度”。软件术语不熟不等于应把理论深度和信息密度降为浅层科普；需要降低的是术语跳跃、跨段依赖和无谓上下文切换。

## 4. 先建立系统模型

解释系统、工具或技术板块时优先回答：

1. 它解决什么问题，边界在哪里；
2. 有哪些层或组件；
3. 每个组件负责什么、不负责什么；
4. 组件间传递什么数据、控制信息和状态；
5. 一次完整请求或任务怎样流经系统；
6. 哪些接口和不变量负责解耦；
7. 外部副作用、故障传播和恢复路径是什么；
8. 替代方案、设计取舍和失效条件是什么；
9. 如何通过测试、日志、指标或实验验证理解。

工具与软件名称只有在帮助解释结构、接口或取舍时才出现，不用产品清单代替知识结构。

系统结构主题优先追踪：

- 控制流；
- 数据流；
- 状态变化；
- 外部副作用；
- 组件边界与接口；
- 不变量；
- 失败传播与恢复路径。

## 5. 从具体行为到抽象结构

- 先展示一个可观察、低复杂度的具体行为，再命名组件、接口、依赖、状态、测试等抽象概念；
- 全文优先使用一个读者熟悉、复杂度可控的真实工程案例贯穿，新概念在同一案例中逐步增加；
- 不要每讲一个概念就更换案例；
- 新术语首次出现时就地解释，并立即指出它在案例中对应什么；
- 缩写、框架名和工具名若不是理解主线所必需，只作为可选标签；
- 保持工程深度，但降低术语跳跃和上下文切换。

概念密集或全景文章在正文展开前先交代整体结构：有哪几个核心部分、它们之间是什么关系、主线怎么走。用一两段文字或一个简单列表说清即可，不需要画关系图。

## 6. 工程阶段必须解释“为什么”

讲产品或软件项目流程时，对每个阶段尽量完整回答：

1. 它要消除什么不确定性、避免哪类失败；
2. 输入是什么；
3. 需要完成哪些具体工作；
4. 产出物是什么，或改变什么系统状态；
5. 产出物怎样被下一阶段使用；
6. 用什么证据判断结果可信；
7. 达到什么可观察门槛算结束并可以进入下一阶段；
8. 过早结束、跳过或设计错误会出现什么症状与返工；
9. 常见替代方案及其取舍是什么。

遇到市场评估、需求、架构、验收等术语时，先用具体问题与案例解释，再给正式名称。

## 7. 黑盒、灰盒与白盒

- **黑盒**：安装、配置、输入输出、外部可观察行为和失败方式；
- **灰盒**：主要模块、扩展点、数据路径、状态持有者和运行时观察方法；
- **白盒**：控制流、数据流、状态流、不变量、关键实现和安全修改方式。

目标是维护或修改项目时，至少结合静态阅读与动态验证，说明入口、调用链、状态持有者、外部边界、特征测试和变更影响面。

## 8. 完整例子、状态与验收

贯穿案例尽量覆盖：

- 从需求到组件划分；
- 接口和数据结构；
- 正常路径与失败路径；
- 状态机、不变量与并发；
- 测试、日志和可观测性；
- 一次设计变更怎样传播；
- 最终怎样证明项目达到目标。

代码只用于验证关键机制，不让大量样板代码挤占结构解释。

讲述可靠性时不能只写成功路径。至少检查：

- 调用前失败留下什么状态；
- 调用成功但确认丢失时怎样判断；
- 重试是否会产生重复副作用；
- 长期失败时是阻断、降级还是继续服务旧结果；
- 恢复是否来自持久状态；
- 日志、指标和 trace 是否足以解释恢复过程。

## 9. 资料与证据要求

对软件工程、架构、测试、部署、运维和 AI 辅助开发等具有成熟社区讨论的主题，生成前主动检索资料。

资料优先级：

1. 当前国际标准、正式规范与权威知识体系；
2. 官方工程手册、原始研究和一手数据；
3. 长期被开发社区引用的原始文章或经典书籍作者文章；
4. 有明确作者、案例和论证过程的前沿工程文章。

不要用搜索聚合页、营销软文、无作者转载或只罗列工具的 SEO 文章支撑核心结论。

文末参考资料必须：

- 提供直接原地址；
- 简述该资料支撑本文哪一部分；
- 区分标准、实证研究、组织经验、个人观点和本文推断；
- 对相互冲突或具有时效性的研究说明适用范围，不选择性只保留支持本文立场的结果。

外部能力和架构假设不得只写“应该可以”。应区分：

- 已确认事实；
- 设计决定；
- 待验证假设；
- 开放问题。

技术实验或 Spike 必须绑定会受结果影响的设计决策，并规定客观通过标准、失败后的备选路线和证据保存位置。

## 10. 计算机与 AI 的边界

AI 可以作为计算机文章的案例或工具。若移除 AI 后，项目生命周期、架构、测试、部署、文档或产品方法仍完整成立，文章归入“计算机”。若移除模型、Agent、Skill、AI 使用或人机协作后主题失去核心对象，归入 AI。

涉及 Vibe Coding、编码 Agent 等混合主题时，必须区分：

- 严格意义的 Vibe Coding；
- 负责任的 AI 辅助编程；
- 以规格、工具和自动验证治理 Agent 的 AI 辅助工程。

不得把三者混成“AI 写代码”，也不得因 AI 提高局部代码生成速度就推断完整交付流程已经被替代。

## 11. 自检与交付检查

每完成 2—3 个核心环节插入一次局部自检。题目应要求区分相邻概念、判断边界或分析失败场景；答案紧随其后并默认折叠。

交付前额外确认：

- [ ] 文章没有把工具列表当成系统结构；
- [ ] 概念密集文章在正文前交代了整体结构与主线；
- [ ] 贯穿案例确实承载了抽象概念；
- [ ] 每个核心阶段或组件都回答了问题、输入、输出、证据与结束门槛；
- [ ] 控制流、数据流、状态流、外部副作用与失败恢复已说明；
- [ ] 高信息密度没有退化成缩写与术语堆叠；
- [ ] 关键工程观点有原始资料或可靠证据；
- [ ] 事实、设计决定、待验证假设、观点与当前研究限制已被区分；
- [ ] 代码只用于验证机制，没有挤占结构解释；
- [ ] 自检题能够检验边界、取舍和失败场景，而非只要求复述名词。

## 12. 已吸收的个性化反馈

- 不能把数学成熟度外推为软件工程术语经验；
- 抽象概念必须从可观察行为和贯穿案例中长出来；
- 重点是系统组成、职责、关系、接口与数据/控制/状态流，不是工具罗列；
- 工程阶段必须解释它解决什么问题、产出什么证据以及何时可以进入下一阶段；
- 概念密集文章需要在正文前交代整体结构，非核心术语降为“只需识别”；
- 软件术语不熟不意味着降低知识密度，而应通过就地定义、完整案例和关系结构降低理解成本；
- Docker 学习基线已修正为“知道用途，但尚未理解内部原理且没有实操经验”。

可复用的计算机领域反馈写入本文件；只针对某个框架、代码库、工具版本或单个项目的修正留在原文章反馈区。
